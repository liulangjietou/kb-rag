# 持久化任务调度投入决策

> 结论：当前不投入通用持久化任务调度平台；达到下述证据门槛后再立项（2026-08-14）。

## 1. 第一性原理判断

持久化调度解决的是“多个进程如何只领取一次、宕机后如何续租、重试如何不重复产生副作用”，不是把
`@Scheduled` 换成另一个框架。当前主服务仍以单实例为明确基线，真实生产数据尚未证明调度重复、主节点
切换时延或积压吞吐已经成为主要约束。此时先引入调度中间件，会新增运维组件、租约状态机、幂等键、
迁移与监控成本，却没有可验证的收益，因此本轮刻意不开发该能力。

## 2. 当前事实

- `t_kb_task` 已持久化 PARSE / INDEX / REBUILD / CLEANUP 的状态与进度，但执行仍由进程内 Executor
  直接提交；它是可观测事实，不是支持竞争领取的任务队列。
- Web/外部源同步、治理清理、审计归档、快照保留等由每个实例的 `@Scheduled` 触发；多实例会重复扫描。
- 索引 upsert、同步补偿等部分动作天然幂等，但外部抓取、归档、清理与长任务没有统一的 lease/owner/
  heartbeat/attempt 语义，不能据此宣称多实例安全。
- M24 模型预占恢复依赖耐久行与乐观锁，已具备多实例重复扫描安全性；这是一个局部不变量，不能替代通用调度。

## 3. 立项触发器

以下任一硬条件在真实环境持续出现，即重新评审；满足“多实例部署”且至少一项运行证据后立项：

1. 生产稳定运行 `kb-rag-server >= 2` 副本，滚动发布期间必须继续接收异步任务。
2. 30 天内出现因重复扫描造成的重复外部请求、重复归档/清理或状态覆盖事件，并有 request_id/任务行证据。
3. 单实例任务队列 P95 等待超过 60 秒或 backlog 连续 15 分钟高于执行并发的 10 倍，且调大单机并发受模型
   限流、CPU、内存或数据库连接池约束。
4. 明确提出任务接管 SLA：实例失效后 5 分钟内必须被其他实例续跑，而当前人工重试或补偿扫描无法满足。

“预计未来会扩容”不算证据；一次偶发慢任务也不算。先采样任务排队、执行、重试、重复副作用和恢复时延。

## 4. 立项后的最小方案约束

立项时先统一任务协议，再选实现（数据库竞争队列、成熟调度器或消息系统）：

- 任务行至少包含 `tenant_id`、payload/version、idempotency_key、priority、next_run_at、attempt/max_attempts、
  lease_owner/lease_until、heartbeat_at、last_error_type；领取必须是数据库原子状态转换。
- 执行采用 at-least-once，所有 handler 必须声明幂等键；不得承诺无法由基础设施保证的 exactly-once。
- 进程死亡后按 lease 接管，重试采用退避与死信终态；暂停、取消、人工重放都必须是持久状态转换。
- 计量上下文随任务持久化，后台模型调用仍归属原租户；敏感正文和凭据不得进入任务 payload。
- 迁移按任务类型逐条进行，旧 `@Scheduled` 与新消费者不可同时对同一类型生效；提供开关、回退和重复执行演练。
- 上线前必须有双实例竞争领取、kill -9 接管、幂等重放、毒任务隔离、租约时钟偏差和积压恢复测试。

## 5. 当前行动

保留现有单实例部署说明；监控 backlog 与补偿结果；新增长任务时要求业务幂等和可恢复状态。未达到触发器前，
不新增 Redis 锁、Quartz、XXL-JOB、消息队列或自研任务中心。
