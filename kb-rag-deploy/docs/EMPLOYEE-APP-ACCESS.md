# 员工应用使用授权

普通员工使用正式应用需要 `app:use` 和角色的应用范围。`app:read`、`app:write`、`app:release`、`search:debug` 分别服务管理或调试，不自动授予员工使用权限。

## 管理员操作

在“角色与权限”中同时设置功能权限、知识库范围和应用使用范围：

- 指定应用：可以留空，留空表示该角色不提供任何应用使用范围。
- 本租户全部应用：包括此后创建的应用；实际使用仍要求有正式版本，并且所有关联知识库都在当前用户范围内。
- 多角色继续遵循现有并集规则：功能权限和各类数据范围分别取并集。
- 应用候选项包含尚未发布的应用，方便提前配置授权；员工目录只返回当前可使用的正式应用。

编辑其他租户的角色时，候选应用来自该角色所属租户。客户端不提交目标租户；服务端先通过角色根资源检查，再读取所属租户的名称和标识。应用列表加载失败时保留表单并允许重试，保存失败保留名称、权限和选择。

## 接口与职责

| 入口 | 权限与行为 |
| --- | --- |
| `GET /api/v1/roles/app-options?role_id=...` | `role:manage`；不传角色 ID 时使用当前用户租户，仅返回 `app_id/name` |
| `POST/PUT /api/v1/roles...` | 角色行、功能权限、知识库范围和应用范围在同一事务内保存 |
| `GET /api/v1/workspace/apps` | `app:use`；只返回当前允许使用的正式应用名称、描述和正式版本标识 |

新增角色字段为 `app_scope_all` 和 `app_ids`。更新请求整体省略这两个字段时保留应用范围，兼容旧客户端；创建请求省略时默认没有范围。只提交 `app_ids` 而不声明范围模式会返回 400。指定列表最多 2,000 项，每个 ID 必须非空且不超过 64 字符。

`RoleService` 负责角色根资源授权与整体事务；`RoleAppScopeService` 负责应用范围校验、替换和批量读取。范围不接受其他租户、已删除或不存在的应用。数据库乐观更新返回零行时，角色服务会拒绝后续授权替换。此检查保护服务端读写期间的并发冲突，当前角色编辑接口仍沿用既有的完整替换协议。

员工目录重新读取数据库中的用户与角色授权，使用只读可重复读事务装配一致的主体快照，不读写权限缓存。随后再次检查租户存在且启用、应用根资源租户、正式版本及所有关联知识库根资源和范围。应用目录不是后续问答请求的授权凭证；会话创建、提问、历史读取仍须独立执行当时的资源授权。

旧缓存缺少 `appIds` 字段时会被视作未命中，重新装配新主体。既有管理接口缓存策略继续保留；本批没有改造所有管理接口的缓存并发失效机制。员工内容入口不得仅依赖缓存里的旧应用范围。

## 数据迁移与回退

V27 增加 `t_kb_role.app_scope_all` 和 `t_kb_role_app`，并新增 `app:use` 权限。迁移只向存活的内置 `SUPER_ADMIN` 授予初始使用权限和全范围；其他角色默认空范围。新租户复制内置角色时只复制范围模式，不复制源租户的具体应用 ID。

应用删除后清理其角色范围关联；角色删除也清理关联。范围替换使用物理删除和重新插入，`(role_id, app_id)` 唯一约束避免重复授权行。

部署顺序为先执行增量迁移，再部署服务端和前端。回退应用代码时保留 V27 的增量表、列和授权数据；旧版本只读取原有列，不要求删除新数据。不要通过删除权限目录行或回滚 Flyway 历史来模拟应用回退。再次升级时可以继续使用已保存的应用范围。

## 验证范围

- 真实 MyBatis、租户插件和 Spring 事务：跨租户拒绝、整组回滚、指定/空/全范围、旧客户端保留、应用删除清理。
- 主体解析：多角色并集、旧 JSON 缓存升级、管理权限不推导使用权、重新读取已撤销范围。
- HTTP 契约：角色接口的字段绑定和校验、候选目录权限、员工目录权限及敏感配置不出现在响应中。
- 浏览器：加载失败重试、保存失败保留、跨角色迟到响应、390px 下新角色的空范围和全范围保存。
- MySQL 8.0.36 隔离验证库：完整 V1–V27 顺序执行、初始权限范围与唯一约束。

本批提供角色授权和员工正式目录接口。员工问答页面、会话持久化、运行幂等恢复、历史答案与引用的当前 ACL 校验在后续批次实现；此目录不能替代这些内容链路的验收。
