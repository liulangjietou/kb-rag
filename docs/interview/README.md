## 编号与检索约定

- **编号稳定**：编号一经发布不再改动；新增题目追加在对应题库的末尾编号，不插队、不重排。互链一律写编号（如「见 P033」「详见 R21」），不写「第 N 题」。
- **每题一个标题**：R、B 用二级标题，P、T、S 用三级标题；标题格式都是 `编号 + 空格 + 题目`，可以直接按编号全文搜索。
- **检索行**：每题标题下一行固定为 `> 标签：… ｜ 难度：… ｜ 关联：…`。
  - **标签**：知识点关键词，同一概念全库用同一个词（如「Prompt注入」「长任务运行时」「发布门禁」）。
  - **难度**：★ 基础 / ★★ 进阶 / ★★★ 高级岗区分度题。
  - **关联**：正文里引用到的其他编号，按出现顺序，最多 6 个。
- **自包含**：每题的答案可以单独阅读；需要展开的细节用编号互链，而不是依赖上下文。

## 推荐读法

1. **第一遍（建立骨架）**：读 03 的「十条原则」和 01 的 P001–P010，能用 3 分钟讲清项目与方法论。
2. **第二遍（项目深挖）**：精读 01 全文，遇到 R 编号就跳到 [RAG 八股](../RAG面试八股.md) 对应题目。
3. **第三遍（理论补齐）**：刷 02，每题答完用「我们在项目里是这样做的」收尾，把理论落回项目。
4. **第四遍（开放题）**：做 04，排障题先练「先分检索还是生成」这一刀，设计题先练需求澄清。
5. **面试前一天**：看 01 的踩坑复盘（P127–P134）与已知缺口（P137），以及 RAG 八股文末的参数速查。

## 把题库导入知识库检索

题库本身就是一份结构良好的 Markdown 语料，可以导入 kb-rag 做检索与问答（也是一次很好的自测）：

1. **切分策略选 heading，层级设为 3**：`HeadingTextSplitter` 按 `^#{1,3}\s` 开启新块，分片边界对齐题目边界，标题和检索行留在各自题目的开头。
2. **理解合并与再切分**：heading 策略把块交给定长切分器打包——短题会与相邻题贪心合并到 token 预算内，单题超过预算会按定长再切。想尽量一题一片，就把 token 预算设到能覆盖大多数题目的长度，并用评测集验证。
3. **按编号精确查**：编号（如 `P033`、`R21`）是连续的字母数字串，BM25 可以直接命中；标签词同理。
4. **按题库分库或用文件名区分**：需要只查某一类题时，按文件分知识库，或在元数据里记录来源文件。

## 答题框架

高级岗的评分点是四种意识，每道题都往这四个方向答：

| 意识 | 面试官在问什么 | 答题动作 |
| --- | --- | --- |
| 取舍 | 为什么不是另一种方案？代价是什么？ | 先给结论，再说放弃了什么 |
| 闭环 | 你怎么证明改动是正向的？ | 评测集、门禁、指标 |
| 边界 | 方案在什么情况下失效？ | 主动讲已知缺口和修法 |
| 演进 | 复杂度是什么时候、因为什么引入的？ | 用真实信号解释，而不是「预计未来」 |

答题格式：**先结论后论证**——一句话结论 → 两三条关键理由 → 一个真实的数字或代码位置 → 代价或边界。

## 口径约定

- 「本项目」「kb-rag 落地」指本仓库主干实现，类名可在 `kb-rag-server` 中直接检索。
- 数字以 `application.yml` 运行时默认值为准；个别类内默认值或部署模板与之不同（例如重排模型类内默认 `gte-rerank`、运行时默认 `gte-rerank-v2`；渲染抓取等待策略代码默认 `load`、`.env.example` 为 `networkidle`）时，文中分别注明。
- 需求文档里写了、代码没有实现的内容，一律标注为偏差，集中登记在 RAG 八股文末的「文档与代码偏差登记」。
