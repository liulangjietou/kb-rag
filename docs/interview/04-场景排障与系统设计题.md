# 知识库场景排障与系统设计题（Agent 应用开发 · 高级岗）

> 定位：[RAG 八股](../RAG面试八股.md)（R）、[项目题](01-项目全量面试题.md)（P）、[理论八股](02-知识库八股面试题.md)（T）回答「是什么、为什么、项目里怎么做」；本文回答两类开放问题：**线上出了问题怎么查**，**给你一个业务场景怎么设计**。这两类是高级岗面试区分度最高的部分，没有标准答案，考的是定位思路和取舍。
>
> 编号 S01–S63，编号稳定。每题标题下一行是检索行 `> 标签 ｜ 难度 ｜ 关联`。排障题按「先判断 → 排查步骤 → 根因与修法 → 本项目落点 → 易错点」作答；设计题按「需求澄清 → 方案 → 关键取舍 → 风险与验收」作答。全库编号与标签索引见 [题目索引](题目索引.md)。

## 答题框架

**排障的第一刀：先分清是检索问题还是生成问题。** 看这次回答引用的资料：资料里没有答案，是检索问题（没召回、被过滤、排太后）；资料里有答案但回答错了，是生成问题（Prompt、上下文组织、模型能力、截断）。这一刀切错，后面所有调参都白做。

**检索问题的四个位置**，按链路顺序查：

1. **能不能被检索到**：文档状态（解析、索引、审核、有效期、回收站）、激活版本、快照可见集、文档 ACL、分片是否被禁用。
2. **召回了没有**：BM25 与向量各路的原始排名，分词和嵌入是否覆盖了这类表达。
3. **排序对不对**：融合、重排后的位置，是否被 `top_n` 截断。
4. **阈值有没有误杀**：阈值作用在哪个分数上，是否在跨查询不可比的分数上设了绝对阈值。

**修复的闭环**：复现 case → 收进评测集 → 改动 → 评测对比（带置信区间）→ 门禁 → 发布 → 线上指标确认。只修单个 case 不进评测集，同类问题一定会复发。

## 一、检索效果排障

### S01 用户反馈「答非所问」，你怎么排查？

> 标签：排障、检索、生成 ｜ 难度：★★ ｜ 关联：T008、T153、P041、R02

**先判断**：拿到原始问题和这次回答的引用，看引用资料里有没有正确答案。没有，是检索问题；有，是生成问题。

**排查步骤**

1. **复现**：用同一个应用版本、同样的多轮历史复现。员工运行有冻结的应用版本与语料快照，要在同一版本上复现，否则查的不是同一份语料。
2. **看改写**：多轮场景下先看改写后的实际查询（调试页 `applied` 里的实际查询）。改写丢了指代或引入了错误实体，后面全错。
3. **看路由**：多库应用看实际路由到哪几个库，是否被路由到了无关库。
4. **看各路召回**：正确分片在 BM25、向量各路里排第几；都不在，说明是召回问题；在但融合或重排后被挤出 `top_n`，是排序问题。
5. **看阈值与降级**：`threshold_applied_on` 和 `degraded` 数组，重排超时会让排序退回粗排。
6. **生成侧**：资料有答案但回答错，检查 Prompt 装配顺序、资料是否被截断、是否多个来源冲突。

**常见根因**：问题太口语化或缩写（改写与同义词）；切分把答案切散（切分策略）；答案在表格或图片里（解析）；多库路由错；`top_n` 太小；资料之间互相矛盾。

**本项目落点**：检索调试页逐分片展示各路原始分、归一化分、融合分、重排分和 `score_type`（P041）；问答调试的耗时诊断（P049）；修复后走质量问题闭环（P079）。

**易错点**：不先分检索还是生成，直接换模型或调 Prompt。

### S02 新上传的文档搜不到，可能是哪些原因？

> 标签：排障、索引、治理 ｜ 难度：★★ ｜ 关联：R24、T064、P011、P022

**先判断**：「搜不到」往往不是检索算法问题，而是文档**还不具备被检索的资格**。按「能不能被检索到」逐项排除。

**排查清单（按链路顺序）**

| 环节 | 检查点 | 本项目的状态 |
| --- | --- | --- |
| 解析 | 解析失败、等待人工确认 | `process_status` 为 `PARSE_FAILED` / `PENDING_CONFIRM` |
| 索引 | 还在排队或索引中；索引失败 | UPLOADED / PARSING / PARSED / INDEXING / `INDEX_FAILED`；同步行是 PENDING 或 FAILED 而不是 SYNCED |
| 版本 | 新版本没激活，检索的是旧激活版本 | 版本状态与激活指针 |
| 治理 | 待审核、未到生效时间、已过期、在回收站 | `publish_status`、有效期、回收站 |
| 权限 | 文档设为 RESTRICTED，调用方角色不在 ACL；开放 API 一律看不到 RESTRICTED 文档 | `visibility` + ACL |
| 快照 | 正式版调用走冻结快照，发布之后上传的文档不在快照里 | 需要重新发布版本 |
| 查询 | 知识库选错、`metadata_filter` 过滤掉了 | 调试页 `applied` |

**最常被忽略的一条是快照**：管理台调试用当前语料能搜到，Agent 调正式版搜不到，原因是正式版跑的是发布时冻结的语料。这是设计如此，不是故障，要重新发布版本。

**本项目落点**：文档页按处理状态、发布状态、来源筛选，`rebuild-status` 返回全库处理中数量；首页知识待办汇总「解析待确认」「文档待审核」「网页抓取失败」「外部来源需处理」四类事项（P026）；快照语义见 P077、P083。

**易错点**：看到「上传成功」就以为能检索。上传成功只代表服务端已接收。

### S03 为什么会召回到文档的旧版本内容？

> 标签：排障、版本管理、索引 ｜ 难度：★★ ｜ 关联：R15、T112、P015、P037

**先判断**：分三种情况——旧版本本来就应该可见（快照语义）、版本过滤漏了（缺陷）、旧版本残留在引擎里（一致性问题）。

**排查步骤**

1. 看调用路径：正式版走冻结快照，快照里就是旧版本，这是正确行为；想让线上看到新版本，要重新发布。
2. 看激活版本：新版本是否已激活，还是停在待审核、待确认。
3. 看检索侧过滤：每个分片带 `version_id`，检索侧强制按可见版本集过滤，这一步不可关闭；如果过滤逻辑被某条路径绕过，就会漏出旧版本。
4. 看引擎残留：切换版本后旧分片是否已从引擎删除；别名是否同时指向新旧两个物理索引。

**本项目落点**：版本可见集由 `RetrievalIndexContextResolver` 一处解析，快照路径与当前路径不混用（P037、P127）；ES 别名双指向的踩坑见 P134。

**易错点**：用「删除旧版本」的方式修，结果把快照依赖的版本删了，导致已发布版本召回为空。被快照引用的版本禁止归档就是为了防这个。

### S04 专有名词、产品型号、错误码搜不到，怎么办？

> 标签：排障、BM25、中文分词 ｜ 难度：★★ ｜ 关联：T076、T078、P027、R17

**先判断**：精确匹配类查询是向量检索的弱项，问题多半在 BM25 这一路：要么分词把词切碎了，要么这一路根本没跑。

**排查步骤**

1. 看 `degraded`：有没有 `vector_route_unavailable`，或反过来 BM25 这一路被评测模式关掉了。
2. 用 ES `_analyze` 看分词结果：「KB-2031」「qwen3-rerank」这类词在 standard 或 IK 分词下被切成什么。
3. 看向量排名：型号类字符串的嵌入往往语义不稳定，排名靠后正常。
4. 看融合权重：加权融合时 BM25 权重太低，精确命中被向量结果淹没。

**修法**

- IK 自定义词典加入专名、型号，热更新（P027），**然后重建索引**，否则只有查询侧生效。
- 关键字段（编号、型号）作为元数据字段，用 `metadata_filter` 精确过滤。
- 用 RRF 融合，精确命中的 BM25 排名第一能直接进入前列。
- 同义词与缩写表（「K8s」与「Kubernetes」）。

**易错点**：只加词典不重建索引，查询侧和索引侧分词不一致，反而更搜不到。

### S05 系统总是拒答（「资料中没有相关信息」），怎么排查？

> 标签：排障、阈值、生成 ｜ 难度：★★ ｜ 关联：R21、T083、T094、P033

**先判断**：拒答有两种来源——检索没给资料（阈值误杀或召回为空），或者给了资料但模型判断不相关。先看这次调用返回的节点数。

**排查步骤**

1. **节点为空**：看阈值作用在哪个分数上（`threshold_applied_on`）。阈值应该打在重排分这类跨查询可比的分数上；重排关闭或降级时退回向量 cosine 分，BM25 单路时阈值不生效。换了重排模型，分数分布变了，旧阈值可能整体偏高。
2. **节点不为空但拒答**：看拒答提示词是否过严（「不确定就拒答」），资料是否被截断到只剩标题。
3. **期望拒答用例**：评测集里要有期望拒答的用例，才能同时衡量「该答没答」和「不该答却答了」。

**修法**：用评测集重新标定阈值（看 Hit Rate 与误答率的权衡），不要凭几个 case 手调；拒答提示词写清「部分相关时回答相关部分并说明缺失」。

**本项目落点**：`threshold_inactive` 降级码表示当前分数类型不可比，阈值没有生效（P033、P036）；最终答案评测的期望拒答用例（P075）。

**易错点**：为了减少拒答把阈值调到很低，结果无关资料进入上下文，幻觉上升。

### S06 回答里的引用编号对不上内容，或者引用了不存在的资料，怎么办？

> 标签：排障、引用、幻觉 ｜ 难度：★★ ｜ 关联：R32、T108、P044、P069

**先判断**：分两种——模型编造了不存在的编号（引用越界），或者编号存在但内容不支持这句话（引用不忠实）。前者可以确定性检测，后者需要评测。

**排查与修法**

1. **越界**：答案里出现的编号必须在本轮引用列表范围内。项目用 `AnswerCitationValidator` 校验，越界返回 `ANSWER_CITATION_INVALID`（502），不把错误答案当成功返回。
2. **编号错位**：引用数组必须保留本轮检索的原始顺序与数量，**即使条目重复也不能去重压缩**，否则后续编号全部错位（P069）。
3. **不忠实**：用答案评测的「引用正确性、引用完整性」两维打分；Prompt 要求每个结论都给出来源，引用条目做 JSON 转义、编号与原文分开编码，文章里自带的章节号不能被当成引用号。
4. **前端**：编号超出本轮引用数的 `[n]` 不渲染成可点击引用（P117）。

**易错点**：只在前端隐藏越界引用，服务端仍返回成功，错误答案照样进入 Agent 的后续推理。

### S07 多轮对话越聊越偏，指代词找不到对象，怎么排查？

> 标签：排障、多轮对话、查询改写 ｜ 难度：★★ ｜ 关联：R20、T089、T122、P067

**先判断**：多轮问题几乎都出在改写：当前问题「那它的价格呢？」没有被改写成完整问题，检索就是在搜「它的价格」。

**排查步骤**

1. 看改写后的实际查询；看改写用了几轮历史（项目取最近 6 轮）。
2. 改写超时或失败时退回原始问题，`degraded` 里有 `query_rewrite_timeout` / `query_rewrite_error`，多轮场景会明显变差。
3. 看历史里是否混入了不该带的内容：员工运行只带**可读的成功**历史，撤权资料派生的问答整对排除（P067）。
4. 看话题切换：用户换了话题，改写却强行把旧实体带进来。

**修法**：改写 Prompt 明确「指代消解 + 保留原意 + 话题切换时不继承」；改写输出只作检索词，不直接进入最终 Prompt；多轮用例单独建评测分组（报告按单轮 / 多轮分组）。

**易错点**：把完整对话历史直接拼进检索查询，长历史把当前意图稀释掉。

### S08 同一个问题问两次，答案不一样，正常吗？

> 标签：排障、生成、一致性 ｜ 难度：★★ ｜ 关联：T115、T120、P078

**先判断**：要区分三层不确定性：检索结果变了、生成采样不同、底层数据变了。

| 层 | 原因 | 处理 |
| --- | --- | --- |
| 数据 | 两次之间文档更新、版本激活、治理状态变化 | 正式版走冻结快照，语料不变 |
| 检索 | 改写结果不同（改写本身调模型）、缓存命中与否、重排超时退回粗排 | 看两次的 `applied` 和 `degraded` |
| 生成 | temperature 大于 0 的采样随机性 | 事实问答用低温度；评测 Judge 固定 `temperature=0` |

**本项目落点**：正式版调用固定应用版本与语料快照；评测可复现依赖冻结输入、语料指纹与配置快照（P078、P085）。

**易错点**：把「措辞不同」和「事实不同」混为一谈。措辞不同可以接受，事实不同必须查。

### S09 表格类问题（数值、对比）总是答错，怎么办？

> 标签：排障、文档解析、切分 ｜ 难度：★★★ ｜ 关联：T016、T113、T137、R03

**先判断**：表格问题通常在解析和切分阶段就坏了，不是模型的问题。先看入库后的分片长什么样。

**排查步骤**

1. **解析**：表格是否被解析成按行拼接的纯文本，表头与数据行失去对应关系；扫描件表格是否 OCR 错位。
2. **切分**：定长切分把一张表切成几段，后几段没有表头，数值失去语义。
3. **检索**：问题问「某产品 2024 年销量」，表格分片里只有数字，BM25 和向量都很难匹配。
4. **生成**：跨行计算、求和对比，模型容易算错。

**修法**：表格按行或按块切分并在每块重复表头；表格转 Markdown 保留结构；为表格生成一句自然语言描述提升召回；数值计算交给工具（SQL 或计算器）而不是让模型心算。

**本项目边界**：需求文档里的「表格行级切分」代码没有实现，面试时照实说，并说明要不要补由评测决定（P014）。

**易错点**：把表格问题当 Prompt 问题调，改一百遍 Prompt 也补不回丢失的表头。

### S10 扫描件或图片里的内容搜不到，怎么排查？

> 标签：排障、OCR、多模态 ｜ 难度：★★ ｜ 关联：R04、T014、T020、P013、P042

**排查步骤**

1. **是否识别为扫描件**：没有文本层的 PDF 要走 OCR；判定错了会得到空文本。
2. **OCR 质量**：看解析预览，识别率低、版面错乱、竖排或手写都会影响；OCR 引擎是否可用（本地 PaddleOCR 兜底需要可选依赖，缺失时任务失败原因会明确提示）。
3. **图片是否有文本代理**：图片要经过视觉模型转写成文本代理才能被 BM25 与文本向量检索；视觉模型没配置，图片就只有文件名。
4. **多模态路**：知识库开了多模态并配置了嵌入模型，才有第三路；正式版的快照路径不走多模态路（P038）。

**修法**：扫描件先看解析预览确认质量；关键文档人工修正分片；需要「图搜图」时开多模态索引并重建。

**易错点**：以为开了多模态就能搜到图片里的文字。多模态嵌入擅长语义相似，图片里的精确文字（型号、数字）仍然要靠 OCR 或视觉模型转写。

### S11 撤掉了某人的权限，他还能看到那份文档的内容，为什么？

> 标签：排障、权限、缓存 ｜ 难度：★★★ ｜ 关联：T178、T181、P037、P067、P090

**先判断**：权限变更后仍可见，通常是某一层缓存或快照「冻结」了授权结果。先确认是哪条链路看到的：检索结果、历史回答、还是前端页面残留。

**排查步骤**

1. **权限缓存**：会话与 RBAC 权限缓存是否及时失效；多实例时会话与权限缓存必须同时切到 Redis，否则一台失效、另一台还在用旧缓存（P090）。
2. **快照**：发布快照冻结的是「哪些版本作答」，**不冻结「谁能看」**；项目的文档 ACL 在快照和当前两条分支都实时裁剪、不走缓存（P037）。如果某个实现把 ACL 结果一起冻结了，就是缺陷。
3. **历史回答**：员工的历史问答是由旧资料派生的。项目在读取历史和进入模型上下文时都重新校验，任一来源不可读就遮蔽整条回答及引用（P067）。
4. **前端残留**：页面没有在授权范围变化时清空已加载的数据和草稿（P116）。
5. **派生数据**：摘要、记忆、语义缓存里是否复制了受限内容。

**易错点**：只隐藏引用、保留由它派生的答案正文。答案本身就是受限内容的转述。

### S12 换了嵌入模型之后，检索效果反而下降了，怎么办？

> 标签：排障、嵌入、评测 ｜ 难度：★★★ ｜ 关联：R10、T054、P017、P076

**先判断**：先确认「下降」是真的：评测集是否代表线上分布，差异是否超出置信区间。然后检查迁移过程本身有没有出错。

**排查步骤**

1. **迁移完整性**：新模型的索引是否全量重建完成，别名是否切到新索引；新旧向量混在一个索引里，分数毫无意义。
2. **查询侧**：查询嵌入是否也换成了新模型；非对称模型是否需要查询前缀或指令。
3. **分数分布**：新模型的相似度分布不同，旧阈值可能整体误杀，要重新标定。
4. **领域适配**：通用榜单高分的模型不一定适合你的领域和语言。

**正确的换模型流程**：新模型建新物理索引 → 从 MySQL 事实源全量重建 → 在新索引上跑评测集对比 → 门禁通过 → 别名原子切换 → 保留旧索引一段时间以便回滚（P017）。

**易错点**：看 MTEB 排名选模型，不用自己的评测集验证。

## 二、生成与答案排障

### S13 离线评测指标很好，线上用户体验却很差，可能是什么原因？

> 标签：排障、评测、运营闭环 ｜ 难度：★★★ ｜ 关联：T151、T150、P048、P080

**常见原因**

1. **评测集不代表线上**：评测问题是标注员写的，用户实际问法更口语、更短、带错别字、多轮指代。
2. **评测链路与线上不一致**：评测走的 Prompt、检索参数、模型与线上不同。项目要求评测复用生产检索链路与同一个 `AnswerGenerationService`，就是为了消除这一条（P048、P080）。
3. **语料不一致**：评测时的语料和线上快照不同。
4. **只评检索不评答案**：Recall 高不代表答案对。
5. **体验问题不在指标里**：首字延迟、引用可读性、拒答话术。
6. **分组被平均掉**：多轮、图片、表格类问题占比小，总体指标掩盖了它们的失败。

**修法**：用线上真实问题（脱敏后）补充评测集；零命中和 BAD 反馈进入质量问题流程转成用例；报告按单轮 / 多轮、span 级 / 文档级分组看。

**易错点**：继续在离线指标上调参，越调离线越好，线上越差。

### S14 发布门禁总是判 GATE_LOG_ONLY，发不出去，怎么办？

> 标签：排障、发布门禁、评测集 ｜ 难度：★★ ｜ 关联：P076、P081、P082、R38

**先判断**：`GATE_LOG_ONLY` 不是「失败」，而是「证据不足以自动决策」。四种情况对应四种处理：

| 原因 | 处理 |
| --- | --- |
| 没绑评测集 | 绑定门禁评测集 |
| 有效用例少于 50 | 扩充评测集；样本太少，差异落在噪声里 |
| 重试后仍有降级用例 | 查降级原因（模型不可用、超时），先修稳定性 |
| 待复核用例占比超过 15% | 文档更新导致证据失效，去证据复核工作台处理（P081） |

真有紧急发布需要时，用 `release?force=true` 留痕放行，审计里能查到是谁、为什么放行。

**易错点**：长期依赖 force 放行，门禁形同虚设；或者为了过门禁删掉难的用例。

### S15 应用回滚到历史版本后，检索结果全空，怎么排查？

> 标签：排障、版本管理、发布门禁 ｜ 难度：★★★ ｜ 关联：P077、P127、R24

**这是项目踩过的真实问题**（P127）。

- **现象**：回滚到历史正式版，检索返回空。
- **根因**：发布时只冻结了索引快照，没冻结可见版本集。回滚后，旧快照索引配上当前的可见集，版本 ID 对不上，全部被强制过滤。
- **修法**：发布快照同时固化 `index_snapshots` 与 `visible_version_ids`；可见集解析收敛到一处，快照路径绝不经过当前激活集。

**如果今天再遇到**，还要排查：快照索引是否被保留期清理删掉了（这时会返回 `snapshot_index_missing` 降级，退回当前语料）；被快照引用的文档版本是否被归档。

**易错点**：同一个决策的两半（查哪个索引、看哪些版本）分散在不同地方解析。

### S16 回答经常被截断在一半，怎么处理？

> 标签：排障、生成、上下文构建 ｜ 难度：★★ ｜ 关联：T114、P045

**先判断**：看模型返回的 `finish_reason`。`length` 表示达到了输出上限，是截断；`stop` 是模型自己结束。

**排查与修法**

1. **检测**：项目把 `finish_reason=length` 识别为 `OUTPUT_TRUNCATED` 错误类型，不把截断的答案当完整答案返回（P045）。
2. **输出预算**：`max_tokens` 太小；或者上下文太长，挤占了模型总窗口留给输出的空间。
3. **上下文预算**：控制注入资料的字符预算（`max_content_length`），优先保留高分资料，而不是把 `top_n` 调大。
4. **任务拆分**：「列出所有 xx」这类长输出问题，改为分页或结构化输出。

**易错点**：只调大 `max_tokens`，不控制输入长度，成本和延迟一起上升。

### S17 回答引用了已经失效或过期的内容，怎么避免？

> 标签：排障、治理、版本管理 ｜ 难度：★★ ｜ 关联：T112、P022、P037

**排查步骤**

1. 失效内容是否在治理上被标记：有效期、下架、回收站。没有标记，系统无从得知它过期了。
2. 标记了但仍被检索到：检查可见集是否叠加了治理谓词。项目从 M11 起可见集叠加发布状态、有效期、回收站三个谓词（P022）；**快照上下文不受影响**，所以已发布版本仍会用发布时的资料。
3. 新旧两份文档同时有效且内容冲突：模型可能引用旧的。

**修法**：内容治理流程（审核、有效期、下架）比算法更重要；冲突资料在 Prompt 里要求「以生效日期最新者为准并说明」；过期资料过多时要重新发布应用版本。

**易错点**：指望模型自己判断哪份资料更新。

### S18 检索结果里有大量重复或高度相似的内容，怎么办？

> 标签：排障、去重、检索 ｜ 难度：★★ ｜ 关联：T018、T103、P040

**常见来源**

| 来源 | 处理 |
| --- | --- |
| 同一文档多次上传、多个版本同时可见 | 内容哈希去重；版本过滤 |
| 不同文档内容相同（转载、复制） | 入库去重或检索后按内容哈希合并 |
| 聊天导入的重叠窗口 | 项目的 `NearDuplicateWindowMerger`（P040） |
| overlap 过大 | 调小 overlap |
| 父子分片多个子片属于同一父片 | 父子合并 |

还可以用 MMR 在相关性与多样性之间取折中。

**易错点**：去重放在重排之后，重复内容已经付过一次重排的钱。

## 三、性能、成本与稳定性排障

### S19 问答延迟高、首字慢，怎么定位？

> 标签：排障、性能、延迟 ｜ 难度：★★ ｜ 关联：T187、P049、P105、R33

**先判断**：先拆分阶段，不要猜。首字延迟 = 检索全程 + 生成首 Token；总耗时再加上生成全文。

**排查步骤**

1. 用分阶段耗时定位：配置解析、检索（其中重排单独计时）、生成首段、生成总耗时。项目的问答调试有服务端与浏览器两组计时（P049）。
2. **检索慢**：改写和重排都要调模型，是检索阶段最大的两块；改写超时预算 800ms、重排 1.5s，超时后降级（P105）。
3. **生成首字慢**：上下文太长；模型排队；没开流式。
4. **排队**：线程池满，项目的检索池和流式生成池队列都为 0，宁可快速降级不排队（P102）。
5. **网络与代理**：反向代理缓冲 SSE，导致用户看不到增量。

**修法**：先砍不必要的阶段（改写只在多轮开）；控制重排候选数；缩短上下文；首字优化靠流式与预热。

**易错点**：只看平均值。要看 P95 / P99，长尾才是用户抱怨的来源。

### S20 模型费用突然暴涨，怎么排查？

> 标签：排障、成本 ｜ 难度：★★ ｜ 关联：T189、P101、R41

**排查步骤**

1. **按维度拆**：按租户、调用类型（对话、嵌入、重排、视觉）、应用、时间拆分用量台账，找出增量来自哪里。
2. **嵌入暴涨**：有人触发了全量重建（换模型、改切分配置导致 `config_stale`），或者大批量入库。
3. **对话暴涨**：某个 Agent 在循环调用；某个调用方重试风暴；Prompt 或上下文变长。
4. **重排暴涨**：候选数调大了。
5. **评测暴涨**：配置矩阵跑了多轮，Judge 开着。

**修法**：租户月配额在出站前原子预占，超额直接 429（P101）；评测提交前看 estimate；Agent 侧设步数与预算上限；限流按 Key 生效。

**易错点**：只看账单总额，没有调用级台账，查不出是谁花的。

### S21 重排超时突然大量增加，怎么处理？

> 标签：排障、重排、降级 ｜ 难度：★★ ｜ 关联：R22、T102、P034、P036

**影响**：重排超时会退回融合后的粗排（`rerank_timeout`），答案质量下降，但服务可用。

**排查步骤**

1. 上游重排服务是否变慢或限流（看调用耗时分布、429）。
2. 候选数是否被调大，文本是否变长（父子分片把长父片送进重排）。
3. 本地线程池是否排队（重排耗时包含调度等待，线程池拒绝也计为失败）。
4. 降级率告警：最近 5 分钟降级占比超过 30% 且样本至少 20 条会告警（P106）。

**修法**：限制候选数与每条文本长度；超时时间按 P99 设；上游不稳定时考虑备用模型；持续降级时要在门禁里体现（重试后仍降级的用例会让门禁判 LOG_ONLY）。

**易错点**：把超时调得很长来「避免降级」，结果整体延迟和线程占用一起失控。

### S22 零命中率突然升高，意味着什么？

> 标签：排障、可观测、运营闭环 ｜ 难度：★★ ｜ 关联：P107、P109、T191

**先判断**：零命中率是 RAG 最早的故障信号之一，「服务全绿、答案全错」时它会先动。要区分**系统故障**和**内容缺口**。

| 类型 | 特征 | 处理 |
| --- | --- | --- |
| 系统故障 | 所有库、所有问题一起升高；伴随降级率上升 | 查引擎、别名、嵌入服务、快照索引 |
| 配置变更 | 某次发布之后突然升高 | 对比版本差异（P084），必要时回滚 |
| 内容缺口 | 集中在某类问题、某个新业务 | 从检索洞察的内容缺口报表补内容 |
| 用户行为 | 新用户群、新入口带来新问法 | 补同义词、补评测用例 |

**本项目落点**：检索洞察在 API 边界记录，只存脱敏后的查询摘要；零命中可以直接建质量问题（P079、P109）。

**易错点**：零命中率上升就降低阈值，把内容缺口掩盖成了幻觉。

### S23 双写积压、引擎和数据库不一致，怎么处理？

> 标签：排障、一致性、索引 ｜ 难度：★★★ ｜ 关联：R14、T190、P016

**先判断**：MySQL 是唯一事实源，引擎是派生数据。不一致时以 MySQL 为准，修复方向永远是「从事实源重放或重建」。

**排查步骤**

1. 看同步状态表：待同步行的数量与最早时间；积压超过 1000 会告警（P106）。
2. 看失败原因：引擎不可达、嵌入限流、映射冲突。
3. 看补偿扫描是否在运行、是否被同一批毒数据反复卡住。

**修法**：引擎恢复后补偿扫描自动追平；大面积不一致直接从事实源全量重建并切别名；单条毒数据要能跳过并记录，不能卡住整批。

**易错点**：手工去引擎里删改数据，事实源和派生数据的关系从此说不清。

### S24 用户点了停止，账单里还是有这次调用的费用，正常吗？

> 标签：排障、成本、流式 ｜ 难度：★★ ｜ 关联：P047、P050、T121

**正常，这是诚实计费的结果。** 关闭本地连接只能「发起」取消，不能保证供应商已经停止计费。

项目的口径（P050）：

- 请求还没发出就取消：释放预占，不计费。
- 已发出后取消，拿到了 usage：按实际用量结算。
- 已发出后取消，没拿到 usage：按预占上界结算，标 `CANCELLED + estimated`。
- 未定价的费用显示「未定价」，不显示成 0。

**排查要点**：停止后服务端是否真的取消了上游请求（心跳每 5 秒一次，用来发现静默期的断连）；是否有代理缓冲导致服务端迟迟感知不到断开。

**易错点**：为了账单好看，把取消的调用当作零费用，实际成本被低估。

## 四、数据、权限与 Agent 接入排障

### S25 批量入库很慢，任务大量积压，怎么办？

> 标签：排障、性能、数据接入 ｜ 难度：★★ ｜ 关联：T192、T201、P102、P104

**排查步骤**

1. 看哪个阶段慢：解析（OCR 最慢，CPU 档 100 页可能要 30 分钟）、嵌入（模型限流）、写引擎。
2. 看并发：索引池刻意小（4 线程加有界队列），防止批量入库饿死控制台；嵌入有全局并发上限，满了回压提交者（P102）。
3. 看失败重试：大量失败任务在反复重试。
4. 看是否触发了不必要的全量重建。

**修法**：OCR 类文档走 GPU 档或提前离线处理；嵌入批量化并控制并发与退避；批量入库错峰；确认是否真的需要持久化调度——达到「单实例任务排队 P95 超过 60 秒」这类门槛才考虑（P104）。

**易错点**：直接调大所有线程池，模型限流更严重，失败重试更多。

### S26 发现一个租户能看到另一个租户的数据，怎么应急？

> 标签：排障、多租户、安全 ｜ 难度：★★★ ｜ 关联：T181、P087、P088、P132

**应急顺序**：止血 → 评估范围 → 根因 → 系统性修复 → 复盘。

1. **止血**：下线或拦截出问题的入口；必要时暂停相关 API Key。
2. **评估范围**：从审计日志查哪些账号、哪些资源、什么时间段被跨租户访问。操作审计有「谁」维度，开放 API 审计有 Key 维度（P099）。
3. **根因**：看这条链路上**有没有一次对根表的查询**。从属表按 ID 寻址、只校验数据范围不校验租户，是最常见的形态（P087）。
4. **系统性修复**：不只修这一个入口，按同一判据扫全部同构入口；统一「先解析根（404）再判范围（403）」。
5. **复盘与告知**：按合规要求通知受影响方。

**易错点**：修完报告的那一个端点就结束。越权漏洞往往是一整族。

### S27 Agent 通过 MCP 调用知识库失败，怎么排查？

> 标签：排障、MCP、Agent ｜ 难度：★★ ｜ 关联：T162、T164、P053、P060

**按错误平面定位**（P053、P060）：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 400 / `-32020` | 现代协议的镜像头缺失、畸形或与请求体不一致 | 检查 `MCP-Protocol-Version`、`Mcp-Method`、`Mcp-Name` |
| 400 / `-32022` | 协议版本不支持 | 从 `error.data.supported` 里选版本 |
| 403 空 body | Origin 不在白名单 | 配置 `CORS_ALLOWED_ORIGINS` |
| 401 | Key 无效、禁用或已轮换 | 重新签发或启用 Key |
| 429 | 超 QPS | 按 `Retry-After` 退避 |
| 200 + `isError=true` | 工具业务失败：参数不合法、应用不在授权范围 | 让 Agent 读 content 修参数 |

**还要检查**：应用是否已发布正式版；传了 `stream:true`（MCP 不支持，会返回业务错误）；覆盖参数是否超出白名单。

**易错点**：把工具业务错误当协议错误处理，Agent 看不到错误内容，无法自我修正。

### S28 记忆库「记错了」或出现了别人的信息，怎么排查？

> 标签：排障、记忆、多租户 ｜ 难度：★★★ ｜ 关联：T157、T158、P056、P057

**先判断**：分「写错了」和「读串了」。

**写错了**：

1. 看抽取：模型从对话里抽出的记忆是否忠实，是否把假设、玩笑、第三方信息当成了用户事实。
2. 看更新：新旧记忆冲突时是否正确覆盖。项目开 `auto_update` 时，把该用户最近 50 条旧记忆连同对话交给模型，模型只能返回 ADD，或「UPDATE + 目标节点 id」，UPDATE 只允许命中这 50 条之内的节点，编造的 id 改不到窗口外的数据（P056）。

**读串了**：

1. 看隔离键：记忆按 Memory Key 绑定的记忆库与 `user_id` 隔离，工具参数不能另行指定库（P057）。
2. 看调用方：`user_id` 是调用方传的，**Agent 侧把用户 ID 传错了**是最常见的原因。

**修法**：提供记忆的查看、更正、删除入口；敏感信息不进入长期记忆；为记忆写入保留来源对话与时间，便于追溯。

**易错点**：把记忆当知识库用，没有冲突处理和遗忘机制。

## 五、系统设计题

### S29 设计一个企业内部知识库问答系统

> 标签：系统设计、架构、权限 ｜ 难度：★★★ ｜ 关联：R46、T005、P004、P138

**需求澄清**（先问再画图）：文档规模与增长速度、文档类型（PDF、Office、网页、Wiki）、用户数与并发、权限模型（部门、密级）、是否需要引用溯源、时效性要求、能否用外部模型 API、上线后谁来运营。

**方案**

- **接入层**：上传、网页、对象存储、Wiki 连接器，统一收敛到一条入库链路；增量同步用版本号或 ETag。
- **处理层**：解析（含 OCR）→ 清洗脱敏 → 切分 → 嵌入 → 双写 BM25 与向量索引；MySQL 作唯一事实源，引擎可重建。
- **检索层**：改写（仅多轮）→ 路由 → 混合召回 → 融合 → 重排 → 权限与版本过滤 → 阈值 → `top_n`。
- **生成层**：带引用的 Prompt、引用校验、拒答策略、流式输出。
- **治理层**：审核发布、有效期、回收站、文档级 ACL、审计。
- **质量层**：评测集、发布门禁、快照回滚、反馈闭环。

**关键取舍**：权限在检索时实时裁剪，不能只在展示层过滤；发布冻结语料快照，保证「门禁测什么，线上跑什么」；没有真实压力前不引入消息队列和调度平台。

**风险与验收**：权限泄露（红队测试）、答案过时（治理流程）、效果不可证明（评测集）。验收看 Recall@K、答案五维分、P95 延迟和权限测试。

### S30 设计一个智能客服知识库

> 标签：系统设计、行业场景、运营闭环 ｜ 难度：★★★ ｜ 关联：T006、T093、T171

**需求澄清**：咨询量与峰值、渠道（网页、App、IM）、是否需要转人工、答错的代价、知识更新频率、是否有历史工单可用。

**方案**

1. **两类知识分开建**：FAQ 问答对（标准问 + 相似问 + 标准答）走「问题对问题」匹配；产品文档走普通 RAG。先查 FAQ，命中高置信直接返回标准答案，未命中再走 RAG。
2. **意图识别前置**：查询订单、退款这类**事务型请求**走工具或业务接口，不走知识库。
3. **澄清与转人工**：低置信、情绪激烈、涉及金额时转人工；歧义问题先反问澄清。
4. **运营闭环**：未命中问题、差评会话每天进入待处理池，运营补 FAQ；新 FAQ 进入评测集回归。
5. **话术控制**：答案模板化，禁止承诺性表述。

**关键取舍**：FAQ 的确定性高于 RAG 的灵活性，客服场景优先确定性；标准答案由运营维护，模型只做匹配和轻度改写。

**风险**：答错导致客诉或资损，所以高风险意图一律不让模型自由发挥。

### S31 设计一个多租户 SaaS 知识库平台

> 标签：系统设计、多租户、安全 ｜ 难度：★★★ ｜ 关联：T068、T181、P086、P087

**需求澄清**：租户数量级、单租户数据规模差异、隔离要求（合规是否要求物理隔离）、是否允许租户自带模型 Key、计费方式。

**方案**

- **隔离模式分级**：小租户共享索引加租户字段过滤；大租户或高合规租户独立索引或独立集群。项目采用索引名带租户段、根聚合表带 `tenant_id` 的方式（P086）。
- **租户根贯穿**：每个入口先解析资源的租户根（404），再判数据范围（403），从属资源经根资源归属租户，不给所有表加租户列（P087、P088）。
- **配额与计费**：模型调用在出站边界按租户原子预占，月配额超额即拒绝（P101）；存储、调用量分别计量。
- **噪声邻居**：按租户限流、按租户的任务并发上限，防止一个租户的批量入库拖垮所有人。
- **租户自助**：角色、成员、SSO 配置由租户管理员自己管；平台侧访问租户数据也要带显式租户条件并留审计，不能靠「超管」身份短路。

**关键取舍**：共享索引成本低但隔离弱，任何一条漏写租户过滤就是跨租户泄露；独立索引隔离强但索引数量爆炸。多数平台用混合模式。

**验收**：跨租户越权测试覆盖所有按 ID 寻址的入口。

### S32 设计一个代码库问答 / 研发知识助手

> 标签：系统设计、行业场景、切分 ｜ 难度：★★★ ｜ 关联：T034、T128、T160

**需求澄清**：仓库数量与语言、问题类型（「这个函数干什么」「在哪里实现了 X」「怎么改 Y」）、是否需要结合 Issue、文档、提交历史、代码能否出内网。

**方案**

1. **按语法结构切分**：用 AST 按函数、类、方法切分，保留签名、所属文件、导入与调用关系；不能按固定长度切，否则函数被截断。
2. **多种索引**：代码文本的 BM25（标识符精确匹配最重要）+ 代码嵌入模型的向量 + 符号索引（定义、引用关系）。
3. **标识符处理**：驼峰、下划线拆词，否则 `getUserById` 搜不到「user」。
4. **Agent 化**：复杂问题交给 Agent 用工具逐步探索：搜索符号 → 读文件 → 跳转定义 → 再检索，而不是一次检索回答。
5. **增量**：按提交增量更新，只重建变化的文件。

**关键取舍**：代码问答的上下文依赖很强，一次检索常常不够，Agent 多步检索更合适，但成本和延迟更高。

**风险**：代码与密钥泄露（扫描后再入库）；回答基于过时分支（绑定分支与提交）。

### S33 设计一个高时效的新闻 / 资讯问答系统

> 标签：系统设计、增量同步、行业场景 ｜ 难度：★★★ ｜ 关联：T023、T064、T091、T201

**需求澄清**：数据源与更新频率（分钟级还是小时级）、需要回答「最新」还是「历史」、时间范围表达、来源可信度差异。

**方案**

1. **实时入库管线**：流式接入，短文本直接切分嵌入，写入延迟控制在分钟级；向量库要确认写入后多久可见（刷新间隔）。
2. **时间是一等公民**：发布时间作为元数据；查询里的「最近」「上周」解析成时间过滤；排序中加入时间衰减。
3. **去重与聚合**：同一事件多家转载，按内容相似度聚类，避免结果全是同一件事。
4. **来源可信度**：权威来源加权，冲突时并列呈现来源。
5. **答案声明时间点**：回答注明「截至 xx 时间」。

**关键取舍**：实时性与索引成本冲突，热数据小索引高频刷新、冷数据大索引低频合并。

**风险**：假新闻与数据投毒，来源白名单与内容审核。

### S34 设计一个电商商品问答系统

> 标签：系统设计、行业场景、元数据 ｜ 难度：★★★ ｜ 关联：T090、T137、T113

**需求澄清**：商品量级、问题类型（参数对比、使用方法、售后政策）、价格库存是否实时、多语言。

**方案**

1. **结构化数据不走向量**：价格、库存、规格参数是结构化字段，实时查询业务接口或数据库，不放进知识库（会过期）。
2. **Self-Query**：从问题中抽取品牌、类目、价格区间等过滤条件，先过滤再检索。
3. **非结构化知识**：说明书、评价摘要、售后政策走 RAG。
4. **对比类问题**：检索多个商品的结构化参数后由模型组织表格，数值比较交给程序。
5. **合规**：价格、功效宣传有严格的合规要求，禁止模型编造。

**关键取舍**：「知识」与「数据」分开——会变的数据查实时系统，稳定的知识进知识库。

### S35 设计一个法律法规问答系统

> 标签：系统设计、行业场景、合规 ｜ 难度：★★★ ｜ 关联：T109、T111、T112

**需求澄清**：面向律师还是普通用户、法规范围与地域、是否包含判例、答错的代价。

**方案**

1. **按条款切分**：法规天然按编、章、节、条组织，按条切分并保留层级路径（「某法 第三章 第二十条」）。
2. **时效与版本**：法规有生效、修订、废止，版本与生效日期必须作为元数据，默认只检索现行有效条款，并能按时间点查询历史版本。
3. **精确引用**：答案必须引用到条款级别，给出原文，不允许意译替代原文。
4. **冲突处理**：上位法与下位法、新法与旧法冲突时，按法律适用规则说明，不由模型自行裁决。
5. **免责与边界**：面向公众时明确「不构成法律意见」，复杂个案引导咨询专业人士。

**关键取舍**：召回率比简洁更重要，漏掉一个适用条款可能导致结论错误。

### S36 设计一个医疗知识问答系统

> 标签：系统设计、行业场景、安全 ｜ 难度：★★★ ｜ 关联：T116、T180、T184

**需求澄清**：面向医生还是患者、知识来源（指南、说明书、文献）、是否涉及患者个人数据、监管要求。

**方案**

1. **知识源分级**：临床指南、药品说明书权威性最高，文献次之，网络内容不入库。
2. **严格的拒答与转诊**：诊断、用药剂量类问题面向患者时不直接给结论，给出就医建议；急症关键词触发紧急提示。
3. **术语归一**：疾病、药品的别名、商品名、缩写映射到标准术语。
4. **隐私**：患者数据脱敏，模型调用优先私有化部署。
5. **可追溯**：每个结论引用来源与版本，便于医学审核。

**关键取舍**：这是「宁可不答，不可错答」的场景，阈值和拒答策略偏保守。

**验收**：医学专家参与标注的评测集，重点看有害回答率而不只是准确率。

### S37 设计一个金融研报分析助手

> 标签：系统设计、行业场景、文档解析 ｜ 难度：★★★ ｜ 关联：T013、T016、T128

**需求澄清**：研报来源与数量、问题类型（观点汇总、数据提取、跨报告对比）、时效性、合规要求。

**方案**

1. **解析是难点**：研报大量表格、图表、页眉页脚；表格结构化提取，图表用视觉模型转写。
2. **元数据**：机构、分析师、发布日期、行业、公司代码，支持过滤与按时间排序。
3. **跨文档对比**：「各家机构对某公司的盈利预测」需要多文档检索后结构化汇总，适合 Agent 多步检索。
4. **数值准确**：数字直接从原文抽取并引用，不让模型改写数字。
5. **观点与事实分开**：标注哪些是机构观点、哪些是公开数据。

**关键取舍**：长文档 + 大量表格，切分策略要按章节，并为表格单独建索引。

**风险**：引用错数字造成投资误导，数值类答案必须可点击回到原文位置。

### S38 设计一个 IT 运维支持 Agent（知识库 + 工单 + 工具）

> 标签：系统设计、Agent、工具调用 ｜ 难度：★★★ ｜ 关联：T166、T171、T172、P059

**需求澄清**：处理哪些问题（密码重置、VPN、权限申请、故障排查）、能执行哪些操作、哪些操作需要审批。

**方案**

1. **知识库作为工具之一**：运维手册、历史工单解决方案进知识库，Agent 通过检索工具获取步骤。
2. **工具分级**：只读工具（查状态、查日志）自动执行；写操作（重启服务、改权限）需要人工确认；高危操作禁止。
3. **状态持久化**：长任务的每一步落库，可中断、可恢复、可审计，停止先落库再取消（参考项目的员工运行，P062、P065）。
4. **工单闭环**：解决后自动沉淀为知识，经人工审核后入库。
5. **权限**：Agent 以请求人身份调用工具，不能拿服务账号越权。

**关键取舍**：自动化程度与风险，先从只读诊断和知识问答做起，逐步开放写操作。

### S39 设计一个多模态产品手册问答系统

> 标签：系统设计、多模态、文档解析 ｜ 难度：★★★ ｜ 关联：R04、R28、T020、P042

**需求澄清**：手册形态（图文 PDF、扫描件、爆炸图、接线图）、用户是否会拍照提问、设备型号数量。

**方案**

1. **图文分别处理，加路不换路**：文字走常规链路；图片由视觉模型转写成文本代理进入主索引，同时产生多模态向量进入第三路（P042）。
2. **拍照提问**：用户上传图片，多模态开启时直接嵌入多模态空间检索，否则由视觉模型转写成文字拼进查询。
3. **型号过滤**：设备型号作为元数据，先按型号过滤再检索，避免不同型号的手册混淆。
4. **答案带图**：回答引用原图位置（页码、图号），让用户对照。

**关键取舍**：多模态嵌入擅长「看起来像」，精确的型号和参数仍依赖 OCR 与文本检索。

### S40 设计一个聊天记录 / 会议纪要知识化系统

> 标签：系统设计、数据接入、隐私 ｜ 难度：★★★ ｜ 关联：R05、T022、P018、P040

**需求澄清**：来源（IM 导出、会议转写）、格式、隐私要求、问题类型（「上次会议定了什么」「谁负责 X」）。

**方案**

1. **格式适配**：不同平台导出格式通过映射档案统一成「时间 + 发言人 + 内容」。
2. **按会话窗口聚合**：单条消息太短没有语义，按时间或条数聚成窗口，窗口之间适当重叠保证上下文连续；重叠带来的重复在检索时合并（P040）。
3. **脱敏**：手机号、邮箱、身份证等默认脱敏后再入库。
4. **元数据**：会话、发言人、时间进入元数据，支持「某人在某时间段说了什么」这类过滤。
5. **摘要层**：为每次会议生成摘要与待办，作为另一层索引。

**关键取舍**：窗口越大上下文越完整，但检索精度下降；重叠提高召回，但产生重复。

**风险**：隐私与授权，聊天内容的可见范围要继承原始会话的参与者范围。

### S41 设计一个个人助理的长期记忆系统

> 标签：系统设计、记忆、Agent ｜ 难度：★★★ ｜ 关联：R44、T156、T157、P056、P058

**需求澄清**：记什么（偏好、事实、事件）、记多久、用户能否查看和删除、多设备与多 Agent 共享。

**方案**

1. **记忆分类**：用户画像（结构化属性，幂等更新）、事实片段（可检索）、事件（带时间）。
2. **写入**：从对话中按规则抽取，而不是全量保存；更新时限定在最近若干条候选内，防止模型乱改（P056）。
3. **检索与注入**：按当前问题语义检索相关记忆，注入时标注来源与时间，数量有上限。
4. **遗忘**：过期规则、低价值记忆衰减、用户主动删除。
5. **隔离**：按用户隔离，Agent 只能访问授权的记忆库（P057）。

**关键取舍**：记忆与知识库不同——记忆是「关于这个用户」的，会被更新和遗忘；知识库是「关于世界或企业」的，有版本和审核（P058）。

**风险**：记错、记串、记住了不该记的敏感信息。

### S42 设计一个企业统一搜索（跨多个系统、带权限）

> 标签：系统设计、权限、数据接入 ｜ 难度：★★★ ｜ 关联：T026、T178、P140

**需求澄清**：接入哪些系统（Wiki、网盘、邮件、工单、代码）、各系统的权限模型、实时性要求。

**方案**

1. **连接器框架**：每个系统一个连接器，统一「列举、取内容、取权限、增量标识」接口（参考项目的 `ExternalConnector`，P140）。
2. **权限同步是核心**：每篇文档带上源系统的访问控制列表（用户、组），检索时按当前用户的身份和组过滤；权限变更要增量同步，撤权时效是关键指标。
3. **身份映射**：各系统的账号统一映射到企业身份（SSO 与目录组）。
4. **结果融合**：不同系统的分数不可比，用 RRF 或按来源分组展示。
5. **早期绑定 vs 晚期绑定**：索引时写入 ACL（快，但撤权有延迟）或查询时回源系统校验（准，但慢），通常两者结合：索引过滤 + 结果回源校验。

**关键取舍**：权限准确性与性能的平衡；宁可漏显示，也不能多显示。

### S43 设计一个 RAG 评测平台

> 标签：系统设计、评测、发布门禁 ｜ 难度：★★★ ｜ 关联：T142、T148、T149、P076、P080

**需求澄清**：评测对象（检索、答案、Agent 轨迹）、评测集规模、多少团队使用、是否要接发布流程。

**方案**

1. **评测集管理**：用例带问题、标准答案、证据（锚定原文片段而不是 chunk ID，换切分策略后仍可用）、期望拒答；版本化、可复核（P072、P081）。
2. **执行**：复用生产的检索与生成链路，配置矩阵并行对比；提交前预估调用次数与费用（P080）。
3. **指标**：检索（Recall@K、MRR、NDCG）、答案（正确性、忠实性、完整性、引用正确性与完整性），带置信区间。
4. **可复现**：冻结评测集修订号、用例输入、语料指纹、配置快照（P078、P085）。
5. **门禁**：同语料双跑、容差判定、证据不足时 LOG_ONLY 需要人工放行（P076）。
6. **闭环**：线上 BAD 反馈与零命中转为用例，人工补证据后回归（P079）。

**关键取舍**：LLM-as-Judge 便宜但有噪声。项目的做法是检索门禁默认生效；答案门禁要应用显式开启（`answer_gate`），Judge 失败保留空值、不折算 0 分，只在双方 Judge 都成功的用例交集上比较，答案分容差 0.2（P075、P076）。先把答案评测当报告积累一致性证据，再决定是否让它拦截发布。

## 六、综合与行为题

### S44 从零推动一个企业知识库项目落地，你会怎么做？

> 标签：综合、运营闭环、评测 ｜ 难度：★★ ｜ 关联：T005、T142、S29

**回答思路**：先定义「好」，再做系统。

1. **选场景**：找一个高频、答案在文档里、答错代价可控的场景（如内部 IT 与制度问答），不要一开始就做「全公司万能助手」。
2. **定指标**：和业务方一起建 50–100 条真实问题的评测集，约定上线标准（如 Top-5 命中率、答案正确率、拒答率）。
3. **梳理数据**：数据归属、权限、更新责任人；脏数据比算法更影响效果。
4. **最小可用系统**：混合检索 + 重排 + 引用，先跑通评测。
5. **小范围上线**：灰度给一个部门，收集反馈与零命中问题。
6. **运营机制**：谁补内容、谁审核、多久回归一次。

**要强调的认知**：知识库项目成败一半在内容运营，技术只是一半。

### S45 业务方只说「效果不好」，没有具体 case，你怎么办？

> 标签：综合、评测、排障 ｜ 难度：★★ ｜ 关联：T153、S01、S13

1. **把感受变成样本**：请业务方给 20 个他们认为答得不好的问题，或者从日志里抽样最近的问答让他们标注好坏。
2. **归因分类**：逐条判断是检索问题、生成问题、内容缺失、还是期望不合理（问题超出知识库范围）。
3. **量化**：按类别统计占比，找出最大的一类先解决。
4. **建立基线**：把这批问题固化成评测集，之后每次改动都能说清楚「好了多少」。
5. **对齐预期**：有些问题本来就不该由知识库回答（实时数据、个人数据），要说清边界。

**易错点**：没有样本就开始调参，改完也说不清是否变好。

### S46 预算有限，你先做哪三件事提升 RAG 效果？

> 标签：综合、成本、检索 ｜ 难度：★★ ｜ 关联：T012、T079、T098

在没有数据证明之前，性价比通常最高的三件事：

1. **建评测集**：没有评测集，所有优化都无法证明。50–100 条真实问题就能开始。
2. **混合检索 + 重排**：BM25 补向量的精确匹配短板，重排把真正相关的内容提到前面；这两项的提升通常比换大模型明显，成本也低。
3. **治理数据**：去掉重复、过期、低质量文档，修正解析错误的关键文档。「垃圾进，垃圾出」在 RAG 里特别明显。

之后再按评测结果决定：是否需要改写、父子分片、微调嵌入模型、换更强的生成模型。

**易错点**：一上来就换最贵的模型或做复杂的 Agentic RAG。

### S47 怎么向非技术的管理者解释 RAG 系统的能力边界和风险？

> 标签：综合、合规、幻觉 ｜ 难度：★★ ｜ 关联：T009、T110、T180

用管理者关心的三件事说：

1. **它能做什么**：在「已经写下来的知识」里快速找到答案，并告诉你出处；它回答的质量取决于资料的质量和完整度。
2. **它不能做什么**：资料里没有的，它不知道；资料过时，它的答案也过时；它不能替代专业判断（法律、医疗、财务结论）。
3. **风险与控制**：可能答错（用引用和评测控制）、可能泄露不该看的内容（用权限控制）、成本随使用量增长（用配额控制）。

最后给一个可量化的承诺，例如「在这 100 个典型问题上，正确率 90%，其余会明确说不知道」，而不是「AI 什么都能答」。

### S48 知识库团队里，数据、算法、工程、运营怎么分工协作？

> 标签：综合、运营闭环、工程化 ｜ 难度：★★ ｜ 关联：T154、P079

| 角色 | 职责 | 交付物 |
| --- | --- | --- |
| 内容运营 | 内容质量、更新、审核、处理 badcase | 知识库内容、FAQ、纠正用例 |
| 算法 | 检索与生成效果，评测方法 | 评测集、策略配置、效果报告 |
| 工程 | 管线、性能、稳定性、权限与安全 | 平台能力、监控告警 |
| 业务方 | 定义「好」，提供真实问题与验收 | 评测集的业务标注、上线标准 |

**协作机制**：以评测集为共同语言——运营补的内容、算法调的参数、工程改的链路，都用同一套评测集证明效果；线上反馈进入质量问题流程，有明确的领取人和关闭标准（P079）。

**易错点**：把知识库当成一次性交付的技术项目，没有运营角色，三个月后内容过期，效果自然下降。

## 七、补充排障题

### S49 知识库内容越加越多，效果反而下降，为什么？

> 标签：排障、检索、治理 ｜ 难度：★★★ ｜ 关联：T233、R23、P040、P022、T059

**先判断**：「加内容变差」几乎都是干扰项变多了，不是模型变笨了。先用评测集按「老问题」和「新内容相关问题」分开看：老问题的召回下降，说明新内容在抢位置。

**排查步骤**

1. **近似重复**：新导入的内容是否和已有内容高度重复（多个版本、转载、同一文档的多种格式）？Top-K 被同一内容的多份拷贝占满，其他证据被挤出去。
2. **版本冲突**：旧版本没下线，新旧制度同时被召回，模型混用（S03、S17）。
3. **泛化内容**：新增了大量目录、模板、概述类片段，成为「什么都能搜到」的 hub（T233）。
4. **跨库干扰**：所有内容放在一个库里，不同业务的相似术语互相干扰（如两个产品线都有「退款流程」）。
5. **统计量漂移**：BM25 的 IDF 随语料变化，某些词的权重变了。
6. **ANN 召回**：数据量上了一个量级，而 `ef` / `num_candidates` 没调，ANN 自身的召回率下降（T059）。

**修法**：入库去重和版本治理；按业务拆库并做路由，而不是一个大库；清理模板化内容；按规模重新调 ANN 参数；用元数据过滤缩小范围；每次大批量导入前后跑同一套评测集。

**本项目落点**：多库路由与白名单（R23）；聊天记录重叠窗口去重在融合之后、重排之前（P040）；有效期和回收站让过期内容退出检索（P022）。

**易错点**：用「换更大的模型」解决干扰问题——干扰项进了上下文，模型越大越会「认真地」使用它们。

### S50 资料里明明有正确答案，模型却按自己的知识回答，怎么排查？

> 标签：排障、生成、幻觉 ｜ 难度：★★★ ｜ 关联：T217、T105、P043、P075

**先判断**：这是生成问题，不是检索问题——确认正确资料确实在本次上下文里，而且排在模型能看到的位置。

**排查步骤**

1. **资料位置**：正确片段是否在上下文中间、被大量无关资料包围（Lost in the Middle，T105）？
2. **资料表述**：资料的说法是否反常识（如内部规定与通用做法相反）？模型对自己的「常识」越确信，越容易忽略资料（T217）。
3. **Prompt 优先级**：系统提示里是否明确「以资料为准」；应用自定义指令里有没有「可以适当发挥」这类冲掉规则的话。
4. **资料冲突**：是否同时召回了新旧两个版本，模型选了与自己知识一致的那个。
5. **模型差异**：换模型或供应商升级后才出现，说明是模型的上下文遵循能力变化（S54）。

**修法**：精简上下文、把最相关资料放在开头或靠近问题的位置；资料带生效日期和来源；要求每个结论带引用；在评测集中加入反事实用例（把资料里的数字改掉，看模型是否跟着资料走）。

**本项目落点**：Prompt 的固定顺序里，拒答与引用规则放在应用自定义指令之后，运营指令冲不掉（P043）；Judge 的忠实度维度能把这类问题量化出来（P075）。

**易错点**：只看答案正确率——模型凭记忆答对时评测是绿的，等记忆和最新规定不一致时才暴露。

### S51 上游模型大面积 429 限流，怎么应急和根治？

> 标签：排障、成本、可靠性、降级 ｜ 难度：★★ ｜ 关联：T194、P143、P101、P036、P102

**先判断**：分清是谁的限流——供应商账号的 QPS / TPM 上限、供应商整体过载，还是自己系统的租户配额（后者错误码不同，P101）。再看是哪类调用：在线问答、批量入库、图谱抽取、评测，它们共享同一个账号额度。

**应急**

1. **保在线**：暂停或降速批量任务（入库嵌入、图谱抽取、评测跑批），把额度让给在线问答。
2. **降级**：改写、重排等可选阶段失败时退回基础链路，不让整个请求失败（P036）。
3. **备用模型**：有多供应商或多模型配置时切换。

**根治**

1. **额度隔离**：在线与离线用不同账号或不同额度池，离线任务永远不能挤占在线。
2. **并发闸门**：每类调用有明确的并发上限，并发数乘以任务数不超过额度（P102）。
3. **退避重试**：只对 429 做指数退避 + 抖动，等待时占住并发槽位，让系统自动降速到额度能承受的水平。
4. **可观测**：限流重试次数单独计量，它是「该不该降并发」的依据。

**本项目落点**：图谱抽取对 `QUOTA_EXCEEDED` 做带抖动的指数退避，重试次数单独打日志，抽取并发与任务并发相乘才是模型看到的峰值（P143）。

**易错点**：429 时立即、同步地重试——所有线程一起回来，复现触发限流的突发，越重试越限流。

### S52 请求报「上下文超长」，怎么处理？

> 标签：排障、上下文构建、生成 ｜ 难度：★★ ｜ 关联：T221、T214、T122

**先判断**：看是哪一部分撑爆的：检索资料、对话历史、工具定义与工具结果，还是输出预算设得过大（输入 + 最大输出超过窗口，有的供应商也会拒绝）。

**排查步骤**

1. **按部分统计 token**：系统提示、工具定义、历史、资料、问题、输出预留各多少。
2. **计数口径**：预算是按字符算的还是按生成模型的分词器算的？中英混排、代码和表格的误差最大（T214）。
3. **异常输入**：是否有超长单条资料（父片过大、表格整表入片）或超长的用户粘贴内容。
4. **Agent 场景**：工具结果是否原样累积在上下文里，每一轮都更长。

**修法**：按「输出 → 固定部分 → 资料 → 历史」的顺序分配预算（T221）；以完整 chunk 为单位丢弃排名最低的资料；历史做摘要；工具结果清理或摘要化；单条资料设长度上限；用户输入在入口处做长度校验并给出明确提示。

**易错点**：捕获异常后简单地把字符串从中间截断——截掉的可能正是答案所在的资料，或者把 JSON 结构截坏。

### S53 Agent 反复调用同一个检索工具、陷入循环，怎么排查？

> 标签：排障、Agent、工具调用 ｜ 难度：★★ ｜ 关联：T165、T173、P054、P053

**先判断**：看轨迹——每次调用的参数是否相同？返回是否相同？模型在调用之间的思考是否在重复同一个判断？

**常见根因**

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 参数完全相同、反复调用 | 工具返回里没有模型能理解的「没找到」信号，或错误被包装成空结果 | 空结果明确说明「未找到相关内容」并给出建议（换关键词、放宽过滤） |
| 参数微调、结果都不满意 | 知识库里确实没有答案，模型不知道何时放弃 | 在系统提示里给出停止条件；工具返回检索质量信号 |
| 调用报错后反复重试 | 错误信息面向人类、模型无法据此修正参数 | 返回结构化错误：哪个参数错、合法取值是什么（P053） |
| 返回内容太长被截断 | 模型没看到关键内容，以为没搜到 | 控制返回条数与长度，提供按 ID 读全文的工具 |

**兜底**：最大步数、最大 token、同参数重复调用检测，触达后要求模型基于已有信息作答或明确说明无法回答（T173）。

**本项目落点**：工具参数和返回的设计原则（P054）；MCP 调用失败时，参数错误作为工具结果返回给模型让它自我修正，协议错误才返回给客户端（P053）。

**易错点**：只加最大步数限制，不修工具返回——循环被截断了，但每次都是在浪费掉最大步数之后才停。

### S54 模型供应商静默升级后，效果变了，怎么发现和应对？

> 标签：排障、评测、版本管理 ｜ 难度：★★★ ｜ 关联：P078、P076、P017、T054

**先判断**：同名模型（尤其是不带日期的别名）背后的版本可能被供应商更换。症状是：没有发布、没有改配置，指标却在某天发生阶跃变化。

**发现**

1. **固定版本**：生产配置使用带日期或版本号的模型标识，不用「最新」别名。
2. **定期回归**：每天用固定评测集跑一次基线，指标出现阶跃就告警。
3. **输出指纹**：记录供应商返回的模型版本或系统指纹字段（如果有），变化即告警。
4. **嵌入模型更危险**：嵌入模型一旦变化，新写入的向量和存量向量不在同一空间，检索会悄悄变差——定期用固定文本计算嵌入，比对与基准向量的相似度。

**应对**

- 生成模型变化：跑完整评测集，对比回答质量和拒答率；必要时回退到固定版本，或调整 Prompt 后重新过门禁。
- 嵌入模型变化：必须全量重建索引（新旧向量不能混用），走不停机迁移流程（P017）。

**本项目落点**：生成模型属于应用版本快照，评测运行固化嵌入版本与语料指纹（P078），模型变化可以被定位到具体版本；发布门禁拦截退化（P076）；嵌入指纹变化会触发文档的 minor 版本和重建（R15）。

**易错点**：把阶跃变化当成用户问题分布的自然波动，错过最佳回退时机。

### S55 同一个意思换个问法，召回结果差异很大，怎么办？

> 标签：排障、检索、查询改写 ｜ 难度：★★ ｜ 关联：T084、T077、P035、P027

**先判断**：用评测集的「同义问法组」量化：同一意图的多个问法，Recall@K 的方差有多大、差在哪一路（BM25 还是向量）。

**常见原因与修法**

| 原因 | 修法 |
| --- | --- |
| 口语化问法与书面文档用词差异大 | 查询改写成规范表述；文档侧补充常见问法（FAQ、doc2query） |
| 缩写、俗称、错别字 | 同义词词典、术语归一化、拼写纠错（T077、T096） |
| 短查询信息不足 | 多轮时补全上下文；必要时反问澄清（T093） |
| 只有一路检索 | 混合检索，两路互补 |
| 向量模型对问法敏感 | 评测不同嵌入模型在同义组上的稳定性；带查询指令前缀的模型要正确加前缀（T046） |

**评测方法**：评测集里每个意图至少准备 3–5 种问法（正式、口语、缩写、带错别字），把「问法稳定性」作为独立指标跟踪。

**本项目落点**：查询改写的结果只作检索词、有硬超时兜底（P035）；IK 分词词典热更新可以快速补充术语和同义词（P027）。

**易错点**：评测集里每个问题只有一种标准问法，线上真实问法一变就崩，但评测报告永远是绿的。

### S56 发现有人在文档里植入了 Prompt 注入指令，怎么应急？

> 标签：排障、安全、Prompt注入 ｜ 难度：★★★ ｜ 关联：T176、P043、P028、P099

**先止血**

1. **定位并下线**：搜索全库中同类特征的内容（隐藏文字、「忽略之前的指令」一类话术、异常链接），把受影响的分片禁用或文档下线。
2. **评估影响**：从审计和检索日志里找出哪些请求召回过这些分片、生成了什么回答，是否有数据被引导外发（如回答里出现可疑链接）。
3. **切断输出通道**：如果注入试图诱导输出外链或图片，临时收紧答案中的链接和 Markdown 图片渲染。

**再根治**

1. **入口**：上传与同步时扫描可疑模式和隐藏文本（白色字、零宽字符、极小字号）；外部来源内容默认进入审核。
2. **组装层**：资料统一包裹为数据，系统指令声明资料中的指令一律无效（P043）。
3. **输出层**：答案里的链接只允许来自资料原文或白名单域名；前端安全渲染。
4. **权限**：Agent 拿到检索结果后能执行的动作越多，注入的破坏越大——高风险动作必须人工确认。
5. **追溯**：确认内容的上传人和来源，处理账号。

**本项目落点**：分片标注支持禁用，并在事务提交后删除引擎中的旧文档（P028）；操作审计记录谁上传、谁修改（P099）；注入防线见 P043、R31。

**易错点**：只删除被发现的那一份文档，没有搜索同类内容，也没有回查已经产生的回答。

### S57 长文档后半部分的内容总是答不出来，怎么排查？

> 标签：排障、文档解析、切分 ｜ 难度：★★ ｜ 关联：T037、T050、S02、P041

**先判断**：先确认后半部分的内容有没有进入分片——在分片列表或检索调试页里搜索后半部分的一句原文。

**按链路排查**

1. **解析截断**：解析服务是否有页数、字符数或超时上限，超长文档只解析了前 N 页？PDF 后半部分是否是扫描页，没有走 OCR？
2. **切分**：是否有「单文档最多 N 个分片」的上限？父子分片下子片是否齐全？
3. **嵌入截断**：分片是否超过嵌入模型的最大输入长度，尾部被静默截断（T037）？整篇文档一次嵌入的方案，后半部分的信息在向量里天然被稀释（T050）。
4. **检索排序**：后半部分的片段缺少标题上下文（如「如上所述」「本章」），单独看语义不完整，排不上来——需要给分片补充章节标题路径。
5. **生成截断**：检索到了，但上下文预算不够，被排在后面的片段丢掉了（T221）。

**修法**：解析和切分的上限要显式记录并告警，而不是静默丢弃；分片携带文档标题和章节路径；超长文档按章节拆分入库。

**本项目落点**：检索调试页可以看到每条结果在各路召回中的排名和被过滤的原因（P041）。

**易错点**：只在文档开头部分抽样验证解析质量，后半部分的问题要到用户提问时才暴露。

## 八、补充设计与综合题

### S58 设计一个 Deep Research（深度研究）Agent

> 标签：系统设计、深度研究、Agent ｜ 难度：★★★ ｜ 关联：T222、T225、T155、T173

**需求澄清**：数据源（公网、内部知识库还是两者）、报告类型（行业调研、竞品分析、技术选型）、时效要求（分钟级还是小时级）、成本上限、是否需要人工在中途确认大纲。

**方案**

1. **澄清与简报**：先与用户确认范围、时间窗口、深度和输出结构，生成研究简报；大纲可让用户确认后再执行。
2. **编排者—工作者**：编排者把简报分解成子问题，并行派发给子 Agent；每个子 Agent 在独立上下文中循环检索、阅读、判断，返回压缩后的发现和来源列表。
3. **检索工具组**：网页搜索、网页读取、内部知识库检索（按用户权限裁剪）、按 ID 读全文；工具返回统一带来源 ID。
4. **反思补漏**：编排者检查覆盖度和矛盾点，追加子任务。
5. **写作与引用校验**：按大纲写报告，逐条核对引用是否支持论断，无法支持的论断删除或标注。
6. **长任务运行时**：任务可能运行几十分钟，要持久化状态、支持断线重连、进度推送和中途取消（参考 P062 的持久运行模式）。

**关键取舍**

- 并行度与成本：子 Agent 越多覆盖越全，token 成倍增长；按任务价值设预算上限。
- 深度与时延：设最大轮数和边际收益停止条件。
- 来源质量：优先一手资料，对内容农场和重复转载降权。

**风险与验收**：事实错误和编造引用是最大风险。验收看事实准确率、引用正确率、覆盖度（对照专家大纲）和单任务成本；用固定研究题集做回归。

### S59 设计一个企业数据问答助手（Text-to-SQL + 文档 RAG）

> 标签：系统设计、Text2SQL、权限 ｜ 难度：★★★ ｜ 关联：T228、T137、T088

**需求澄清**：数据源（数仓、业务库）、用户群体（管理层、业务分析、一线）、问题类型（查数、趋势、归因）、权限要求（行级、列级）、准确率要求。

**方案**

1. **路由**：区分「查数」（走 SQL）、「问规则与原因」（走文档 RAG）和「混合」（先取数再检索解释材料）。
2. **语义层先行**：核心指标（营收、毛利、活跃用户）在指标平台里定义口径，模型优先选择指标 + 维度 + 过滤条件，而不是自由写 SQL。
3. **Schema 检索**：没有覆盖到指标层的长尾问题，检索相关表和字段说明、样例值、历史示例 SQL，再生成 SQL。
4. **执行安全**：只读账号、只读副本、表白名单、强制 LIMIT、`EXPLAIN` 代价上限、超时；行级和列级权限按提问人身份在执行层施加。
5. **结果呈现**：返回结果表 + 图表 + 口径说明 + 可展开的 SQL；数值直接来自结果集。
6. **反馈闭环**：用户确认正确的问答对进入示例库；错误的进入评测集。

**关键取舍**：指标层覆盖越多越准，但建设成本高——先覆盖最高频的 20% 指标，长尾走 Schema 检索并明确提示「此结果为自动生成的查询，请核对口径」。

**风险与验收**：口径不一致和越权查询是最大风险。验收用「问题 → 标准结果」集计算执行准确率，另测越权用例全部被拒。

### S60 设计一个合同审核 / 文档比对助手

> 标签：系统设计、行业场景、文档解析 ｜ 难度：★★★ ｜ 关联：T013、T016、T108、S35

**需求澄清**：合同类型、审核依据（公司标准条款、法规、历史合同）、输出形式（风险清单、修改建议、批注版文档）、谁来做最终判断。

**方案**

1. **结构化解析**：合同按条款层级解析（章、条、款），保留编号和页码；表格（价格、付款节点）结构化提取。
2. **条款对齐**：把待审合同的每个条款与标准模板中的对应条款对齐（先按标题和语义检索候选，再由模型确认对应关系）。
3. **逐条审核**：对每个对齐的条款，检索审核规则库（如「违约金上限」「管辖法院」）和相关法规，模型输出：是否偏离、风险等级、依据、修改建议。
4. **缺失检测**：标准模板里有、待审合同里没有的条款单独列出。
5. **版本比对**：两个版本的合同做结构化差异（按条款对齐后比对），而不是纯文本 diff。
6. **呈现**：在原文位置批注，每条意见附依据和原文定位；人工逐条采纳或驳回。

**关键取舍**：逐条审核准确但调用多、成本高；可以先用规则和轻量模型筛出高风险条款，再用强模型精审。

**风险与验收**：漏报比误报危险；验收看高风险条款的召回率，以及律师对建议的采纳率。结论必须由人工签署，系统只做辅助。

### S61 设计一个企业级 MCP 网关 / 工具平台

> 标签：系统设计、MCP、安全 ｜ 难度：★★★ ｜ 关联：T164、T227、T161、P142

**需求澄清**：有多少内部系统要暴露为工具、调用方有哪些（内部 Agent、员工桌面客户端、第三方）、身份体系、审计与合规要求。

**方案**

1. **统一入口**：网关对外是一个（或按域分组的少数几个）MCP 服务器，对内代理到各业务系统的工具实现；工具注册时声明名称、描述、参数 Schema、风险等级、负责人。
2. **身份与授权**：对外按 OAuth 资源服务器校验令牌（受众必须是网关）；对内用网关自己的凭据或令牌交换访问下游，禁止令牌透传（T227）。工具级授权：用户角色 × 工具 × 数据范围。
3. **工具治理**：工具上线评审（描述质量、参数校验、返回长度）、版本管理、下线通知；工具描述变更要审计，防止「工具描述投毒」。
4. **工具发现**：工具很多时提供按任务检索工具的能力，或按角色和场景分组下发，避免一次暴露上百个工具（T161）。
5. **风险分级**：只读工具直接调用；写操作和高风险工具要求人工确认或二次授权。
6. **可观测与限流**：按调用方、用户、工具做限流和配额；全量审计（谁、代表谁、调用了什么、参数摘要、结果状态）。

**关键取舍**：集中网关便于治理，但会成为单点和瓶颈——网关只做鉴权、路由、审计，不承载业务逻辑，按无状态方式水平扩展。

**风险与验收**：越权调用和提示注入驱动的危险操作是最大风险。验收：越权用例全部拒绝、高风险工具必经确认、每次调用可追溯到具体用户。

### S62 设计一个多语言、多地区的全球化知识库

> 标签：系统设计、合规、嵌入 ｜ 难度：★★★ ｜ 关联：T051、T118、T025、T183

**需求澄清**：涉及哪些语言、内容是否有多语言版本（还是只有一种源语言）、用户用什么语言提问、各地区的数据驻留和合规要求。

**方案**

1. **数据驻留**：按地区部署数据面（存储、索引、模型调用），受监管数据不出境；控制面可以集中。
2. **检索**：多语言嵌入模型支持跨语言检索；BM25 按语言使用对应分析器（中文分词、日文、德语复合词等）；查询语言检测后，必要时把查询翻译成内容的主要语言再做一路检索。
3. **内容版本**：同一文档的多语言版本建立关联，优先返回用户语言的版本；只有源语言时，检索源语言内容、用用户语言作答并标注「译自原文」。
4. **生成**：答案语言跟随用户；引用指向原文，术语使用各语言的术语表统一译法。
5. **评测**：每种主要语言单独的评测集和指标，不能用英文结果代表所有语言。

**关键取舍**：「先翻译再检索」简单但丢失细节、增加延迟；多语言嵌入更直接但在小语种上质量参差——按语言分别评测后决定。

**风险与验收**：小语种效果差、数据跨境违规。验收按语言看检索与答案指标，并通过合规审查。

### S63 怎么衡量并向业务证明知识库项目的价值（ROI）？

> 标签：综合、运营闭环、评测 ｜ 难度：★★ ｜ 关联：T150、S44、S47

**先明确**：技术指标（Recall、忠实度）是过程指标，业务方要的是结果指标。立项时就要和业务方约定用哪个结果指标衡量，并先测出基线。

**按场景选结果指标**

| 场景 | 结果指标 |
| --- | --- |
| 客服 | 自助解决率、转人工率、平均处理时长、满意度 |
| 内部问答 | 同类问题在群里和工单里的数量、找到答案所需时间 |
| 研发 / 运维助手 | 故障定位时长、重复问题的比例 |
| 销售 / 售前 | 方案准备时长、响应客户问题的时效 |

**方法**

1. **基线**：上线前测一段时间的现状数据。
2. **对照**：能做 A/B 就做（T210）；不能做就用分批上线的团队做对照，避免把季节性波动算作收益。
3. **成本侧**：模型费用、基础设施、内容运营人力，一起算。
4. **质量侧**：答错的代价要计入（如错误答复导致的客诉），不能只算节省的时间。
5. **定期报告**：月度报告包含结果指标、使用量、质量指标、成本和改进计划。

**易错点**：用「调用次数」「活跃用户数」证明价值——使用多不代表有效；也不要只报节省的时间而不报答错的代价。
