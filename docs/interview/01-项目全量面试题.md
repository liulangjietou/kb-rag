## 答题口径

高级岗的评分点不是「做了什么功能」，而是四件事，每道题都往这四个方向答：

1. **取舍**：每个设计都要能回答「为什么不是另一种」，以及它的代价。
2. **闭环**：改动怎么证明是正向的——评测、门禁、指标。
3. **边界**：方案在什么情况下失效，已知缺口是什么。主动说，比被问出来强。
4. **演进**：复杂度是被真实问题逼出来的，不是预判出来的。没有 MQ、没有调度平台，都要能讲清楚「为什么现在不需要、什么信号出现才需要」。

## 一、项目综述与架构

### P001 用一分钟介绍这个项目

> 标签：项目综述、架构 ｜ 难度：★ ｜ 关联：P002

**考察点**：能不能一句话讲清定位，能不能讲出和 Demo 的差别。

**参考回答（30 秒版）**

kb-rag 是一个可自托管的企业知识库与 RAG 系统：运营在管理台维护知识和应用，员工使用已授权的正式应用问答，外部 Agent 通过 REST 或 MCP 接入检索、问答和长期记忆。它和一般 RAG Demo 的差别在三个闭环：

1. **质量闭环**：span 锚定的评测集、检索与最终答案两层指标、发布门禁同语料双跑、快照冻结与秒级回滚。
2. **一致性闭环**：MySQL 是唯一事实源，ES / Qdrant / Neo4j 都是可重建的派生索引，双写靠状态表加补偿扫描。
3. **治理闭环**：多租户、RBAC、文档级 ACL、内容审核与有效期、操作审计、Token 配额。

技术上是 Java 17 / Spring Boot 主服务 + 两套可互换的解析服务（Python / Java）+ React 管理台；不配任何模型 Key 也能跑通「上传 → 检索」。

**3 分钟版提纲**：背景与对标（百炼知识库的产品形态，开源）→ 架构（五模块六边形 + 解析微服务 + 存储分工）→ 三条主链路（入库、检索、发布）→ Agent 接入（REST / MCP / 记忆库 / 持久运行）→ 你做的最难的三件事（P002）→ 结果数据。

**坑**：高级岗的项目介绍必须带数字。准备好你自己的评测结果（Recall@5、Hit Rate、答案五维分）和性能数据；仓库里的压测脚本 `kb-rag-deploy/scripts/benchmark.sh` 的验收口径是基础链路 P95 < 2s。没有数字的介绍，面试官只能按「做过功能」给分。

### P003 为什么自研，而不是直接用 Dify / RAGFlow 这类平台？

> 标签：选型、架构 ｜ 难度：★★ ｜ 关联：P004

**考察点**：选型判据，以及是否清楚自研的代价。

**参考回答**

判据不是「功能多少」，而是三个硬约束：

1. **权限必须是检索谓词级**：租户、文档 ACL、版本可见集都要在召回时生效，并且可审计。
2. **质量必须能被证明**：改了参数要有同语料双跑的门禁，发布物要冻结它被测过的语料。
3. **与企业既有体系集成**：Java 技术栈、LDAP / OIDC / SAML / CAS 单点登录、既有运维体系。

需求文档把 RAGFlow / QAnything 等开源产品列为参照系，差异化定在「标注 → 评测 → 发布」质量闭环、双引擎混合检索、嵌入模型版本化和界面全配置化。当这三条约束成为硬约束时，基于通用平台二开改的是它的核心链路，长期维护成本高于自研。

代价要主动说：模型适配、解析器、前端都得自己维护；生态插件要自己接；团队要有能力守住这套工程纪律。

**追问**：「那为什么不用 LangChain4j 或 Spring AI？」见 P004 追问。

### P004 讲一下整体架构

> 标签：架构、选型 ｜ 难度：★★ ｜ 关联：P101、P045、P047

**考察点**：分层与依赖方向、存储分工、为什么这样拆。

**参考回答**

```
kb-rag-web（React 18 + AntD 5）──┐
智能体 / MCP 客户端 ──REST/MCP──┤
                                ▼
kb-rag-server（Java 17 / Spring Boot 3.3）
  kb-api ─► kb-app ─► kb-domain ─► kb-common
     └────► kb-infrastructure ─► kb-domain
        │HTTP
        ▼
kb-rag-parser（Python）或 kb-rag-parse-java（二选一，同一契约）

存储：MySQL（唯一事实源）· MinIO（原件与解析产物）· ES（BM25，lite 模式兼向量）
      · Qdrant（full 模式向量）· Neo4j（可选图）· Redis（可选：会话与权限缓存）
```

三条要点：

1. **六边形依赖**：`kb-domain` 定义二十多个出站端口（`EmbeddingProvider`、`VectorStore`、`ChatProvider`、`ObjectStorage`……），`kb-app` 只依赖端口、从不依赖 `kb-infrastructure` 的具体类，`kb-api` 是唯一装配点。换引擎、零 Key、可选组件因此都是**装配问题**而不是业务代码里的 if-else。
2. **领域算法是纯函数**：切分、融合、评测指标、门禁裁决、标注迁移相似度都没有 IO，可以用手挑的数字把每个分支钉死在单测里。
3. **零 Key 统一装置**：`ModelProviderConfig` 是唯一读模型凭据的地方，凭据为空就注入 `Unconfigured*` 实现；`GraphStoreConfig`（`NEO4J_URI` 空 → `DisabledGraphStore`）、Qdrant 同理。上游只写 `isConfigured()` 一个分支，全链路没有散落的 null 判断。

**追问：为什么不用 LangChain4j / Spring AI？**

需求决策 D1 写过 LangChain4j，但实现里没有引入（这是一处文档偏差）。模型适配器直接写在 JDK HttpClient 之上，原因是三件框架会挡住的事：

1. **计量必须在 HTTP 出站边界**：请求发出前原子预占配额，响应后按供应商 usage 结算（P101）。框架把这个边界藏起来了。
2. **流式的终态语义要自己掌握**：`finish_reason=length` 判截断失败、缺 `[DONE]` 判不完整、断连要能取消上游请求（P045、P047）。
3. **能力面很小**：对话、嵌入、重排、视觉、多模态嵌入五类，走 OpenAI 兼容协议，适配成本可控。

代价是新供应商要自己写适配器。

**追问：实体和 Mapper 放在 domain 层，不怕领域层被持久化框架污染吗？**

这是务实取舍：少一层实体转换，代价是领域层带 MyBatis-Plus 注解；真正要保持纯净的是算法类，它们没有 IO。存量是贫血模型，新逻辑按「实体自身状态放实体、跨聚合编排放 Service」归位，不为了纯粹而整体重构。

**代码锚点**：`kb-rag-deploy/docs/ARCHITECTURE.md` §3.1–3.2；`ModelProviderConfig`。

### P005 系统有哪几类调用方？鉴权怎么分？

> 标签：架构、权限、认证 ｜ 难度：★★

**考察点**：多身份面的隔离设计。

**参考回答**

三条完全独立的鉴权链：

| 调用方 | 入口 | 凭据 | 授权 |
| --- | --- | --- | --- |
| 管理台 / 员工工作台 | `/api/v1/*`、`/api/v1/workspace/*` | 请求头 `satoken`（Sa-Token 会话） | RBAC 权限码 + 知识库数据范围 + 应用使用范围 |
| 知识库开放 API / MCP | `/api/v1/knowledge/{search,chat,feedback,mcp}` | `Authorization: Bearer kb-sk-*` | Key 的 `app_scope` + 令牌桶限流 + 审计 |
| 记忆库开放 API / MCP | `/api/v1/memory/**` | `Authorization: Bearer kb-mk-*` | 一把 Key 绑一个记忆库，库内按 `user_id` 隔离 |

为什么要分三条：凭据形态、失败面、限流口径互不干扰。换成 Sa-Token 之后请求头也分了家——控制台走 `satoken`，开放 API 走 `Authorization`，一条链的凭据递到另一条链上，不会走到「看起来像但校验失败」那一步。

**追问：控制台为什么不读 Cookie？**

`is-read-cookie=false` 是安全前提而不是风格：浏览器不会替攻击者带上自定义请求头，CSRF 在构造上就不成立。一旦打开 Cookie 读取，整个管理 API 都要另配 CSRF 防护。

### P006 为什么 MySQL 是唯一事实源？

> 标签：一致性、架构 ｜ 难度：★★ ｜ 关联：R11

**参考回答**：检索链路的正文永远回 MySQL 取，引擎只给 chunk id 和分数；索引能推倒重建；删除语义确定。引擎命中但事实源没有这行 → 丢弃并异步清理引擎（实时路径的自愈）；行存在但被禁用 → 只丢弃不清理；快照路径关闭自愈。详见 R11。

**追问**：「为什么检索要多一次回表，不怕慢吗？」——回表是按 chunk id 的主键批量查询，候选最多几十到一百条；换来的是陈旧副本永远到不了用户面前，以及「引擎数据坏了也不是灾难」。这是用一次 IN 查询买一致性。

### P007 配置为什么分五层？请求级覆盖为什么只允许四个参数？

> 标签：架构、配置、发布门禁 ｜ 难度：★★

**考察点**：配置优先级设计，以及「门禁验证过的东西不能被调用方改掉」这条不变量。

**参考回答**

五层优先级从低到高：①环境变量 / `application.yml`（`KbProperties`）→ ②全局系统设置（`t_kb_system_config`）→ ③知识库级（`KbRetrievalConfig`，字段全可空，空即回落上层）→ ④应用版本快照（`AppConfigSnapshot`，发布时固化，**唯一不回落全局的一层**）→ ⑤API 请求级覆盖。

第 ④ 层不回落，是因为发布门禁验证的是「这份配置在这份语料上的效果」。如果运维改了全局默认值，已发布版本的行为就跟着变，门禁结论等于作废。

第 ⑤ 层是白名单，只有 `top_n`、`score_threshold`、`metadata_filter`、`max_content_length` 四项（`RequestOverridePolicy`）。它们只改变**返回形态**，不改变门禁验证过的检索行为；`recall_top_k`、融合、重排、版本 / 禁用 / 治理过滤都冻结在快照里。

白名单外的键**拒绝而非忽略**，返回 `INVALID_PARAM` 并记审计 `override_keys`。原因是静默丢弃会让 Agent 以为调参生效，从错误的结果里得出错误结论。

**追问**：「白名单为什么在结构上也成立？」`KnowledgeCallCommand` 只建模这四个字段，其他调参字段根本没有落点；传输层把载荷里出现过的调参键名收集进 `presentedOverrideKeys`，由服务层一处拒绝。这是结构和文本两半一起兜底。

**代码锚点**：`KbProperties`、`SystemConfigService`、`KbRetrievalConfig`、`AppConfigSnapshot`、`RequestOverridePolicy`、`KnowledgeCallCommand`

### P008 统一错误契约怎么设计？业务码和 HTTP 状态码是什么关系？

> 标签：架构、API设计 ｜ 难度：★★

**考察点**：错误语义是否可被调用方（尤其是 Agent）程序化处理。

**参考回答**

管理端所有 REST 返回同一个信封 `Result{code, message, data, request_id}`。`code` 是 `ErrorCode` 枚举名，`message` 只给安全文案，不带堆栈和内部细节，`request_id` 永远回显，用来关联服务端日志。

业务码和 HTTP 状态码一一绑定在枚举里。例如：

| 业务码 | HTTP |
| --- | --- |
| `INVALID_PARAM` | 400 |
| `UNAUTHORIZED` / `INVALID_API_KEY` | 401 |
| `FORBIDDEN` / `APP_ACCESS_DENIED` | 403 |
| `NOT_FOUND` / `VERSION_NOT_FOUND` | 404 |
| `PAYLOAD_TOO_LARGE` | 413 |
| `CONVERSATION_BUSY` / `EVAL_DATASET_CONFLICT` / `KNOWLEDGE_SNAPSHOT_UNAVAILABLE` | 409 |
| `RATE_LIMITED` / `MODEL_QUOTA_EXCEEDED` | 429 |
| `UPSTREAM_MODEL_ERROR` / `ANSWER_CITATION_INVALID` | 502 |

设计要点有三个：

1. **409 家族很大**：乐观锁冲突、幂等键复用了不同内容、会话已有活动运行，都属于「你的前提已过期，请重新读取」，调用方处理方式一致。
2. **429 分两种**：`RATE_LIMITED` 是短期限流，可以退避重试；`MODEL_QUOTA_EXCEEDED` 是月配额耗尽，重试没有意义。
3. **502 表示上游不可信**：模型出错，或模型引用了不存在的资料编号，都算上游问题，与服务自身 500 分开。

**追问**：「为什么 JSON 解析失败也要统一翻译成 400？」异常翻译层统一返回 `INVALID_PARAM`，并且日志不记录解析异常里可能携带的用户字段值，避免敏感输入进日志。

**代码锚点**：`kb-common/.../api/Result.java`、`ErrorCode.java`、全局异常处理器

### P009 表结构有哪些通用约定？为什么业务 ID 和自增主键并存？

> 标签：架构、数据模型、一致性 ｜ 难度：★★

**考察点**：数据模型基本功，以及这些约定解决的具体问题。

**参考回答**

业务表通常带「五件套」：`created_at`、`updated_at`、`lock_version`（乐观锁）、`deleted`（逻辑删除）加自增主键 `id`。对外暴露的是 `VARCHAR(64)` 业务 ID（如 `credential_id`、`kb_id`），带唯一键。

- **两套 ID 并存**：自增主键给 InnoDB 聚簇索引保持顺序写入；业务 ID 对外，不暴露数据量和插入顺序，也便于跨库迁移。
- **乐观锁**：所有「读 → 改 → 写」都带 `lock_version`，零行即冲突，返回 409 让用户重新载入，**不自动重试覆盖别人的修改**。
- **逻辑删除**：配合回收站与审计追溯；需要唯一约束的地方要把 `deleted` 考虑进去，或改为物理删除重插（关联表「先删后插」就是这么做的）。
- **多租户**：根聚合表带 `tenant_id`，由租户插件自动追加条件；从属表靠父表裁剪。

**追问**：「关联表要不要唯一键？」项目里两种做法并存，要能说出各自的依据：M15/M16 的关联表（如 `t_kb_doc_acl`）契约写明**故意不设唯一键**，改绑一律先删后插，由单点服务（如 `DocumentAclService`）保证不重复；V27 的 `t_kb_role_app` 则加了 `(role_id, app_id)` 唯一约束，用数据库兜底防止重复授权行。前者靠「只有一个写入口」，后者多一道数据库保险，代价是改绑必须严格先删后插。

**代码锚点**：Flyway `V1__baseline.sql`、`V19__web_credential.sql`、`V17`（多租户与 ACL）

### P010 为什么强调「单实例基线」？哪些状态是进程内的？

> 标签：架构、并发、部署 ｜ 难度：★★★

**考察点**：能否主动说清系统的部署前提与扩容边界，而不是默认「天然可水平扩展」。

**参考回答**

主服务以单实例为明确基线。进程内状态有这些，扩容前必须逐项处理：

| 状态 | 多实例后果 |
| --- | --- |
| 登录验证码 challenge / proof、登录失败守卫 | 需要粘性路由，或迁到 Redis / 数据库做共享原子存储 |
| 开放 API 令牌桶限流 | N 个实例等于 N 倍配额 |
| `@Scheduled` 定时任务（同步、清理、归档、快照保留） | 每个实例都扫描，外部副作用会重复 |
| 员工运行的心跳与过期扫描 | 只能判中断，没有跨实例接管 |
| 改写 / 路由 / 可见集等进程内缓存 | 只影响命中率，不影响正确性 |
| 会话与 RBAC 权限缓存 | `KB_CACHE_PROVIDER=redis` 一键切换，两者必须同时切 |

已经天然多实例安全的只有少数几处：MCP 无状态、检索链路无状态、模型预占恢复靠耐久行加乐观锁、邮件 outbox 用 `FOR UPDATE SKIP LOCKED` 加租约领取。

**原则**：把「单实例」写进文档是诚实，而不是缺陷。扩容触发条件写在 `DURABLE-SCHEDULING-DECISION.md`，达到证据门槛再投入。

**代码锚点**：`LOGIN-CAPTCHA-CONTRACT.md` §2、`DURABLE-SCHEDULING-DECISION.md`、`ARCHITECTURE.md` §7.2

## 二、数据接入与索引管线

### P011 从上传到可检索，完整链路是什么？事务边界画在哪？

> 标签：数据接入、索引、事务 ｜ 难度：★★

**考察点**：异步管线、事务与外部 IO 的边界、失败语义。

**参考回答**

```
UploadValidator（扩展名 + 大小 + magic number）→ 原件入 MinIO
→ 短事务写 document + document_version（只写元数据）
→ afterCommit 提交异步管线（IndexPipelineService）
→ 指纹判定（全匹配则复用上一构建的 chunk）→ 解析（HTTP 调解析服务，透传 X-Request-Id）
→ 清洗 / 脱敏 → 图片 VLM 文本代理插回原位 → 切分 → 嵌入
→ chunk 写事实源 → 同步行写 PENDING → 双写引擎 → 置 SYNCED
→ 版本 READY → 激活（切换可见集）
```

三个决策：

1. **事务里只写元数据**：解析和嵌入会失败，外部服务的失败不该回滚数据库事务，也不该长时间占连接。
2. **事务提交后才提交异步任务**：异步 worker 用独立连接读版本行，事务内触发会读不到未提交的行——这是 M1 联调时真实出现的竞态，所以统一用 `TransactionSynchronization.afterCommit`。
3. **编排与执行分离**：`IndexPipelineService` 只管阶段顺序和失败归类；切分落库、任务状态机、激活后续动作分别下沉到 `ChunkSplitter`、`IndexTaskLifecycle`、`VersionActivationHandler`。

失败语义：`PARSE_FAILED` 与 `INDEX_FAILED` 按异常错误码分流，运维据此判断该查解析服务还是索引链路；构建失败一律置 `BUILD_FAILED` 且绝不激活；执行方法不向异步包装层抛异常——状态已经如实落库，再抛只会用一条更模糊的记录覆盖它。

**追问：为什么要有 `PENDING_CONFIRM` 状态？**

知识库可以开「解析预览」：解析完先停下，让运营看清洗后的结果、必要时改清洗规则重解析，确认后再切分入库。默认关闭，因为多数语料不需要人工把关。

**代码锚点**：`DocumentService`、`IndexPipelineService`、`ChunkIndexWriter`；`kb-rag-deploy/docs/FLOWS.md` §1。

### P012 解析服务为什么独立部署？为什么还做了两套实现？

> 标签：文档解析、架构、合规 ｜ 难度：★★

**考察点**：职责边界、许可证合规、双实现的等价性保证。

**参考回答**

独立部署的三个理由：依赖污染（OCR、PDF、Office 重依赖）、故障隔离（畸形 PDF 能吃掉几个 G）、扩缩容曲线不同。并且立了一条不变量：**解析服务不调任何大模型**，模型配置、Key、成本归属只有主服务一份。

两套实现：`kb-rag-parser`（Python / FastAPI，契约定义方）与 `kb-rag-parse-java`（Java / Spring Boot），同端口、同契约、同环境变量，`PARSER_BASE_URL` 指向哪个都不改主服务。做第二套的实际原因是许可证：Python 版的 PDF 路径依赖 PyMuPDF，免费分发侧是 AGPL-3.0，带网络服务条款，而解析服务恰好是网络服务；Java 版走 Apache-2.0 的 PDFBox，直接依赖全部是宽松许可。

**追问：两套实现怎么保证行为等价？**

契约先行（OpenAPI）+ 端到端对拍脚本 `kb-rag-parse-java/tools/crosscheck.py`，覆盖 PDF 文本层、图片去重、Markdown 表格、时间戳归一、空白语义、聊天消息逐字段比对；差异项逐条登记。唯一涉及契约文本的差异是 `ocr_source` 取值（Java 侧是 `tesseract`），而主服务判断的是这个标记「存不存在」而不是「等于什么」，所以契约仍然成立。

**追问：解析服务自身的安全基线？**

单文件 100MB 上限；zip 解包校验路径不越界、解压总量 500MB / 条目 2000 上限（防 zip-slip 与 zip 炸弹）；XML 类解析禁用 DTD 与外部实体（防 XXE）；解析期零出站请求（SSRF 基线）；阻塞解析跑在 4 个 worker 的线程池里，单次 300 秒超时。

### P013 扫描件和图片怎么处理？

> 标签：文档解析、OCR、多模态 ｜ 难度：★★ ｜ 关联：P038、P012

**参考回答**

- **扫描页判定**：某页文本层少于 20 个字符就视为扫描页，按 150 dpi 渲染成图片（`SCANNED_PAGE_TEXT_THRESHOLD`）。
- **文字识别三级次序**：server 侧 VLM（有 Key，默认 `qwen-vl-max`）→ 解析服务本地 OCR（离线，Python 用 PaddleOCR、Java 用 tesseract，默认不装）→ 跳过。本地 OCR 成功会回填页文本并打标，server 据此跳过 VLM，避免重复花钱。
- **内嵌图片**：VLM 生成的文本代理用占位符插回原文对应位置，参与统一切分；chunk 的 metadata 记 `image_urls`，返回时换成 30 分钟的预签名 URL。
- **保护上限**：每篇最多 100 张图、单张 10MB；每篇文档同时在途的视觉调用 8 个——串行的话一篇图多的文档会占一个管线槽位半小时。单张失败不影响整篇。
- **可选多模态向量**：见 P038。

**追问：为什么 VLM 调用放主服务而不是解析服务？** 见 P012 的不变量：所有模型调用集中在主服务，计量、配额、降级才有唯一入口。

### P014 切分策略有哪些？父子分片为什么只能配定长？

> 标签：切分、父子分片 ｜ 难度：★★ ｜ 关联：R07、R09

**参考回答**：五种策略 `fixed_length / separator / heading / page / llm_semantic`，枚举封闭；父子分片是独立开关，默认父 1200 / 子 400 / 子片重叠 50 token，引擎只索引子片。详见 R07、R09。

「只能配定长」是按实现收窄的口径：`ParentChildSplitter` 是定长切分器与自身组合两遍，从来没有「先用所选策略切父片」的实现；此前配 `llm_semantic` 时会静默跑定长、指纹却记 `llm_semantic`。补实现的代价很高——LLM 语义切分逐父片再调一次模型的成本与缓存语义都没设计过，页 / 标题边界也和「父长子短两级预算」天然冲突——所以选择**收窄口径并在配置校验处直接拒绝**，而不是留一个看起来生效的组合。

**追问：需求文档写的「智能切分」「表格行级切分」呢？** 代码没有实现，默认策略是 `fixed_length`。照实说，并说明要不要补由评测决定。

### P015 文档更新怎么上线？版本和指纹怎么设计？

> 标签：版本管理、索引 ｜ 难度：★★ ｜ 关联：R15

**参考回答**：文档级版本 + 指纹复用（内容哈希、解析指纹、切分指纹、嵌入版本全部一致才复用上一构建的 chunk，只有嵌入变了就只重跑嵌入），激活只是切换可见集里的 `document_version_id`，不重建索引；旧版本保留 3 个可秒级回退；被应用快照引用的版本禁止归档。详见 R15。

**追问：为什么版本号要分 major / minor？** 字节变了（`content_hash` 变）是内容变化，major+1；字节没变但解析、切分、嵌入指纹变了是「同一内容的不同加工」，minor+1。运营看版本号就能区分「文档改了」还是「处理方式改了」。

### P016 MySQL 和引擎的一致性怎么保证？

> 标签：一致性、索引 ｜ 难度：★★★ ｜ 关联：R14

**参考回答**：同步状态表按「分片 × 物理索引」记录，先写 `PENDING` 再调引擎、成功置 `SYNCED`、失败置 `FAILED`；补偿任务每 30 秒扫 `FAILED` 和超过 5 分钟的 `PENDING`，按物理索引分组幂等重放，单批 500，重试 5 次告警。删除方向先写后删。详见 R14。

**追问：同步状态为什么是「分片 × 物理索引」而不是「分片 × 引擎」？** 重建期间同一个分片同时写新旧两个物理索引，两个目标的成败是独立事实。按引擎记，就没法表达「新索引写成功了、旧索引还没」，也就没法判断什么时候可以切别名。

### P017 不停机换嵌入模型，或者从 lite 迁到 full，怎么做？

> 标签：嵌入、索引、运维 ｜ 难度：★★★

**参考回答**

```
建新物理索引（命名 kb_{kbId}_{嵌入段}_{快照段}，嵌入段随模型变）并登记为第二写入目标
→ 双目标写入期：新增 / 变更分片自动写两处
→ 全量回填历史分片（幂等 upsert + updated_at 水位二次校验补写）
→ 校验新目标没有 PENDING / FAILED
→ updateAliases 原子切换别名（is_write_index）
→ 下线旧目标，清理其同步记录
```

业务读写只寻址别名，所以切换对检索链路完全透明；切换前旧索引持续服务。

**追问：水位二次校验解决什么？** 回填读的是某一时刻的快照，回填期间在线写入可能修改已经回填过的分片。回填结束后按 `updated_at` 水位再扫一遍补写，堵住「回填覆盖了更新的在线写入」的竞态。

**追问：别名切换踩过什么坑？** 早期用 `putAlias` 追加别名，导致别名同时指向新旧两个索引、写入永久失败；改为 `updateAliases` 原子操作并显式设置 `is_write_index`。

**追问：改切分参数为什么不走这套？** 切分参数不改引擎 schema，走同一物理索引内按文档原子替换 chunk（先写新片再删旧片）；「新索引 + 别名切换」只留给嵌入切换、lite → full、schema 变更三类场景。

### P019 网页、S3 / OSS、Confluence 怎么接入？为什么不新增入库旁路？

> 标签：数据接入、增量同步 ｜ 难度：★★

**考察点**：扩展数据源时如何复用而不是复制链路。

**参考回答**

所有来源都把内容物化成文件，交给同一个 `DocumentService.upload(kbId, fileName, bytes)`。**不新增任何入库旁路**，于是审核、有效期、版本、指纹复用、索引管线全部免费继承——开了审核的知识库登记一个 URL，新文档同样先落 DRAFT。

增量判断各用各的稳定标识：

| 来源 | 增量依据 | 未变化 |
| --- | --- | --- |
| 网页 | `sha256(body)` 与上次比对；文件名由 URL 稳定派生（`{host}-{path}-{url_hash8}.html`） | UNCHANGED，不触上传 |
| S3 / OSS | object key + ETag | UNCHANGED |
| Confluence Cloud | `pageId:version` | UNCHANGED，不请求正文 |

同步结果四态：SUCCESS / UNCHANGED / SKIPPED（绑定文档在回收站，不给回收站文档追加版本）/ FAILED，单项失败不中断批次。

**追问：列表超过上限怎么办？**

单源单轮默认最多 500 个对象，超出就只处理前 500 个、源状态至少记 PARTIAL，**并禁止做「消失判定」**——没列全就不知道缺的那部分是删了还是没列到。同理，Confluence 列表结构不完整、页面缺 id 或 cursor 循环直接判本轮失败，**不能把上游异常翻译成「页面已删除」**。

**追问：连接器怎么扩展？** `ExternalConnector` SPI（type / validateConfig / listObjects / fetchObject / testConnection），`ConnectorRouter` 按 `source_type` 路由、未知类型拒绝而不回落；连接器特有字段在登记和更新前就 fast-fail。

### P020 抓取用户给的 URL，SSRF 怎么防？

> 标签：安全、SSRF、数据接入 ｜ 难度：★★★

**考察点**：出站请求的安全基线。

**参考回答**

网页导入是系统里第一处「用户给什么就请求什么」的出站请求，所以单独建了 `UrlGuard`：

1. 只允许 http / https，URL 带 userinfo（`user@host`）直接拒绝。
2. 主机解析出的**每一个** IP 都必须不是回环、私网、链路本地、组播、`0.0.0.0`。
3. **重定向不自动跟随**，手动跟随最多 3 跳，且**每一跳重新过 UrlGuard**——防「公网 URL 302 到 169.254.169.254」。
4. 定时同步时重新校验，防 DNS rebinding。
5. 连接 / 读取超时 10 秒；**流式限制体积 10MB，不信 `Content-Length`**；Content-Type 白名单。
6. `allow-internal-address` 默认 false，注释标 DANGER，只给内网开发部署用。

其他出站面同一思路：Confluence 只接受 HTTPS 根地址，JDK HttpClient 禁止自动重定向，分页的 next 链接必须与登记地址同源才携带 Basic Token；带图提问只接受 base64，不接受图片 URL；解析服务解析期零出站。

### P022 审核、有效期、回收站怎么影响检索？

> 标签：治理、检索 ｜ 难度：★★ ｜ 关联：R24

**参考回答**

三套治理状态全部收敛为版本可见集的**行谓词**（`ActiveVersionResolver`：`trashed=0 AND publish_status=PUBLISHED AND 在有效期窗口内`），不写进任何引擎；状态变更只翻一行数据库记录并让缓存失效，无需重建索引。详见 R24。

几个语义决策：

- **PUBLISHED 是终态，不能退回审核**。审核的是「文档准入」而不是每个版本；要下架用有效期或回收站。追加新版本也不重置发布态。
- **允许把过期时间设在过去**——运营要的就是「立即下架」。
- **删除两段式**：DELETE 是移入回收站（可恢复，引擎数据原样保留、靠可见集挡住），只有回收站里的文档才能 purge；每天自动清理超过 30 天的回收站文档，单批 100 篇。
- **已发布快照不受治理回溯**：发布物应答门禁测过的语料，这是特性不是缺陷。

### P023 网页 JS 渲染抓取怎么做？无头浏览器带来了什么新攻击面？

> 标签：数据接入、SSRF、安全 ｜ 难度：★★★

**考察点**：新增一条能力时，是否识别出它绕过了既有防线。

**参考回答**

SPA 或 frameset 页面在服务端只返回脚本壳，静态抓取入库后没有正文。M17 为网页源加了按源开关 `render_js`（默认关），开启后由内嵌的 Playwright-Java（Chromium headless）完成「导航 → 等待 → 取 `page.content()`」。

**渲染只替换「取字节」这一步**，产物仍是 HTML 字节，交给既有的 `DocumentService.upload` → HtmlParser → 版本 / 治理 / 索引链路，不新增入库旁路。

新攻击面在于：浏览器会自动加载页面里的所有子资源（img / xhr / fetch / iframe / css），这些请求不经过主 URL 的 UrlGuard，可以被用来访问 `169.254.169.254` 这类元数据端点。防线是**路由拦截每一个子请求，逐个过同一个 UrlGuard**，重定向目标同样被拦截校验，这是能否上线的前置条件。

资源上的约束：

- `Semaphore` 限制渲染并发，浏览器 context 很重，超并发会 OOM。
- 每次抓取新建 context，用完即弃。
- 浏览器懒启动；未安装 Chromium 时，只让该源同步 FAILED 并给出原因，不拖垮启动。
- 总闸 `WEB_IMPORT_RENDER_ENABLED` 关闭时，所有 `render_js=1` 的源回落静态抓取。

**追问**：「等待策略默认是什么？」代码运行时默认是 `load`（`application.yml` 的 `WEB_IMPORT_RENDER_WAIT_UNTIL:load`）；部署模板 `.env.example` 写的是 `networkidle`，用 compose 部署时后者生效。`networkidle` 对长轮询页面会一直等到超时，这是契约里记录的开放问题。

**代码锚点**：`PlaywrightWebPageFetcher`、`WebPageFetcherDispatcher`、`UrlGuard`、`M17-CONTRACTS.md` §2–§3

### P024 需要登录的站点怎么抓？怎么防止抓到的是登录页？

> 标签：数据接入、安全 ｜ 难度：★★

**考察点**：凭据作用域的最小化，以及「HTTP 200 不等于拿到了内容」。

**参考回答**

**站点凭据**（M18，表 `t_kb_web_credential`）按 host 挂一份，类型有两种：`BASIC`（用户名 + 密码）和 `HEADER`（任意请求头，覆盖 Bearer 与 Cookie）。凭据属于站点而不属于页面，同一站点登记再多 URL 也只存一份，轮换只改一处。

**host 精确匹配，禁止后缀或通配**。后缀匹配正是 `wiki.example.com` 的凭据被发给 `evil.example.com` 的经典路径。`FetchCredential.appliesTo` 在每一跳重定向、每一个渲染子请求上都判断一次，重定向无法把认证头带到外部 host。读接口永不回传 `secret`。

**登录墙检测**（`LoginWallDetector`）：未认证的请求往往拿到的是**登录表单加 HTTP 200**，不检测就会把表单当正文入库并被检索到，这正是 M18 的起因事故。判定规则很保守：

- 正文里有 `type=password` 的输入框，单独即可判定。
- 最终 URL 像登录端点，**且**标题像登录页，两者同时满足才判定。

这样一篇「介绍登录页设计」的文章不会被误伤。检测放在所有抓取都经过的唯一出口，静态与渲染两条路径不会各自漂移。

**追问**：「凭据为什么明文存储？」与外部数据源 `secret_key` 同一决策（D17）：单管理员控制台、网络隔离部署。建议站点侧使用专用只读账号，控制泄漏的爆炸半径。这是需要主动说明的已知边界。

**代码锚点**：`FetchCredential`、`LoginWallDetector`、`V19__web_credential.sql`、`V22__web_credential_tenant.sql`

### P025 外部数据源同步失败了，怎么只重试失败项？

> 标签：数据接入、增量同步、幂等 ｜ 难度：★★ ｜ 关联：P104

**考察点**：部分失败的恢复语义，以及「清单被截断时不能推断删除」。

**参考回答**

外部源对象明细默认筛选失败对象；有文档写权限的用户可以点「仅重试失败项」（`POST /api/v1/ext-sources/{id}/retry-failed`，返回 `{accepted:true}`，受理不等于完成）。

- **范围**：每批最多 `kb.ext-source.max-objects-per-source` 个，优先处理最久未尝试的记录；不扫描新对象，也不碰健康对象。
- **清单截断**：复用有上限的远端清单拿实际版本和标题。清单被截断时，没出现的对象保持失败并记录范围提示。**只有完整清单才能证明对象已消失**。
- **消失或类型不再支持**：标为跳过，不删除绑定文档。
- **ETag**：失败状态不能仅凭 ETag 相同就标为未变化；重新入库成功后清除旧失败原因。
- **互斥**：单实例内同一来源的完整同步和失败重试互斥，重叠操作不重复写入。
- **中断**：已落库的逐项结果保留，未完成的仍可人工重试；不承诺后台自动续跑。

**追问**：「为什么不做自动重试队列？」遵守单实例调度边界，见 P104。自动续跑需要租约和幂等键，现在没有达到立项门槛。

**代码锚点**：`EXTERNAL-SOURCE-FAILED-RETRY.md`

### P026 来源的「最近同步时间」为什么拆成三个字段？

> 标签：数据接入、可观测、一致性 ｜ 难度：★★

**考察点**：时间语义的精确建模，以及并发写入下时间单调性的保证。

**参考回答**

一个「最近同步时间」回答不了运营真正关心的三个问题，所以拆成三个字段（V34）：

| 字段 | 含义 | 何时推进 |
| --- | --- | --- |
| `last_fetch_at` / `last_sync_at` | 最近一次尝试开始 | 每次尝试，包括失败 |
| `last_success_at` | 最近一次完整成功 | 网页 SUCCESS / UNCHANGED，外部源 SUCCESS |
| `last_content_change_at` | 最近一次真正接入新文档或新版本 | 上传链路返回非重复内容；外部源部分成功也可推进 |

失败和部分成功保留之前的成功时间；重复内容不推进内容变更时间。旧数据没有足够证据，新列保持 NULL，页面显示「暂无记录」，**不回填推测值**。

并发安全靠两点：时间字段走独立 Mapper，用 SQL 原子取最大值；普通实体更新不写这两列。这样迟到的同步结果或旧的设置表单都不会把较新时间倒写回去。

**边界**：来源时间都不能证明文档已完成解析、索引或审核发布，那些状态以文档页为准。

**代码锚点**：`HOME-SOURCE-HEALTH.md`、`V34__source_health_timestamps.sql`

### P027 IK 分词词典怎么热更新？为什么这个接口免鉴权？

> 标签：BM25、中文分词、运维 ｜ 难度：★★

**考察点**：外部组件集成协议的理解，以及免鉴权端点的风险论证。

**参考回答**

专有名词、产品代号被 IK 切碎，是「专名搜不到」的常见根因。词条在控制台维护，存 MySQL（`IkDict`），ES 的 IK 插件通过**远程词典**轮询 `/internal/dict/ik/{ext|stop}.txt` 拉取。

**协议的关键在缓存头，不在正文**。插件先发 HEAD，比较 `Last-Modified` 和 `ETag`，变了才下载；词典没变时返回 304。304 不是优化，而是防止每个节点每次轮询都重载分词器的机制。响应必须是 `text/plain; charset=UTF-8`，插件不猜编码，否则中文词条会乱码。

免鉴权的理由：插件是 ES 内部的裸 HTTP 客户端，无法携带 Bearer Token，要求鉴权会让热更新整体不可用；暴露内容只是运营主动录入的领域词，不含个人数据、文档内容或配置。豁免在控制器注释和 `WebMvcConfig` 拦截排除清单两端同时写明理由。

**追问**：「热更新后老文档需要重建吗？」需要。新词只影响之后的分词；已入索引的分片仍是旧切分，要让老内容按新词命中必须重建索引（别名切换，不停机）。查询侧分词会立即生效，于是出现「查询按新词切、索引按旧词切」的不对称，这正是需要重建的原因。

**代码锚点**：`InternalDictController`、`IkDictService`、`kb-rag-deploy/es-ik/`

### P028 分片标注有哪几种操作？为什么删除旧引擎文档要等事务提交后？

> 标签：治理、一致性、事务 ｜ 难度：★★★

**考察点**：人工修正与派生索引的一致性，以及不可逆操作与事务的顺序。

**参考回答**

标注有四种手工操作：编辑、合并、拆分、禁用。四者走同一条变更管线：**MySQL → 嵌入 → 双引擎**。

- **新文档在事务内写，旧文档在提交后删**。多写一次，只是几秒钟的重复；先删后回滚，则会留下补偿扫描看不见的空洞，因为回滚后的行仍然声称「已同步」。
- **语义校验放在服务入口而非控制器**：同文档、同版本、顺序连续、偏移越界这几项，只有数据库能回答，拆到两层就有两处要保持同步。
- **父片不进引擎**：父片只存 MySQL，推进引擎会让同一段文本匹配两次，还会把长度悬殊的段落放在一起比分。合并或拆分父片会重切子片，保证子片始终是父片文本的一个划分。

**版本继承**（`AnnotationInheritanceService`）：新版本只自动继承「禁用」，按归一化正文**精确**匹配，不用相似度猜测。编辑、合并、拆分不继承，因为新版本可能切法不同，重放会把运营决策作用到没人审过的文本上；没能继承的操作列入待复核清单，附原文摘录。

**追问**：「知识库删除为什么也要等提交后再删物理索引？」同一原则：引擎 drop 不可逆。标记与清理任务行加入删除事务，引擎删除在提交后由 CLEANUP 任务执行；同时先把分片从引擎移除，避免等待 drop 期间软删除的分片仍被检索到。

**代码锚点**：`ChunkAnnotationService`、`AnnotationInheritanceService`、`EngineChunkCleaner.removeAfterCommit`、`KnowledgeBaseService.delete`、`IndexCleanupService`

### P029 LLM 语义切分怎么落地？失败了怎么办？

> 标签：切分、Prompt注入、降级 ｜ 难度：★★ ｜ 关联：P014、P128

**考察点**：把概率性组件放进确定性管线时的约束设计。

**参考回答**

核心原则：**模型只指出切点，从不改写正文**（`LlmSemanticTextSplitter`，策略码 `llm_semantic`）。

1. **只输出下标**：每个窗口把候选句 / 行单元编号后发给模型（单元按 `\n.!?;。！？；` 断开），模型只返回「哪些单元结束一个分片」的下标数组，分片文本由这些位置从**原始字符串**切出。模型的措辞没有任何路径能进入分片，这是该策略的全部忠实性保证。
2. **输出强校验**：返回值必须是整数 JSON 数组，在窗口单元范围内，且严格递增。任一条不满足（JSON 畸形、越界、不递增）时，**只有该窗口**回退到定长切分并记 error 日志，文档其余部分不受影响。这也是注入防线之一：文档里的指令最多让一个窗口退化，改不了正文。
3. **滑动窗口**：长文档按批评判；后一个窗口带上前一个窗口末尾 2 个单元作只读上下文，使切点两侧都有正确的句子，但只有本窗口新增的单元会成为分片，重叠不会产生重复。
4. **缓存**：窗口结果存到对象存储，键由文档内容哈希、Chat 模型标识和固定的 Prompt 版本（`split_prompt_v1`）共同派生。换模型或换 Prompt 恰好让缓存失效，其他变化不会；同一文档重建不重复付费。
5. **选择门槛**：没有可用 Chat 模型时，配置校验直接拒绝这个策略（入口单点校验，下游不再检查）。
6. **组合限制**：父子分片只能配定长（见 P014），「LLM 切分 + 父子」会被配置校验拒绝（见 P128）。

**追问**：「语义切分值不值？」看评测。收益集中在结构弱、主题跳跃的长文档，代价是入库成本和时延；结构清晰的文档用 heading 策略几乎零成本，效果往往接近。

**代码锚点**：`LlmSemanticTextSplitter`、`FixedLengthTextSplitter`、`KnowledgeBaseService`（语义策略门槛校验）

## 三、检索链路

### P030 讲一下检索链路，为什么阶段顺序不能调？

> 标签：检索、架构 ｜ 难度：★★★ ｜ 关联：R25

**参考回答**

```
图片分路 → 改写 → 路由 → 解析索引上下文 → 多路召回（子片级）→ 库内融合 → 跨库融合
→ 近重复合并 → 重排 → 父子归并（含禁用剔除）→ 阈值 → top_n
```

每一级都可关，但没有两级能换位——改写在召回后没有作用对象；重排在融合前是在排两个不可比的列表；父子归并在重排前会把真正命中的子片藏起来；阈值在重排前是在一个即将被替换的分数上做丢弃。逐条论证见 R25。

另外两个「一条链路」的设计值得主动讲：单库调用就是 N=1 的多库调用；线上索引和发布快照也是同一条链路，差异只在 `RetrievalIndexContextResolver` 解析出的「查哪个索引 + 用哪个可见集」。**调试页、评测、门禁、线上流量走的是同一段代码**，这是评测结论能迁移到线上的前提。

**代码锚点**：`RetrievalService`（类注释逐条写了顺序理由）。

### P032 融合怎么做？多库怎么合并？

> 标签：融合、RRF、路由 ｜ 难度：★★ ｜ 关联：R18、R19

**参考回答**：库内默认 RRF（k=60），可选加权（每查询每路 min-max 归一化，`w_vec=0.6`，常数路归一化为 1.0）；开了图路或多模态路的库强制 RRF。跨库只用名次不用分数（`CrossKbRrfFusion`），跨库分覆盖库内分；重排候选是全局预算 50，按权重向下取整、余数给最高权重库、只在有候选的库之间分（`KbQuotaAllocator`）。详见 R18、R19。

### P033 阈值打在哪个分数上？`score_type` 为什么要如实上报？

> 标签：阈值、重排 ｜ 难度：★★★ ｜ 关联：R21

**参考回答**：重排分 > 归一化余弦 > 都没有就放弃阈值并报 `threshold_inactive`；节点上报被过滤的那个分数及其类型，调用方光看响应就能验证过滤。详见 R21。

**追问：Agent 调用方拿到 `score` 应该怎么用？** 只在 `score_type` 为 `rerank` 或 `cosine` 时把它当绝对相关度用；`fused_rrf`、`fused_weighted`、`bm25_rank` 只能用于同一次响应内排序。这也是为什么不能省掉 `score_type` 字段。

### P034 重排怎么做？成本怎么控？

> 标签：重排、成本 ｜ 难度：★★ ｜ 关联：R22

**参考回答**：cross-encoder（默认 `gte-rerank-v2`），1.5 秒硬超时，候选上限 50，超时 / 失败区分原因码并退回粗排，提交到线程池这一步也单独兜底；`hybrid` 模式按 0.7 / 0.3 混合语义分与归一化 BM25 分，但阈值仍只打纯语义分。详见 R22。

**追问：开了父子分片，候选怎么算？** 按子片粗排依次纳入，直到归并后父片数达到 `max(top_n×3, 20)` 或子片达到 50。需求文档写的「联动提升到 `max(50, top_n×5)`、硬上限 100」代码没有实现，`top_n=20` 时 60 个父片的目标可能凑不满——主动讲出来，并给出修法：按 `top_n` 计算候选上限，与供应商单次请求上限取小，超出时分批调用。

### P035 改写和路由都要调大模型，怎么防注入、防拖垮？

> 标签：查询改写、路由、Prompt注入 ｜ 难度：★★★ ｜ 关联：R20、R23

**参考回答**

- **改写**：默认关闭；800ms 硬超时包住整个调用；结果只作检索词、不进任何其他 prompt；输出压成单行、截断到 512 字符；只带最近 6 轮历史；缓存 key 是 query 与各轮内容的哈希。详见 R20。
- **路由**：只在调用方显式开启且绑定多库时运行；模型只有提议权，结果与绑定库**求交集**；空交集、解析失败、超时、没配模型一律回退搜全部并报 `route_fallback_all`——**宁可慢，不要静默地只用部分语料回答**。详见 R23。

**追问：为什么路由失败不回退到「搜空」或「搜第一个库」？** 那是不可观测的失败：用一部分语料答出来的答案，从外面看和正确答案没有区别。搜全部只是慢一点，而且响应里带着标记。

### P036 降级怎么设计？零 Key 能跑吗？

> 标签：降级、可观测 ｜ 难度：★★ ｜ 关联：R26

**参考回答**：必需级（BM25 召回）失败报错，增强级失败降级；所有降级进 `degraded` 数组并带按处置动作分类的原因码（14 个）；没人要求的阶段因缺模型而跳过不算降级。零 Key 下嵌入 `SKIPPED`、检索退 BM25 单路、生成返回 `UPSTREAM_MODEL_ERROR` 并提示配置。详见 R26。

**追问：降级了，Agent 调用方应该怎么处理？** 看原因码决定：`rerank_timeout` 可以直接用结果但降低置信；`vector_route_unavailable` 说明语义召回缺失，同义改写类问题可能漏召回，适合提示用户换关键词；`snapshot_index_missing` 说明发布版本在用当前语料作答，需要告警运维。**原因码的价值就在于让调用方能做不同的动作。**

### P037 版本可见集、发布快照和文档 ACL 是什么关系？

> 标签：版本管理、权限 ｜ 难度：★★★ ｜ 关联：R24

**参考回答**：可见集决定「哪些版本能被召回」，治理状态是它的行谓词；正式版用冻结的可见集查冻结的快照索引；**文档级 ACL 在两个分支都实时裁剪、不走缓存——发布冻结的是「哪些版本作答」，从来不冻结「谁能看」**。详见 R24。

### P038 图路和多模态路怎么做？为什么快照上下文要关掉它们？

> 标签：GraphRAG、多模态 ｜ 难度：★★ ｜ 关联：R27、R28

**参考回答**

- **图路**：检索侧零 LLM（切词 → Neo4j 实体全文匹配 → 最多 2 跳 → 溯源回 chunk，关联度 = 匹配分 / (1+跳数)），回溯到的 chunk 再回 MySQL 复核同一谓词（「图提议、MySQL 裁决」），开图路的库强制 RRF。
- **多模态路**：IMAGE 类 chunk 额外产多模态向量，文本 query 嵌入同一空间作独立一路参与 RRF；加权融合下跳过并报 `mm_route_skipped`；「加路不换路」，文本代理照常保留。
- **快照上下文关闭且不记降级**：图和多模态索引都没有冻结副本，跑它们会让发布版本召回到门禁没测过的语料。调用方要的是发布版本，拿到的就是发布版本应有的样子——这是能力边界，不是故障。

详见 R27、R28。

### P039 父子分片下，禁用的子片会不会从父片里漏出去？

> 标签：父子分片、治理、安全 ｜ 难度：★★★ ｜ 关联：R29

### P040 聊天记录的重叠窗口会召回重复内容，怎么去重？为什么放在融合之后、重排之前？

> 标签：检索、去重、融合 ｜ 难度：★★★

**考察点**：阶段顺序的成本与信息论证。

**参考回答**

聊天导入的重叠滑窗刻意让相同的对话轮次出现在两个分片里，命中这些轮次的查询会召回两个互相引用的结果，各占一个 `top_n` 名额和一份回答预算。

`NearDuplicateWindowMerger` 的规则：同一会话的两个窗口，消息区间重叠达到**较小窗口的一半**（`MERGE_RATIO_THRESHOLD = 0.5`），就丢弃排名靠后的那个。低于一半说明两者确实携带不同轮次，丢掉会损失内容。每个保留结果最多报告 5 个被吸收的分片 ID（`MAX_MERGED_IDS`），只供调试页解释排名，不用来还原召回集。

阶段位置的理由：

- **在融合之后**：只有融合后的排名能说明两个重叠窗口哪个更好。
- **在重排之前**：重复候选送进 cross-encoder 要付两次钱，之后还是要被丢掉。
- **不并入 `ParentChildMerger`**：父子合并是把同文档子片组成段落，成员仍然可见；这里是因为「已经说过」而直接丢弃候选。两件事唯一的共同点是缩短列表。
- **没有 `msg_span` 的分片永不触碰**：上传文档天然不参与，没有聊天导入的库只是一次保序遍历。

**代码锚点**：`NearDuplicateWindowMerger`、`RetrievalService`

### P041 检索调试页能看到什么？和线上调用有什么区别？

> 标签：检索、排障、可观测 ｜ 难度：★★ ｜ 关联：P109、P049

**考察点**：可解释性工具的设计，以及调试结果与线上行为的差异。

**参考回答**

检索调试页（M2，`search:debug` 权限）是回答「为什么这条没召回 / 为什么排在后面」的第一工具，展示三层信息：

- **实际生效的链路**（`applied`）：召回实际使用的 query（改写后）、融合方式、阈值作用在哪个分数上（`threshold_applied_on`，没过滤时为 `none`）、实际路由到的知识库。
- **每个结果的分数**：`score` 与 `score_type`，以及向量原始分、BM25 原始分、两路归一化分、融合分、重排分；图路结果还显示关联度、跳数和命中实体。
- **合并与脱敏痕迹**：父子模式下展开被合并的子片；聊天导入显示「已归并重叠窗口 ×N」；禁用子片被精确剔除时给出提示。

参数面板可临时调 `recall_top_k`、`top_n`、重排开关与模式、阈值；结果可以勾选「收进评测集」，也可以逐条反馈，直接接上质量闭环。

和线上的三处区别要讲清楚：

1. **语料**：调试与管理台预览用所选配置加**当前活动语料**；正式版对外调用走冻结快照。所以调试好了，线上未必一样，需要确认快照内容。
2. **权限**：需要 `search:debug` 或 `app:read`；调试入口不替代员工问答的 `app:use`。
3. **指标**：调试和评测不进生产监控和检索洞察，洞察只在 API 边界记录（见 P109）。

**追问**：「问答调试的耗时诊断怎么测？」见 P049。

**代码锚点**：检索调试页（`kb-rag-web/src/pages`）、`CHAT-PREVIEW-RELIABILITY.md`

### P042 以图搜图和带图提问是怎么走检索链路的？

> 标签：多模态、检索、安全 ｜ 难度：★★ ｜ 关联：P038

**考察点**：多模态输入如何复用文本链路，以及输入的安全边界。

**参考回答**

**图片分派是检索链路的第一步**（`MultimodalRetrievalService.dispatchImages`，在改写之前），两条路二选一：

1. **多模态路**（M14 F6）：知识库开了 `multimodal_enabled` 且多模态嵌入（`multimodal-embedding-v1`，1024 维）已配置时，图片直接嵌入图文同一空间，查 `{kbId}_mm` 索引（图搜图、图搜文），结果作为第三路与文本各路一起做 RRF。
2. **VLM 转写**（M9）：否则由视觉模型把图转成文字，以「[图片内容] 」前缀拼到 query 尾部，之后与普通文本查询完全相同。VLM 失败时追加降级码 `image_understanding_unavailable`；丢掉图片后没有可检索内容时报 `INVALID_PARAM`。

输入约束在一个校验单点（`ImageQueryService`）：只接受裸 base64，**不接受 URL**，杜绝 SSRF；最多 3 张，单张解码后 5MB，合计 10MB；`query` 仍然必填，纯图检索不做。

索引侧是「**加路不换路**」：IMAGE 类分片（内嵌图、独立上传图、扫描页整页渲染）额外产多模态向量，VLM 文本代理照常进主索引，BM25 和文本向量都还能命中。多模态路失败记 `mm_route_unavailable`，主路不受影响；`fusion_mode=weighted` 时多模态路不参与，记 `mm_route_skipped`。

`images` 不在覆盖白名单里：图片是问题的一部分，和 `query` 同性质，不是调参。

**追问**：「正式版调用为什么不走多模态路？」见 P038：快照路径关闭图路和多模态路，**且不记降级**。多模态索引没有冻结副本，跑它会让发布版本召回到门禁没测过的语料。

**代码锚点**：`MultimodalRetrievalService`、`ImageQueryService`、`RetrievalService.recallMultimodal`、`M14-CONTRACTS.md` §6–§7

### P044 怎么保证模型不乱编引用？

> 标签：引用、幻觉 ｜ 难度：★★ ｜ 关联：P075

**考察点**：把「模型听话」变成「可检测、可拒绝」。

**参考回答**

三层，从预防到拦截：

1. **Prompt 里给出本轮合法编号清单**：「本轮仅有 N 条可引用资料，合法引用编号完整列表：[1] [2] …」，没有资料时明确「不能生成任何 [数字] 引用标注」。
2. **编号与正文分字段**：只许用 `citation` 字段的编号，不许用正文里的章节号、原文参考文献号或历史回答里的编号。
3. **生成后确定性校验**（`AnswerCitationValidator`）：用 Markdown 解析器遍历正文文本节点（链接、图片不算），任何 `[n]` 超出本轮资料数就判 `ANSWER_CITATION_INVALID`，答案标记为「仅供核查」、不发成功终态。流式场景不阻塞首字，结束前统一校验。

边界要说清：它只校验「编号合法」，**不判断引用的证据是否真的支持那句话**——那是离线 Judge 的 `citation_correctness` 负责的事（P075）。

### P045 模型输出被截断了，系统怎么知道？

> 标签：生成、可观测 ｜ 难度：★★

**参考回答**

检查 `finish_reason`：`stop` 才是正常结束；`length` 判 `OUTPUT_TRUNCATED` 失败；其他显式非正常结束同样判失败，而且不把供应商返回的任意字符串拼进错误、日志或界面。流式场景下缺少 `[DONE]` 结束帧也判不完整。已经产生的用量照常结算。

一句话：**传输成功不等于回答完整**。半句话处被砍断的答案，比报错更容易误导人。输出预算也分开配：生成 1024 token、改写 128 token、Judge 2048 token——共用一个短预算会把每个答案都砍在半句。

**代码锚点**：`ChatCompletionOutcome`、`OpenAiChatStreamSubscriber`（提交 `58da37a`）。

### P046 SSE 事件契约是什么？引用为什么最后发？

> 标签：流式、引用 ｜ 难度：★★ ｜ 关联：R33

**参考回答**：`message_delta* → references → done`，失败走 `error`，整个流只有一个终态；引用在完整答案通过校验之后才发，上游必须收到 `[DONE]` 才算正常结束；`degraded` 放在 `done` 里；静默期每 5 秒发注释心跳。详见 R33。

**追问：前端怎么判断「回答完整」？** 只认业务终态：收到 `done` 才算成功；HTTP 正常 EOF 但没收到终态，报 `STREAM_INCOMPLETE` 并保留已收到的内容；主动停止不显示为网络失败，也不自动重发问题。

### P047 用户中途关页面，服务端还在生成吗？钱怎么算？

> 标签：流式、成本 ｜ 难度：★★★

**参考回答**

开放 API 和预览走连接生命周期：客户端断开 → 心跳写失败被发现 → 取消上游 HTTP 请求；取消只绑定该次调用的资源句柄，不去中断可能已被线程池复用的线程；进入最终生成前会再检查一次取消状态。检索内部尚未接入取消信号的同步改写、重排调用可能跑到它们自己的超时，但不会再进入生成。

计费按「供应商可能已经受理」保守处理：

| 情况 | 状态 | 配额 |
| --- | --- | --- |
| 请求发出前取消 | CANCELLED | 释放预占 |
| 上游明确拒绝 | FAILED | 释放预占 |
| 正常结束且有 usage | SUCCEEDED | 按实际结算 |
| 正常结束但无 usage | SUCCEEDED + estimated | 按预占上界结算 |
| 发出后取消、没拿到 usage | CANCELLED + estimated | 按预占上界结算 |

关闭本地连接只能发起取消，不能保证供应商已停止计费，所以不能记成零。

### P048 为什么所有生成都要走同一个 `AnswerGenerationService`？

> 标签：生成、架构、评测 ｜ 难度：★★

线上问答、管理台预览、离线评测三者共用这一个生成入口：Provider 解析（按应用版本快照固化的模型，经 `ChatProviderFactory` 按模型名缓存实例）、系统 Prompt、消息装配都在这里。原因只有一个——**门禁不能测一份线上永远不会执行的「近似 Prompt」**。

### P049 问答调试的耗时诊断怎么设计？为什么服务端和浏览器要分开测？

> 标签：可观测、性能、流式 ｜ 难度：★★★

**考察点**：延迟度量的边界定义，避免重复相加和错误归因。

**参考回答**

每轮回答可以展开耗时诊断，分两组：

- **服务端**：配置解析、检索（含改写、路由、召回、融合、重排）、重排（检索内）、生成、首段等待、执行总耗时。
- **浏览器**：首段等待、接收总耗时。

分开测，是因为两者边界不同：服务端总耗时不含鉴权、异步排队、最终引用写出和网络往返，浏览器测的才是用户体感。设计要点：

1. **单调时钟**：服务端用 `System.nanoTime`，浏览器用 `performance.now`，不受墙上时钟调整影响。
2. **包含关系不能重复相加**：首段等待包含在总耗时里，重排包含在检索里；各段单独取整到毫秒，合计可能有舍入差。
3. **未知、未执行、0 毫秒要区分**：改写、路由、召回尚未单独采集，不能从检索总耗时倒推。
4. **重排状态显式**：`rerank_status` 有 `APPLIED` / `DISABLED` / `EMPTY_CANDIDATES` / `UNAVAILABLE` / `TIMEOUT` / `FAILED` / `SKIPPED`，只有应用、超时、失败三种携带耗时；线程池拒绝也算失败。

**只在管理台预览**采集，以可选 `diagnostics` 事件在终态之前发送；公开 API、MCP、员工会话都不新增字段。诊断不含提示词、密钥或费用，费用走模型用量账本，不能由耗时估算。

**代码锚点**：`CHAT-DIAGNOSTICS.md`、`KnowledgeApiService.preview`、`api/chatDiagnostics.ts`

### P050 流式生成中途断了，怎么判断回答是否完整？服务端怎么取消上游？

> 标签：流式、成本、可靠性 ｜ 难度：★★★

**考察点**：流式协议的终态判定，以及取消与计费的真实边界。

**参考回答**

**完整性判定**：OpenAI 兼容接口开启 `stream: true`，必须收到上游 `[DONE]` 才发 `references` 和 `done`。前端的业务流驱动只接受一次 `done` 或 `error` 终态：

- HTTP 正常 EOF 但没有终态，报 `STREAM_INCOMPLETE`，已收到的内容保留。
- 解析失败也是失败终态。
- 主动停止不显示为网络失败，也不自动重发问题。

**取消链路**：`SseChatStreamListener` 发现连接关闭后，取消该次调用持有的上游 HTTP 句柄。取消只绑定本次调用的资源，**不去中断可能已被复用的线程池线程**。静默期每 5 秒发一次 SSE 注释心跳，没有新 Token 时断连也能被发现。进入最终生成前再检查一次取消状态。

**计费真相**：关闭本地连接只能「发起」取消，不能保证供应商已停止计费。所以已发出后取消且没拿到 usage 的，按预占上界结算，标 `CANCELLED + estimated`；未定价费用不显示成已知的 0。

**追问**：「SSE 解析器有哪些边界？」UTF-8 跨网络块、BOM、LF / CRLF / CR 三种换行、注释、多行 data；只派发以空行结束的帧；单行最多 64 KiB，单事件最多 1 Mi 字符。

**代码锚点**：`CHAT-STREAM-LIFECYCLE.md`、`ChatStreamHttp`、`SseChatStreamFactory`、`kb-rag-web/src/utils/sse.ts`

### P051 为什么同时提供 REST 和 MCP？「第二种 transport，不是第二种身份」是什么意思？

> 标签：Agent、MCP ｜ 难度：★★

**考察点**：协议扩展时如何不扩大安全面。

**参考回答**

MCP 让任何兼容客户端（Claude Desktop、Cursor、自研 Agent）配一个 URL 加一把 Key 就能把知识检索、问答、长期记忆当工具用；REST 服务于确定性的业务集成与流式问答。

「第二种 transport」的含义：MCP 请求在进入 Controller 前先过 Origin 校验，然后进入**与 REST 完全相同**的 Key 鉴权、授权范围、限流、审计过滤器链，最后调 REST 孪生的同一个服务方法。多一种协议，不多一种凭据、不多一套权限、不多一份业务语义。

| MCP 服务 | 端点 | 工具 | 凭据 |
| --- | --- | --- | --- |
| `kb-rag-knowledge` | `POST /api/v1/knowledge/mcp` | `knowledge_search` / `knowledge_chat` | `Bearer kb-sk-*` |
| `kb-rag-memory` | `POST /api/v1/memory/mcp` | `memory_add` / `memory_search` / `memory_list` / `memory_update` / `memory_delete` / `memory_get_profile` | `Bearer kb-mk-*` |

### P052 MCP 服务端为什么手写？无状态和双协议兼容怎么做？

> 标签：MCP、Agent ｜ 难度：★★★

**参考回答**

`McpServerEngine` 零 SDK 依赖。这是一个取舍：协议面很小（现代版 `server/discover` / `ping` / `tools/list` / `tools/call`，旧版多一个 `initialize` 与通知），而需求是同一 URL 同时服务两个协议时代、完全复用既有过滤器链与 principal、不维护会话——引入 SDK 反而要绕过它自带的 transport 与会话管理。代价是协议演进要自己跟进。

- **无状态**：不签发也不要求 `Mcp-Session-Id`，身份和协议版本都在每个 POST 里自足，水平扩展没有会话粘滞。
- **按请求识别时代**：有现代标记（请求头、`_meta` 或 `server/discover`）走 2026-07-28 协议，逐请求校验 `_meta` 与 `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` 头体一致性，不从上一个请求推断能力；否则走 `2025-03-26` / `2024-11-05` 的 initialize 流程。
- **状态码按时代隔离**：现代协议头体不一致 400 / -32020、版本不支持 400 / -32022、方法未实现 404 / -32601；旧版协议错误仍由 HTTP 200 的 body 承载。
- **工具目录可缓存**：discover 与 `tools/list` 给出 5 分钟 public 缓存提示、按名称稳定排序——工具 schema 里没有租户私有数据；但**调用结果绝不能按这个规则共享缓存**。

### P053 MCP 调用失败，错误应该返回给谁？

> 标签：MCP、工具调用 ｜ 难度：★★

**考察点**：Agent 工具设计里最容易做错的点。

**参考回答**

三个失败平面，各自有各自的读者：

| 平面 | 例子 | 表现 | 谁来处理 |
| --- | --- | --- | --- |
| transport | Key 无效、限流、Origin 非法 | HTTP 401 / 429（REST 信封）/ 403 | 运维与集成方 |
| 协议 | JSON-RPC 格式错、方法不存在、工具名不在目录 | JSON-RPC error | 客户端框架 |
| 工具结果 | 参数不合法、资源不存在、`stream:true` | `result.isError=true`，文本是「错误码: 消息」 | **模型** |

关键决策：**业务失败只进工具结果平面，不抛成协议错误**。参数写错、文档不存在，模型读到 `isError` 和可读的错误信息后能自己改参数重试；抛成协议错误，客户端框架会吞掉或直接报错，模型根本看不到，Agent 就失去了自纠的机会。

### P054 给 Agent 用的工具，参数和返回怎么设计？

> 标签：工具调用、Agent ｜ 难度：★★

**参考回答**

1. **工具少而粗**：知识库只暴露两个工具，参数复用 REST 的请求对象；融合、重排这些内部级别 Agent 不需要知道，也改不了——请求级覆盖只有 `top_n`、`score_threshold`、`metadata_filter`、`max_content_length` 四个白名单参数，白名单外直接 INVALID_PARAM 而不是忽略。
2. **身份不进参数**：记忆库工具的库来自 Key 的绑定关系，arguments 里根本没有 `library_id` 这个字段，越权无从谈起。
3. **显式校验**：`McpArgumentBinder` 用 Jackson `treeToValue` 转对象后手动调 jakarta Validator——树转换不会触发 Bean Validation，这一刀必须自己补上。
4. **结果双形态**：`content[0].text`（JSON 文本）给只认 text 的旧客户端，`structuredContent`（与 REST `data` 同构）给能读结构的客户端，两者同源产出。
5. **不支持的能力明确拒绝**：`knowledge_chat` 带 `stream:true` 返回 INVALID_PARAM 工具结果并指路 REST SSE。

**追问：为什么越权返回 404 而不是 403？** 403 等于告诉调用方「这个资源存在，只是你不能碰」。对 Agent 来说，id 可能是模型幻觉出来的，也可能是注入诱导的探测，统一 404 不泄露存在性。

### P055 MCP 端点为什么要校验 Origin？

> 标签：MCP、安全 ｜ 难度：★★

**参考回答**

MCP 端点常被部署在内网或开发机上，而浏览器里的任意网页都能向它发请求——如果端点只靠「在内网」保证安全，恶意页面就能借用户的浏览器打进来（DNS rebinding 是典型手法）。

`McpOriginValidationFilter` 位于两条 Key 鉴权过滤器之前：没有 Origin 的服务间调用放行；有 Origin 的必须命中既有 `CORS_ALLOWED_ORIGINS`，否则 403。**来源规则只有这一份，不另造 MCP 白名单**，避免两份配置漂移。

### P056 记忆库怎么写入？抽取怎么防止模型乱改记忆？

> 标签：记忆、Agent ｜ 难度：★★★

**参考回答**

`POST /api/v1/memory/add`：`messages`（交给模型按片段规则抽取）与 `custom_content`（原文直写，不经模型）二选一或同时提供。

1. **规则驱动**：片段规则决定抽什么、是否 `auto_update`、多久过期；画像规则决定抽哪些用户属性。新建记忆库自带一条内置默认规则，开箱即用。
2. **更新只许发生在窗口内**：开 `auto_update` 时，把该用户最近 50 条旧记忆连同对话交给模型；模型返回 ADD，或「UPDATE + 目标节点 id」，UPDATE **只允许命中这 50 条之内的节点**——模型编造一个 id，也改不到窗口外的数据。
3. **画像幂等 upsert**：按「画像规则 × 用户」唯一键写入，同一用户同一规则只有一份画像。
4. **写入刻意不是一个事务**：抽取夹在写入之间，持有数据库连接跨一次大模型往返，中等负载就会把连接池耗尽。每个节点独立落库并立刻写检索副本；失败最多丢一次调用的尾部，调用方看到错误可以重试。
5. **嵌入失败不阻塞写入**：该节点向量置空，仍能被 BM25 召回；检索副本可以从 MySQL 重建。

### P057 记忆库怎么检索？隔离怎么做？

> 标签：记忆、多租户 ｜ 难度：★★

**参考回答**

```
加载该用户画像 → 可选意图识别（判定与记忆无关则直接返回空节点 + 画像，省一次检索）
→ 可选改写 → 检索（强制 filter：library_id + user_id + 未过期）
   嵌入可用：kNN + BM25 并联；零 Key：BM25 单路
→ 可选重排（候选 = max_results × 3，上限 100；阈值只作用于重排分）
→ 回 MySQL 取事实源（保序，已删节点静默跳过）→ 截断到 max_results
```

隔离三层：Key 绑定唯一记忆库（应用级）、`user_id` 查询谓词（实体级）、管理端的租户围栏（`MemoryLibraryGuard` 让每个带 libraryId 的入口先解析库）。所有记忆库共用一个 ES 物理索引，隔离完全靠 filter——所以 filter 由服务端构建，不接受调用方传入。

**追问：开放端为什么不拼租户条件？** 开放端线程上没有控制台主体，租户围栏整条跳过是必须保留的语义——一拼租户条件，Key 反而会把自己的库过滤掉。开放端的隔离由「Key 绑库 + user_id」两层谓词完成。

### P058 记忆和知识库有什么区别？什么该放哪里？

> 标签：记忆、选型 ｜ 难度：★★ ｜ 关联：R44

**参考回答**：知识库存组织的公共知识（运营写入、版本化、门禁保障），记忆库存某个最终用户的偏好与事实（Agent 抽取、增量更新、可过期）。判据是「这条信息属于谁」——把用户偏好写进知识库，就会被别的用户检索到，这是权限事故而不是效果问题。详见 R44。

**追问：Agent 一轮对话里怎么同时用两者？** 先 `memory_search` 拿画像与相关记忆放进系统提示词（个性化），再 `knowledge_search` / `knowledge_chat` 拿有据答案（事实）；回答后再 `memory_add` 把新偏好写回。两次检索互不影响各自的隔离模型。

### P059 一个外部 Agent 从零接入 kb-rag，完整流程是什么？

> 标签：Agent、MCP、工具调用 ｜ 难度：★★ ｜ 关联：P007

**考察点**：能否把平台能力串成一条可交付的接入路径，而不是只讲接口。

**参考回答**

```text
建知识库并入库 → 建应用、关联知识库（可多库 + 权重）
→ 建版本、提交测试（DRAFT → TESTING）→ 绑定评测集发布（门禁）→ RELEASED
→ 应用中心签发 API Key（kb-sk-*，授权范围 = 指定应用）
→ Agent 调 REST（/api/v1/knowledge/search、/chat）或 MCP（/api/v1/knowledge/mcp）
→ 需要长期记忆时：建记忆库、签发 Memory Key（kb-mk-*），调 /api/v1/memory/* 或 /api/v1/memory/mcp
→ 终端用户反馈回传 /api/v1/knowledge/feedback，进入质量闭环
```

关键点：

1. **Agent 面对的是「应用」，不是知识库**。检索参数、Prompt、模型、路由都冻结在应用版本快照里，Agent 只能覆盖白名单内四个参数（见 P007）。
2. **MCP 和 REST 是同一身份的两种 transport**：同一把 Key、同一套授权范围、限流、审计。MCP 工具 `knowledge_search` / `knowledge_chat` 对应 REST 孪生端点；记忆库有 `memory_add`、`memory_search`、`memory_list`、`memory_update`、`memory_delete`、`memory_get_profile` 六个工具。
3. **记忆库由 Memory Key 绑定**，工具参数不能另行指定库，避免 Agent 越界读写别人的记忆。
4. **灰度**：显式传 `app_version` 可以调用测试版，审计标 `target_stage=beta`，统计不与正式流量混算。

**追问**：「为什么让 Agent 调 `search` 而不是 `chat`？」多数 Agent 自己有 LLM 和规划能力，要的是证据而不是答案：`search` 返回带引用定位的节点，由 Agent 自己综合；`chat` 适合没有生成能力的轻量调用方。

**代码锚点**：`MCP接入指南.md`、`记忆库接入指南.md`、`KnowledgeOpenApiController`

### P060 MCP 里的 `knowledge_chat` 为什么只返回单次 JSON？传了 `stream:true` 怎么处理？

> 标签：MCP、流式、工具调用 ｜ 难度：★★ ｜ 关联：P053

**考察点**：协议能力边界与错误平面的选择。

**参考回答**

MCP 的 `tools/call` 被设计为一次请求对应一个结果，服务端无状态、不签发 `Mcp-Session-Id`，每个请求重新认证，可以安全重试和水平扩展。`knowledge_chat` 在 MCP 中只返回完整答案；需要 Token 流时走 REST SSE（`/api/v1/knowledge/chat` + `stream:true`）。

MCP 调用传了 `stream:true`，返回的是**工具业务错误**（HTTP 200，`result.isError=true`），而不是协议错误。协议层的请求本身是合法的，出问题的是参数取值；业务错误的 content 会被 Agent 读到，它可以自行去掉参数重试。协议错误则往往被客户端框架拦截，模型看不到。

**追问**：「错误平面还有哪些？」现代协议的镜像头缺失或头体不一致返回 400 / `-32020`；版本不支持返回 400 / `-32022`；方法未实现返回 404 / `-32601`；Origin 不在白名单返回 403；Key 无效返回 401、超 QPS 返回 429，这两者用 REST 错误信封。见 P053。

**代码锚点**：`MCP接入指南.md` §5–§6、`M22-CONTRACTS.md`

### P061 开放 API 的终端用户反馈怎么设计？为什么 `request_id` 查不到就拒绝？

> 标签：Agent、运营闭环、评测集 ｜ 难度：★★ ｜ 关联：P079

**考察点**：反馈数据的可用性与可信边界。

**参考回答**

`POST /api/v1/knowledge/feedback`，入参 `{request_id, chunk_id, verdict(GOOD/BAD), comment?, end_user_id?}`，用 API Key 认证，沿用开放 API 的限流。落到既有的 `t_kb_retrieval_feedback`，加 `channel=OPEN_API` 维度，控制台反馈列表和洞察页可按渠道筛选。

- **`kb_id` 和 `query` 不由调用方传**，而是用 `request_id` 反查检索留痕补齐。查不到就返回 `INVALID_PARAM`（「request_id 无效或已过期」）：没有原查询的反馈无法转成评测用例，是垃圾数据。
- **`end_user_id` 只是调用方自报**，系统不为其真实性背书。
- `comment` 截断到 512 字符，落 `note` 列。

反馈之后的路径：GOOD 反馈可转评测用例；BAD 反馈不能直接当证据，要走质量问题处理，由人补正确证据（见 P079）。

**代码锚点**：`M16-CONTRACTS.md` §3（F7）、`RetrievalFeedbackService`

## 六、员工问答：长任务运行时

> 这一部分是 Agent Runtime 的缩影：长耗时、可中断、可恢复、有副作用（花钱）、要持续校验权限。高级 Agent 岗很爱问。

### P062 为什么把问答从「一次 HTTP 连接」改成「持久运行 + 只读订阅」？

> 标签：长任务运行时、Agent ｜ 难度：★★★

**参考回答**

连接生命周期的问答有三个解决不了的问题：刷新页面答案就没了；断网重连只能重新提问、重复花钱；多个标签页各自提交同一个问题。

改造后：

- 提问是一个**命令**（`POST .../runs`），服务端在短事务里写账本、占据会话活动位，只有首次受理的调用方在事务提交后才调度执行。
- 读取是**只读订阅**（`GET .../runs/{runId}` 或 SSE `.../events`），连接断了只影响订阅，不影响运行；重连读同一个运行。
- 停止是另一个**命令**（`POST .../stop`），只有用户明确点击才取消。

一句话：**连接只是观察窗口，运行才是事实。**

### P063 幂等提交怎么做？

> 标签：幂等、长任务运行时 ｜ 难度：★★

**参考回答**

1. 客户端每次提问生成一个 `request_id`（8–128 位字母、数字、下划线或连字符），问题最长 8000 字符。
2. 服务端在**会话锁**内检查幂等：同 id 同内容 → 返回原运行；同 id 换内容 → `409 CONVERSATION_REQUEST_CONFLICT`；另一个运行尚未结束 → `409 CONVERSATION_BUSY`。
3. 数据库兜底：`(conversation_id, client_request_id)` 与 `(conversation_id, turn_no)` 唯一约束。
4. 原请求重放不受后续换版影响：幂等检查先于解析当前发布版本。
5. 执行者还要取得一次性的 `start` 领取资格，队列拒绝时保存失败终态并释放会话。

前端配合：发送结果不明时保留草稿，用户点「确认发送结果」用**同一个 id** 重试；只有「重新生成」才换新 id。自动恢复只做 GET，永远不自动重新提交。

### P064 断线重连怎么做？SSE 推的是什么？

> 标签：断线恢复、流式 ｜ 难度：★★★

**参考回答**

订阅每秒读一次**已提交的**运行快照，空闲 5 秒发一次注释心跳，每条连接最长 2 分钟；实例最多 64 个订阅、同一租户用户最多 4 个，超额 429。

| 事件 | 内容 | 客户端处理 |
| --- | --- | --- |
| `snapshot` | 完整运行状态，事件 id 为 `run_id:revision` | 替换，不追加 |
| `done` | `{run_id, status, revision}`，只在读到持久终态后发 | FAILED / CANCELLED / INTERRUPTED 也是终态，不能都渲染成成功 |
| `error` | `{code, message, retryable, clear_content}` | 只说明订阅失败，不能自动重新提交问题 |

重连总是先拿到完整快照，**不依赖保存逐 token 事件**——存储和一致性都简单得多。完整答案、成功终态、释放活动位在同一事务提交，连接只能读到提交后的状态，不能凭内存里的完成信号发成功。

**追问：同一个 revision，内容会变吗？** 会。`restricted`（权限投影）可能在 revision 不变时改变——用户被撤权后同一个快照要清空正文与引用，所以相同序号的权限投影也必须应用。

### P065 停止怎么做？为什么先落库再取消？

> 标签：长任务运行时、一致性 ｜ 难度：★★★

**参考回答**

顺序：**先持久化停止状态，再取消上游生成**。反过来的话，取消上游之后、写库之前进程挂了，运行会停在 RUNNING，过期扫描再把它判成 INTERRUPTED——用户明明点了停止，看到的却是「中断」。

终态不可逆：迟到的检查点、失败回调、成功回调都复活不了运行。删除会话时在同一事务里取消活动运行并软删会话，提交后再取消上游。

边界要诚实：取消能中断生成阶段的上游 HTTP 请求；检索管线只在进入和退出时检查取消信号，内部同步的改写、重排调用可能跑到它们自己的超时——但不会再进入生成。**不能描述成「所有检索请求都能即时中止」。**

### P066 进程挂了、运行卡住了怎么办？为什么不自动重跑？

> 标签：长任务运行时、可靠性 ｜ 难度：★★ ｜ 关联：P104

**参考回答**

- **心跳**：执行中每秒写一次累计正文检查点或心跳，同时重验身份、应用范围与全部证据权限；撤权或维护失败立即取消生成。
- **过期扫描**：应用启动后每 30 秒扫描一次 3 分钟没更新的活动运行，每批最多 100 条；取得会话锁后**重新核对更新时间**再判 `INTERRUPTED`——扫描之后恰好有心跳的运行不会被误杀。
- **正常停机**：把本实例持有的排队 / 执行中运行标为 `INTERRUPTED`。
- **上限**：单次运行最长 10 分钟、答案最长 100,000 字符。

**不自动重跑**有两个原因：重跑会重复花钱；重跑的答案可能和用户已经看到的半截答案不一致。让用户决定是否「重新生成」（新的 request_id）。

**追问：多实例下谁来接管？** 当前明确是单实例执行基线，不提供跨实例自动接管；多实例接管需要 lease / owner / heartbeat 协议，立项门槛见 P104。

### P067 多轮历史怎么进上下文？撤权了怎么办？

> 标签：多轮对话、权限 ｜ 难度：★★★

**参考回答**

- 取最近 10 轮、合计 24,000 字符以内的**可读的成功**历史；不截断单个问答对，避免形成误导性的半段上下文。
- 历史读取和进入模型上下文时，都重新校验知识库归属、当前文档 ACL、文档 / 版本是否存在，以及发布、生效、过期、回收状态。
- **任一来源不可读，整条回答及其引用被遮蔽**——不能只隐藏引用、继续展示由它派生的答案。用户自己的问题保留显示，但这对问答整体排除出模型历史。
- 新回答保存「本轮引用 ∪ 历史继承依赖」：本轮没有新命中，也不会丢掉它通过前文用到的资料，下次撤权时同样能遮蔽。

### P068 员工运行为什么要「严格快照」？

> 标签：版本管理、长任务运行时 ｜ 难度：★★

**参考回答**

`EmployeeRunTarget` 在受理时捕获应用版本、配置、冻结索引与可见版本集。之后即使发布了新版本，已受理的运行也不会切到新语料。

严格模式（`strictSnapshot`）的三条规则：快照内版本集合为空就保持为空、不去查询该库；索引或版本集合绑定缺失 → `KNOWLEDGE_SNAPSHOT_UNAVAILABLE`，**禁止静默读取当前语料**；从未保存过快照的历史发布明确使用当前语料，并以 `snapshot_bound=false` 告诉界面。

开放 API、MCP、调试和评测保持原契约（快照缺失时回退实时并报 `snapshot_index_missing`）；严格模式只由员工执行入口设置，浏览器请求不能指定。

**追问：为什么员工入口比开放 API 更严格？** 员工看到的答案会被当成组织的正式口径；开放 API 调用方能读 `degraded` 自行决策，员工界面上一个降级标记很可能被忽略。

### P069 引用编号和页码有什么讲究？

> 标签：引用 ｜ 难度：★★

**参考回答**

- 引用数组先保留本轮检索的原始顺序与数量，正文 `[1]` 对应第一个本轮条目；**即使条目重复也不能去重压缩**，否则后续编号全部错位。历史继承的依赖追加在后并标 `inherited=true`，不分配本轮编号。
- `page_no` 只接受真实 PDF 页码；DOCX、表格、网页的逻辑分段不冒充物理页码。
- `chunk_title` 是切片元数据里的标题（可能由语义切分生成），不能标成原文章节标题；`chunk_ordinal` 是片段顺序，不等于原文自然段号。
- 引用只保存稳定的文档、版本、片段标识与可核实的定位信息，**不保存会过期的预签名 URL**。

一句话：**引用是给人核实用的，任何「看起来像但不是」的信息都会让核实失败。**

### P070 员工能用哪些应用？`app:use` 为什么要和 `app:read` 分开？

> 标签：权限、多租户、长任务运行时 ｜ 难度：★★

**考察点**：「管理权」与「使用权」的分离，以及目录不是授权凭证。

**参考回答**

普通员工使用正式应用需要两样东西：功能权限 `app:use`，加上角色上的**应用使用范围**（指定应用，或「本租户全部应用」，后者包括以后新建的应用）。`app:read`、`app:write`、`app:release`、`search:debug` 服务管理或调试，**都不自动推导出使用权**。

分开的理由：管理员能看配置，不等于该以员工身份在正式应用里提问；反过来，员工不该因为能用应用就看到提示词和模型配置。

员工目录 `GET /api/v1/workspace/apps` 只返回当前可用的正式应用，判定条件是：租户存在且启用、应用根属于该租户、有正式版本、**所有关联知识库**都在当前用户范围内。

两个关键约束：

1. **目录不是授权凭证**：建会话、提问、读历史都要独立执行当时的资源授权。
2. **目录重新读库**：用只读可重复读事务装配一致的主体快照，不读写权限缓存；旧缓存缺少 `appIds` 字段视为未命中，防止用缓存里的旧范围放行。

**追问**：「多角色怎么合并？」功能权限和各类数据范围分别取并集。只提交 `app_ids` 而不声明范围模式，返回 400；更新请求整体省略这两个字段，则保留原范围，兼容旧客户端。

**代码锚点**：`EMPLOYEE-APP-ACCESS.md`、`RoleAppScopeService`、`V27__employee_app_usage_scope.sql`

### P071 员工的「有帮助 / 需改进」反馈怎么设计？为什么不直接生成评测用例？

> 标签：运营闭环、评测集、并发 ｜ 难度：★★ ｜ 关联：P079

**考察点**：反馈的归属、并发与数据质量边界。

**参考回答**

- **归属到具体运行**：反馈挂在本人的某一次运行上，天然携带应用版本、原问题和证据关联。
- **只有 `SUCCEEDED` 可评价**：停止、失败、中断、执行中的运行都不能评价。
- **并发控制**：请求带 `expected_revision`。相同内容的重试直接返回原结果（幂等）；用旧修订号提交不同内容返回 `409 FEEDBACK_VERSION_CONFLICT`，页面保留编辑内容，用户核对最新反馈后再改，避免多标签页静默覆盖。
- **最小写入**：只改反馈字段、更新时间和行修订号，不动答案、引用、运行状态、会话活动时间或模型上下文。
- **授权**：需要 `app:use`、应用范围、本人会话归属，以及当前证据仍可读；受限视图的 `feedback` 为空。说明最多 512 字符。

**不直接生成评测用例**，是因为 BAD 反馈只说明「这次不好」，不说明「什么是对的」。BAD 分片不能当正确证据，必须经过质量问题流程，由人补全标准答案和正确证据，再用真实回归验证（见 P079）。

### P072 评测集怎么建？

> 标签：评测集 ｜ 难度：★★ ｜ 关联：P079

**参考回答**

- **span 锚定，不绑 chunk_id**：每条用例是 query + 可选标准答案 + 证据（文档 + 原文片段）。换切分策略后评测集照样能用——这是能拿评测集去比较切分参数的前提。
- **跨版本**：证据锚定 `doc_id`（跨版本稳定），同时记录标注时的版本号作溯源；文档更新后证据在激活版本里匹配不到，用例标 `evidence_stale`、单列统计、**不计入未命中**；文档被彻底删除，用例直接 deprecated。
- **图片用例**用文档级锚定：Top-K 里出现该图片衍生的任一分片即命中。
- **多轮用例**带 `messages`，评测走完整的多轮改写链路，报告按单轮 / 多轮分组。
- **期望拒答用例**：专门测拒答策略。
- **来源**：检索调试页一键「收进评测集」（自动携带会话历史）；GOOD 反馈可转用例（BAD 不可转——负反馈不构成正向证据）；质量问题闭环里的纠正用例（P079）；随部署分发的示例评测集。

### P073 命中判定为什么用「以 span 为分母」的重叠率？标注迁移为什么又用对称的 Dice？

> 标签：评测、指标 ｜ 难度：★★★

**考察点**：度量的方向性——很少有人想过。

**参考回答**

- **评测命中**问的是「返回的文本覆盖了证据吗」：重叠率 = 归一化后的字符交集 ÷ **span 长度**（固定以 span 为分母）；归一化去空白、折叠全半角、忽略脱敏掩码字符；Top-K 内多个单元对同一 span 的覆盖并集 ≥ 0.5 即命中。一个大 chunk 完整包含证据就应该是 1.0，所以它**天然是非对称的**。
- **标注跨版本迁移**问的是「新版本里哪个分片和旧分片是同一段内容」：用字符 3-gram 的 **Dice 系数** `2|A∩B| / (|A|+|B|)`，对称；阈值 0.35、只推荐 top 3、候选限于同一文档当前激活版本、短文本不推荐；只推荐 + 人工逐条确认，不自动迁移、不批量。

如果把评测的非对称指标拿去做迁移，任何一个大分片都会被判成「完全匹配」所有被它包含的小分片，迁移建议就全错了。需求文档专门写了一条：**评测重叠率不得复用于分片间相似度匹配**。

### P074 检索指标怎么算？K 指什么？

### P075 最终答案怎么评？

> 标签：评测、LLM-as-Judge ｜ 难度：★★ ｜ 关联：R36

**参考回答**：复用生产生成路径生成答案，独立 Judge 打五维分（正确性、忠实度、完整性、引用正确性、引用完整性，1–5 分制）+ 答 / 拒是否正确；Judge 失败保留空值、不折算 0 分，门禁只在双方 Judge 都成功的 case 交集上比较；Judge 模型可独立配置、有独立输出预算。详见 R36。

**追问：答案门禁为什么默认关闭？** 应用版本要显式开启 `answer_gate`，历史版本默认关闭。答案评测要多花一轮生成和一轮 Judge 的钱，且 Judge 有噪声；让它默认拦截发布，等于把一个概率性的评分器变成了强制关卡。先作为报告，积累足够的一致性证据后再由应用自行开启。

### P076 发布门禁怎么设计？

> 标签：发布门禁、评测 ｜ 难度：★★★ ｜ 关联：R38

**参考回答**

- 同语料、同时刻双跑（候选配置 vs 当前正式版配置），在双方共同判定的 case 交集上重算指标。
- `ReleaseGateJudge` 是纯函数，**检查顺序就是规格**：未绑定评测集 → 双跑失败 → 期间语料或评测集变化（不可比）→ 有效 case 少于 50 → 待复核占比超过 15% → 重试后仍有降级 case，这些都只记录不拦截；之后才比较指标：首发无基线走绝对阈值，否则候选 < 对照 − ε 才拦截。
- `ε = max(2pp, 1/N)`：N=50 时翻一个 case 恰好是 2pp；再留 `1e-9` 浮点余量，防止 `0.88 − 0.90 = −0.020000000000000018` 把恰好等于容差的情况误判为回退。
- 答案门禁（显式开启时）单独裁决，与检索结论按「非通过优先」合并；答案分容差 0.2。
- 三态：通过 / 拦截（可 force 放行并留痕）/ 仅记录（需人工确认发布并留痕）。

详见 R38。

**追问：门禁任务为什么不能和评测任务共用线程池？** 门禁要等它提交的两个评测 run 结束。同一个池里，门禁占着线程等 run，run 排在门禁后面等线程——自等待死锁。所以门禁池（4 线程）和评测池（6 线程）分开。

### P077 发布快照冻结了什么？回滚怎么做？

> 标签：版本管理、发布门禁 ｜ 难度：★★

**参考回答**

- **同时冻结两样东西**：各引擎的快照索引（ES 用 `_clone`，硬链接段文件、毫秒级；Qdrant 按游标分批拷贝点）和可见版本集。快照索引不挂别名、按物理名直查。**只冻结索引不冻结可见集**，正是早期「回滚后召回全空」缺陷的根源：回滚到旧版本时，旧快照索引配上当前可见集，版本对不上，全部被过滤掉。
- **时点**：晚于门禁双跑、早于 RELEASED 生效——保证门禁所测索引就是发布后所用索引。
- **回滚**：RELEASED 唯一（生成列 + 唯一索引），原正式版转 SUPERSEDED；回滚 = 把历史版本重新置为正式版。SUPERSEDED 的快照按保留数（默认 3）清理，RELEASED 永不清理；被快照引用的文档版本禁止归档。
- **例外**：分片禁用 / 启用属于全局质量止血，除实时别名外同步广播到该库所有生效的快照索引——快照不可变，但止血必须穿透。自愈、补偿、重建只作用于实时别名，防止跨索引误删。

### P078 评测结果怎么保证可复现？

> 标签：评测、一致性 ｜ 难度：★★ ｜ 关联：R39

**参考回答**：提交时用独立的 `REPEATABLE_READ` 只读事务一次读出评测集修订号与全部用例输入，存进运行的 `case_inputs`；用例编辑走乐观锁，冲突返回 `409 EVAL_DATASET_CONFLICT`；运行固化语料指纹、激活版本集、嵌入版本；评测线程带离线标记，不计入生产监控与洞察；卡死超过 120 分钟只改判 FAILED、不重跑。详见 R39。

**追问：为什么跨表快照一致性测试只在 MySQL 上跑？** H2 的 `REPEATABLE_READ` 能读到另一张表新插入的行，行为和 MySQL 不同；在 H2 上跑这个断言只会给出错误的信心。所以通用写入与回滚在 H2 测，跨表快照并发只在真实 MySQL 测。

### P079 线上用户点了「需改进」，怎么变成一次可验证的修复？

> 标签：运营闭环、评测 ｜ 难度：★★★

**参考回答**

```
BAD 反馈 / 零命中 → 建质量问题（同一来源复用） → 领取
→ 填写原因、完整问题、标准答案与正确证据 → 形成纠正用例（待回归）
→ 执行包含该用例的最终答案评测
→ 人工对照标准答案、实际答案、五维评分，写核验说明 → 确认解决
```

「确认解决」在同一事务里重新核验，不依赖前端预览或运行的 SUCCESS 状态：用例输入、运行冻结输入与当前用例一致；验证版本属于受影响应用，配置与运行快照一致，语料指纹未变；正确证据仍可检索、版本与标注一致；有有效答案、答 / 拒行为正确、无降级、五维各达到 4/5；正常回答的标准证据全部命中；人工说明非空。

### P080 评测的配置矩阵有哪几种模式？为什么不给评测单独写一条检索链路？

> 标签：评测、成本、检索 ｜ 难度：★★ ｜ 关联：P048

**考察点**：评测与线上行为一致性，以及评测成本护栏。

**参考回答**

`EvalMode` 四种：`BM25_ONLY`、`VECTOR_ONLY`、`HYBRID`（融合、不重排）、`HYBRID_RERANK`（融合 + 重排）。一次提交最多 6 个配置（`evalTaskExecutor` 核心线程 6，低于它会把「一个动作」的矩阵悄悄串行化），报告按配置横向对比。

- **复用生产链路**：每种模式只是映射成 `RetrievalCommand` 的参数（开关哪几路、要不要重排），评测执行器对所有模式都调同一个 `RetrievalService`。复制一套检索链路给评测，两者迟早漂移，评测通过就不再代表线上。
- **零 Key 时快速失败**：需要向量的模式在零 Key 部署中直接置 FAILED 并说明原因，**不静默退化成 BM25 结果却标着「向量」或「混合」**。
- **费用护栏**：提交前调 `POST /api/v1/eval-datasets/{id}/runs/estimate`，分别预估嵌入、重排、改写、Judge 的调用次数。
- **离线档**：超时放宽，降级用例自动重试，不计入生产监控。

**追问**：「答案评测也复用生产 Prompt 吗？」是。离线答案评测把矩阵实际召回的节点原样交给 `AnswerGenerationService`，防止门禁测到一条线上永远不会执行的「近似 Prompt」（见 P048）。

**代码锚点**：`EvalMode`、`EvalRunService`、`M4b-CONTRACTS.md`

### P081 文档更新后评测证据失效了怎么办？证据复核工作台怎么工作？

> 标签：评测集、版本管理、治理 ｜ 难度：★★

**考察点**：评测集的维护成本控制。

**参考回答**

1. **切换前预告**：激活新版本前，`activate-impact` 返回 `affected_eval_case_count`，确认框提示「将有 N 条评测用例进入待复核」。
2. **切换时同步扫描**：锚定该文档的全部 span 级用例，证据在新激活版本里匹配不上的，标 `evidence_stale`。

### P082 应用版本的状态机是怎样的？单应用为什么只能有一个 RELEASED？

> 标签：发布门禁、版本管理、一致性 ｜ 难度：★★

**考察点**：发布流程建模与数据库层不变量。

**参考回答**

```text
DRAFT → TESTING → GATING → GATE_PASSED   → RELEASED → SUPERSEDED
                        ↘ GATE_LOG_ONLY → （force 留痕放行）→ RELEASED
                        ↘ GATE_BLOCKED
回滚：历史 RELEASED / SUPERSEDED 版本重新 release
```

- **提交测试**（`submit-test`）：DRAFT → TESTING，测试版可以被显式调用做灰度。
- **发布**：绑定门禁评测集时进入 GATING，同语料双跑；通过则 RELEASED，原正式版变 SUPERSEDED。
- **LOG_ONLY 四种情况**：未绑评测集、有效用例少于 50、重试后仍含降级用例、待复核占比超过 15%。这时不自动发布，需要 `release?force=true` 留痕放行。
- **SUPERSEDED 不可被对外调用**，返回 `404 VERSION_NOT_FOUND`。

**唯一 RELEASED 靠数据库保证**：虚拟列加唯一索引，应用层并发发布也不可能出现两个正式版（实现期在临时库实测触发 1062 唯一键冲突）。发布和回滚都是原子状态切换。

**追问**：「首发没有对照怎么判？」配置了绝对阈值就与阈值比，否则记录基线并放行。

**代码锚点**：`M4c-CONTRACTS.md`、`AppVersionService`、`ReleaseGateService`、`ReleaseGateJudge`

### P083 测试版灰度怎么调？灰度流量和正式流量怎么区分？

> 标签：发布门禁、版本管理、可观测 ｜ 难度：★★

**考察点**：灰度的语义边界，尤其是语料版本。

**参考回答**

开放 API 的 `app_version` 缺省路由到当前 RELEASED；显式传测试版版本号即可调用 TESTING 版做灰度，审计标 `target_stage=beta`，控制台的量统计不会把灰度和用户真实看到的流量混在一起。

要讲清楚的边界：**测试版没有快照**。快照只在正式发布时创建，所以测试版灰度、管理台调试、评测这些无快照上下文，读取的是 MySQL 里**当前激活**的文档版本。灰度验证的是「新配置 + 当前语料」，不是「发布后冻结的那份语料」。

**追问**：「M6 之前发布的历史正式版没有快照怎么办？」兼容回退为当前激活版本，不记降级；员工运行会明确标 `snapshotBound=false`，界面必须显示真实语义。

**代码锚点**：`TargetStage`、`KnowledgeCallCommand.appVersion`、`RetrievalIndexContextResolver`

### P084 两个应用版本到底差在哪？版本差异功能怎么设计？

> 标签：版本管理、权限、发布门禁 ｜ 难度：★★

**考察点**：「无法比较」与「没有差异」的区分，以及权限对统计口径的影响。

**参考回答**

版本差异只读，比两件事：

1. **配置**：关联知识库及权重、检索参数、模型、提示词、路由、门禁参数与门禁评测集绑定。对象属性顺序不算差异；知识库顺序保留（首个库可能提供默认配置）；零值、关闭、空文本、未设置分别显示。
2. **资料**：`GET /api/v1/app-versions/{id}/corpus-diff?baseline_id=...`，集合来源有四种：
   - `FROZEN`：版本保存的发布资料集合，显式空列表是合法空集。
   - `CURRENT`：未发布版本引用知识库的当前活动集合，尚未冻结。
   - `EMPTY`：用户选择无对照。
   - `UNAVAILABLE`：历史集合缺失，**不能用当前集合补写历史**。

任一侧元数据不完整时 `comparable=false`，数量未知，不返回推断的差异条目；权限不足或接口失败显示可重试错误，**绝不显示「无差异」**。

权限：需要 `app:read`、`kb:read`、应用数据范围与两侧全部知识库范围；文档 ACL 在统计和分页**之前**裁剪，无权读的资料不影响数量。响应只含文档名、版本和增删替换标记，不含正文和存储地址，禁止缓存。

**代码锚点**：`APP-VERSION-DIFF.md`、`AppVersionComparisonService`、`api/appVersionComparison.ts`

### P085 评测排队期间有人改了用例，结果还可信吗？

> 标签：评测、一致性、事务 ｜ 难度：★★★

**考察点**：评测输入的快照一致性，以及测试数据库与生产数据库的隔离级别差异。

**参考回答**

可信，因为评测提交时就冻结了输入：

1. **写侧**：用例的增删改和证据复核，与评测集修订号、计数同事务提交；乐观锁未命中时显式检查零行，返回 `409 EVAL_DATASET_CONFLICT` 并整体回滚。删除也携带读取时的用例版本，防止按旧状态误删。
2. **提交时**：用一个独立的 MySQL `REPEATABLE_READ` 只读事务，在同一数据库视图下读出集合修订号与全部用例输入；事务在模型调用前结束，同批配置共用这份输入。
3. **运行记录**：`case_inputs` 保存问题、多轮上文、标准答案、拒答期望、证据、锚点类型和当时状态，不含运营备注。执行器从快照恢复，不重读当前用例表。
4. **旧数据**：缺少输入快照的旧待执行运行明确失败并要求重新提交，**不拿现在的用例附会历史输入**。

**追问**：「为什么跨表快照测试只在真实 MySQL 上跑？」H2 的 `REPEATABLE_READ` 能读到另一张表新插入的行，与 InnoDB 的一致性读语义不同，在 H2 上断言会得出错误结论。

**边界**：输入快照只证明「用了哪些用例」，不等于冻结了检索索引，也不能单独证明问题已解决。

**代码锚点**：`EVALUATION-INPUT-CONSISTENCY.md`、`EvalDatasetConcurrencyTest`、`V30__evaluation_case_inputs.sql`

### P086 多租户模型怎么设计？

> 标签：多租户、权限 ｜ 难度：★★

**参考回答**

- `tenant_id` 只加在**根聚合表**（用户、角色、知识库、API Key、评测集、应用，后续补上记忆库与站点凭据），从属资源经根归属租户——避免出现第二个可以不一致的事实源。

### P087 你们踩过什么越权漏洞？怎么系统性修掉的？

> 标签：权限、安全、踩坑 ｜ 难度：★★★

**考察点**：安全问题的根因分析能力。

**参考回答**

踩过一整族。典型形态：从属表（网页源、文档、分片、标注、评测集、外部数据源、反馈……）不带 `tenant_id`，按从属 id 直接寻址的入口前面只有一个「数据范围守卫」，它回答的是「这个库在不在你的数据范围里」，一行租户判断都没有，而且对租户内超管、未配数据范围的库管理员直接短路放行。结果是 43 个控制台端点可以跨租户操作，包括覆写别家外部数据源的 AK/SK、硬删别家登记、把别家文档回滚到旧版本。

根因有两层：

1. **只覆盖数据范围的守卫比没有守卫更危险**——它让 code review 以为这条路径已经守住了。
2. **围栏只保护它实际发出的语句**。守卫里一个提前 `return`，连同后面已经写好的围栏查询一起跳过，而这种失败在方法体里看不出来，因为围栏是拦截器。

修法：守卫重命名为 `KbResourceGuard`，9 个方法一律先解析围栏根表；另外 15 个「路径里自带 `kbId` 却从不查根表」的入口，修复落在服务层方法首行（服务方法是所有调用方的必经之路）。判据只有一条：**这条链路上有没有一次对根表的查询？没有就是未守，哪怕路径里带着 `kbId`**——那是调用方声明的作用域，不是被证实的作用域。还有一条更细的：「从属行属于这个父」和「这个父属于你」是两个问题。

### P088 越权为什么返回 404？判定顺序有什么讲究？

> 标签：权限、安全 ｜ 难度：★★

**参考回答**

- 404 而不是 403：403 告诉调用方「这个 id 存在，只是你不能碰」，这本身就是信息泄露。
- **租户（404）先于数据范围（403）**：反过来，别家租户的 id 会先吃到 403，状态码差异就泄露了存在性。
- **404 要连措辞一起收**：应用版本守卫让「跨租户」与「版本不存在」共用同一个错误码、同一段文案，文案里不含 `appId`；第二跳如果报成 `APP_NOT_FOUND`，就等于用错误码差异告诉调用方「你猜的 id 是真的，只是在别人那里」。

### P089 RBAC 怎么设计？

> 标签：权限 ｜ 难度：★★

**参考回答**

- 权限码目录全局共用：`kb:read/write/delete`、`doc:write/review`、`search:debug`、`feedback:manage`、`eval:read/write/run`、`app:use/read/write/release`、`apikey:manage`、`audit:read`、`system:config`、`user:manage`、`role:manage`、`tenant:manage`、`memory:read/write`。
- 五个内置角色：SUPER_ADMIN / KB_ADMIN / EDITOR / REVIEWER / VIEWER；自定义角色被引用时拒删。
- 三类范围：功能权限码、知识库数据范围、应用使用范围；多角色时各自取并集。
- **管理权不推导使用权**：`app:read/write/release` 不自动授予 `app:use`，员工使用正式应用必须单独授权。
- 控制台端点全量标注 `@RequiresPermission`，无权限返回 403 PermissionDenied（与开放 API 的 Forbidden 区分）。
- 权限缓存写时失效，不靠 TTL 穿透。

**追问：升级到 RBAC 时，存量账号怎么办？** 自动授予 SUPER_ADMIN，否则升级后没人能进用户管理页。收敛成最小权限是运维职责，系统每次启动**逐租户**检查超管人数，超过 1 人就 error 日志点名——**只提醒不自动降级**，自动降级总会在某个部署上选错幸存者。

### P090 会话和权限缓存为什么必须用同一个开关？

> 标签：缓存、权限 ｜ 难度：★★

**参考回答**

`KB_CACHE_PROVIDER` 同时决定会话和权限缓存的存放位置（`local`：会话落 MySQL、权限缓存在进程内；`redis`：两者都进 Redis）。只共享会话不共享权限，会得到「登录态跨节点一致、授权判据不一致」——某个刚被降权的账号在某个节点上还是管理员，比两者都不共享更难察觉。

三个细节：

1. **共享存储，不是「本地缓存 + 失效广播」**：广播是尽力而为的，某节点重连时丢一条失效消息，它就一直用着旧授权；共享存储下失效就是一次删除，要么成功要么报错。
2. **读写失败降级，失效失败上抛**：读不到回落数据库仍然正确，写不进下次再查；失效失败意味着旧授权还在，必须抛异常让调用方事务回滚（6 处调用点都在 `@Transactional` 方法里、DB 写入之后）。
3. `evictAll` 用 SCAN 而不是 KEYS，避免一次角色编辑阻塞和会话共用的 Redis。

### P091 单点登录支持哪些？有什么安全细节？

> 标签：认证、安全 ｜ 难度：★★

**参考回答**

- **LDAP**：裸 JNDI simple bind，不引入 Spring LDAP；域账号首登自动建号、授默认角色（VIEWER，只读——更宽就等于把写权限发给所有有域账号的人）。组同步开启后每次登录按「组 DN = 角色」映射，**只全量替换 LDAP_SYNC 来源的授权，手工授权永不触碰**；零命中回退默认角色，不产生无角色账号。
- **OIDC / SAML 2.0 / CAS**：各自独立开关。令牌通过 302 到 `{web-base-url}/login#sso_token=...` 的 **URL fragment** 交付——fragment 不进服务器日志和 Referer，前端解析后立即清地址栏。
- **SAML 不引入框架库**，在 JDK 的 XMLDSig 上实现：信任判断只有一条——配置的 IdP 证书是否签了**身份被读取的那个元素**；签名引用必须覆盖 Response 或 Assertion 的 ID，防止合法签名的断言被塞进攻击者构造的外壳；再校验 NotOnOrAfter、Audience、InResponseTo，允许 60 秒时钟偏差；XML 解析禁用 DOCTYPE 与外部实体。

**追问：自己实现 SAML 验签，还要防什么？** 签名包裹（XSW）类攻击的核心是「验签的元素」和「读取身份的元素」不是同一个，所以要同时保证引用覆盖被消费的元素、且该 ID 在文档中唯一（XMLDSig 的安全校验模式会检查重复 ID）。能讲到这一层，说明真的理解 SAML 的攻击面。

### P092 API Key 怎么设计？

> 标签：认证、安全 ｜ 难度：★★ ｜ 关联：P103

**参考回答**

- 一把 Key 三形态：明文只在创建时返回一次；库里只存 SHA-256 摘要用于鉴权；前缀用于展示。
- 授权范围：全部应用或指定应用列表，越权 403 `APP_ACCESS_DENIED` 并记审计。
- 限流：每 Key 一个进程内令牌桶，默认 10 QPS，超限 429 + `Retry-After`。
- 审计：异步落库，query 摘要无条件脱敏并截断到 200 字符；401 不落审计（没有可归属的 Key，落库只会让垃圾请求灌爆审计表），403 与 429 落；保留 180 天后归档到对象存储再分批物理删除。
- 请求级覆盖只放 4 个响应形态参数，越界拒绝而不是忽略——忽略会让调用方以为自己的参数生效了。

**追问：`last_used_at` 为什么异步写？** 每次鉴权同步写一次库，等于在每个请求路径上加一次写事务。这里还踩过坑：`@Async` 标在同一个 bean 的方法上，自调用不经过代理，注解静默失效，每次认证都在请求线程上同步写库（P103）。

### P094 登录滑块验证码怎么设计？为什么验证码失败不计入账号锁定？

> 标签：安全、认证 ｜ 难度：★★★

**考察点**：低成本自动化门槛的完整威胁模型，而不是「做了个拼图」。

**参考回答**

流程：`challenge`（服务端生成带缺口的随机背景与拼图片，**不返回横向答案**）→ 浏览器采集一次滑动轨迹 → `verify`（服务端校验落点、单调时钟实测耗时与轨迹，签发短时一次性 proof）→ `login` 携带 proof，原子消费后才校验账号密码。

关键设计：

- **只存摘要**：challenge 和 proof 都是 32 字节随机数，服务端只保存 SHA-256 摘要，放在有容量上限和 TTL 的进程内缓存里。
- **先消费再判断**：可识别的 challenge 在拼图、轨迹、限流判断**之前**原子消费；登录在校验密码之前消费 proof。失败后重放同一个值必定失败。
- **请求体硬上限**：Jackson 反序列化之前，`verify` 限 32KB、`login` 限 8KB，覆盖错误的 `Content-Length`、chunked 和 HTTP/2；字段层再限用户名 128、密码 512、proof 固定 43 字符。
- **验证码失败不进登录审计**：匿名请求刷验证码不应导致真实账号被锁定；真实凭据失败才走「5 次锁 15 分钟」。
- **防时序枚举**：未知账号也执行一次固定的 dummy BCrypt 校验。

**边界**：它不替代账号锁定、网关限流或 WAF。状态都是进程内的，多实例要粘性路由，严格的全局额度必须迁到 Redis 或数据库。

**代码锚点**：`LOGIN-CAPTCHA-CONTRACT.md`、`LoginSliderCaptcha.tsx`

### P095 客户端 IP 怎么取？`X-Forwarded-For` 为什么不能直接信？

> 标签：安全、认证、审计 ｜ 难度：★★

**考察点**：代理链下的来源地址可信度。

**参考回答**

`X-Forwarded-For` 是请求头，任何客户端都能伪造。直接信它，攻击者每次换一个 IP 就能绕过按来源的限流和登录锁定，审计里的来源地址也会被伪造。

项目的规则：**只有 socket peer 命中 `TRUSTED_PROXY_CIDRS` 时才读取 `X-Forwarded-For`**，并从右向左剥离可信代理，取第一个不可信地址作为客户端地址。直连或来源不在白名单时，转发头一律忽略。默认只信任本地 Vite 开发代理的回环地址，生产必须换成实际网关 CIDR，**禁止配置 `/0`**。

验证码 challenge / proof 绑定、口令登录、浏览器 SSO 审计共用这一处统一解析的地址，避免各处取法不一致。

**追问**：「为什么是从右向左？」每一跳可信代理都把它看到的对端追加到头部末尾，所以越靠右越可信；从右边剥掉自己人，剩下的第一个就是可信链路之外的真实来源。从左取第一个，拿到的是客户端自己填的值。

**代码锚点**：`LOGIN-CAPTCHA-CONTRACT.md` §2、客户端地址解析器

### P096 「记住用户名和密码」怎么做才安全？

> 标签：安全、前端 ｜ 难度：★★

**考察点**：前端存储在 XSS 威胁下的等价性。

**参考回答**

应用只在 `localStorage` 保存「是否记住」和各登录方式的用户名，**从不保存密码**。密码框保持标准的 `autocomplete="current-password"`；用户勾选后，在认证成功后调用 Credential Management API，把凭据交给浏览器或系统的密码管理器保存。

不能把密码明文、Base64 或用前端可得密钥加密后写进 `localStorage`、`sessionStorage` 或 IndexedDB：页面一旦有 XSS，这些做法都**等价于明文持久化**，因为攻击脚本和解密代码运行在同一个源里。

另外两个细节：上次成功的登录方式（`LOCAL` / `SSO`）单独记在 `kb-rag.login-method.v1`，不含身份和凭据；切换登录方式会清空密码并刷新验证码。

**代码锚点**：`LOGIN-CAPTCHA-CONTRACT.md` §4、`AUTH-ENTRY-EXPERIENCE.md`、`api/authStorage.ts`

### P097 邮箱自助注册怎么防止绕过管理员审核？

> 标签：安全、认证、幂等 ｜ 难度：★★★

**考察点**：「证明邮箱归属」与「获得系统权限」的分离，以及公开接口的滥用防护。

**参考回答**

M26 的核心不变量：**申请成功不签发 token，也不在账号表留下待激活账号**。正式账号、租户归属与角色只由管理员审核事务创建，审核前不存在可登录的账号生命周期。

公开端只有三个精确 POST 免登录：

1. **发验证码**：先原子消费绑定 IP 与 User-Agent 的滑块 proof，再按邮箱、IP、单实例全局三层限流。
2. **验证邮箱**：锁定验证行，常量时间比较验证码 HMAC；成功后返回**一次**明文注册票据，库里只存 SHA-256。
3. **提交申请**：请求不再接收邮箱，只从票据锁定的验证行取已验证邮箱；保存 PENDING 申请和消费票据在同一事务。浏览器为一次提交生成稳定的 `client_submission_id`，响应丢失后同标识同票据重试返回原回执，换票据被拒。

其他细节：

- 验证码明文只存在于调用栈和即时邮件中；错误验证码在独立事务里先扣减次数，业务异常不能回滚掉次数。
- 邮箱已被占用时走相同的加锁、HMAC 与次数状态机，只是邮件提示已有账号，缩小账号枚举的时序侧信道。
- 密码至少 12 字符、UTF-8 不超过 72 字节（防止 BCrypt 静默截断）；BCrypt 在事务外有并发为 2 的非等待舱壁，拿不到槽位直接 429。
- 审核需要 `user:manage` 与 `tenant:manage` 同时满足；授予的角色写入不可变快照，账号日后调权不改写历史审核事实。

**代码锚点**：`M26-CONTRACTS.md` §1–§2、`V26__email_registration.sql`

### P098 审核结果邮件为什么走 outbox？多实例下怎么防重复发送？

> 标签：一致性、幂等、并发 ｜ 难度：★★★ ｜ 关联：P104

**考察点**：事务与外部副作用的解耦，以及 at-least-once 的诚实边界。

**参考回答**

如果在审核事务里直接发 SMTP，邮件服务短暂故障会回滚已经创建的账号或审核结论；如果事务提交后再发，进程崩溃又会丢通知。outbox 的做法是：**通知行与审核事实在同一事务写入 `t_kb_mail_outbox`**，提交后由派发器发送。

派发器三段式：

1. 短事务里用 `FOR UPDATE SKIP LOCKED` 选取到期行，用 `next_retry_at + lock_version` 领取一个有界 lease。
2. 事务提交后才执行 SMTP，慢 SMTP 不持有行锁或数据库连接。
3. 另起短事务，按 lease 版本 CAS 为 `SENT` 或 `FAILED`。

多实例不会在有效 lease 内重复领取。失败按指数退避，达到上限保留 `FAILED` 行供排查。默认单轮 50 封、最多 5 次、基础退避 60 秒、lease 60 秒、每 5 秒调度一次。

**诚实的边界**：SMTP 已接收而进程在标记 `SENT` 之前崩溃，lease 过期后可能再发一次。不引入分布式事务时，这就是 at-least-once。outbox 只承载审核结果，不承载验证码或票据。

**追问**：「这和不上调度平台的决策矛盾吗？」不矛盾。这是一个局部不变量：单一任务类型、天然需要多实例安全，用数据库领取就够了；通用调度平台的立项门槛见 P104。

**代码锚点**：`M26-CONTRACTS.md` §3–§4

### P099 操作审计怎么做？「谁」是怎么拿到的？

> 标签：审计、合规、并发 ｜ 难度：★★

**考察点**：切面审计与异步落库的线程边界。

**参考回答**

M16 用 `@AuditedOperation(module, action, targetType)` 注解加 `OperationAuditAspect`（`@Around`）覆盖全部管理台写操作。方法**成功返回后**，从 `UserContextHolder` 取主体，用 SpEL 从路径变量或返回值里取业务 ID，再取 `HttpServletRequest` 的客户端 IP 和 `request_id`，然后 `@Async` 落库 `t_kb_operation_audit`。

关键纪律：**主体信息必须在请求线程里取完再交给 executor**。异步线程没有请求上下文，也拿不到 `ThreadLocal` 里的用户，到那边再取就是空的，或者是线程池里上一个请求残留的用户。

表结构带 `tenant_id`、`user_id`、`username`、`module`、`action`、`target_type`、`target_id`、`detail` JSON、`client_ip`、`request_id`，按租户 + 时间、用户名、目标、创建时间建索引。默认保留 180 天，与 API 审计一致，由保留期清理扫 `created_at`。

**追问**：「和开放 API 审计有什么区别？」开放 API 审计记的是 Key 维度的调用（query 只存脱敏摘要、覆盖参数键、目标阶段）；操作审计记的是控制台用户的写操作。两者都不存查询原文。

**代码锚点**：`OperationAuditAspect`、`M16-CONTRACTS.md` §7

### P100 监控端点怎么暴露才安全？为什么不复用控制台 Token 保护 Actuator？

> 标签：安全、运维、可观测 ｜ 难度：★★

**考察点**：运维平面与业务平面的隔离。

**参考回答**

Actuator 放在独立监听器上：`MANAGEMENT_SERVER_PORT=20003`，`MANAGEMENT_SERVER_ADDRESS=127.0.0.1`，只暴露 `health`、`info`、`prometheus`。`health` 只返回聚合状态，不返回 MySQL、ES、MinIO、Qdrant、Neo4j 的组件名、地址和失败详情。访问业务端口 `20000` 的 `/actuator/health` 应该得到 404。

需要远程抓取时，显式改监听地址，同时必须：防火墙只放 Prometheus 固定来源；不发布到公网；跨不可信网络走带 TLS 和认证的反向代理，且只转发 `/actuator/prometheus` 与必要的健康路径；管理端口不能和业务端口相同。

**不复用控制台 Token**：监控采集器不是控制台用户，把两类凭据放进同一认证链，会扩大控制台 Token 的分发范围。远程采集的认证与来源限制应该收敛在运维网络或反向代理这一层。

**代码锚点**：`ACTUATOR-SECURITY.md`

### P101 模型配额怎么控制？

> 标签：成本、并发 ｜ 难度：★★★

**参考回答**

- **计量位置在 Provider 的 HTTP 出站边界**：对话、嵌入、重排、视觉、多模态嵌入五类调用全部经过这里，没有第二个入口可以漏记；适配器不知道数据库细节。
- **先预占后使用**：请求前按输入与输出预算的保守上界，对「租户 × 月份」计数器做原子条件 UPDATE；配额不足直接 429 `MODEL_QUOTA_EXCEEDED`。
- **结算**：明确的上游失败才释放；供应商已返回但没给 usage 的，按预占上界结算并标 estimated；解析业务响应失败也不释放已结算的消费。
- **崩溃恢复**：每小时第 5 分钟扫描超过 60 分钟仍 RESERVED 的台账，按预占量保守结算（记 FAILED + RESERVATION_EXPIRED + estimated）；台账乐观锁保证多实例重复扫描只有一个成功；批内任何计数更新失败整批回滚。
- **成本**：按价格快照计算、按币种分别汇总，不做汇率换算；缺价格显示「未定价」，不当成零。

**追问：踩过什么坑？** 预占事务里先 `INSERT IGNORE` 建计数行、再条件 `UPDATE`：行已存在时 `INSERT IGNORE` 在唯一键上拿 S 锁，`UPDATE` 要 X 锁，两个并发预占各持一把 S 锁互等升级，InnoDB 判死锁。修法是条件 `UPDATE` 先行，影响 0 行才建行（`1fdfe58`）。教训：**并发写同一批行时，所有事务必须以相同顺序、从一开始就拿最终需要的锁。**

### P102 线程池怎么配？有什么规则？

> 标签：并发、性能 ｜ 难度：★★★

**参考回答**

**池形状只有一条规则：要么队列为 0，要么 core == max。** `ThreadPoolTaskExecutor` 只有队列**满了**才会扩容到 max，所以「深队列 + 更大的 max」里的 max 永远到不了——写下的上限是个不会发生的数字。这条踩过两次：索引池 `core=2,max=4` 挂 200 深队列，常年只有 2 个线程；评测池 `core=2,max=6` 挂 50 深队列，常年只有 2 个，而它的注释写着「6 个 run 并行」。现在有测试用反射遍历全部线程池 Bean 钉住这条规则。

| 池 | core / max / queue | 为什么 |
| --- | --- | --- |
| 检索 | 4 / 16 / 0 | 宁可快速降级不排队，先吸收突发再拒绝 |
| 流式生成 | 2 / 16 / 0 | 排队的流 = 客户端盯着没有首 token 的连接 |
| 索引 | 4 / 4 / 200 | 刻意小 + 有界队列，防饿死控制台 |
| 嵌入 | 4 / 4 / 500，CallerRuns | 全局嵌入并发上限，满了回压提交者 |
| 评测 run / case | 6 / 6 / 50；4 / 4 / 500，CallerRuns | 6 = 一次提交的配置矩阵上限；case 并发是全局上限而非每 run |
| 门禁 | 4 / 4 / 20 | 必须与评测池分离，防自等待死锁 |
| 审计 | 1 / 1 / 2000 | 异常只记日志绝不上抛 |

### P103 `@Async` 踩过什么坑？拒绝策略怎么选？

> 标签：并发、踩坑 ｜ 难度：★★

**参考回答**

**自调用失效**（`32f0a3c`）：Spring 的 `@Async` 基于代理，同一个 bean 内部的自调用不经过代理，注解静默失效、在调用线程上同步执行。当时五处受影响：整个评测矩阵阻塞在 HTTP 提交线程上、评测池空转；门禁的两次评测加轮询全压在发布请求线程上；每次 API Key 认证都在请求路径上同步写一次库。修法是注入 Executor 显式提交——不走 self 注入，也不拆 bean（拆出来会与评测服务互相依赖，Spring Boot 3 默认禁止循环引用）。补了三个断言「提交线程 ≠ 执行线程」的回归测试，退回自调用就变红。

**拒绝策略**：评测池与门禁池保留默认的 AbortPolicy，不换 CallerRuns——把整条评测 run 拽回提交它的 HTTP 线程，恰恰是上面修掉的形态。代价是 `execute()` 会抛异常，而两处提交都发生在「状态已落库之后」，所以兜底必须写在提交处：被拒的评测 run 就地改判 FAILED 并写明原因；被拒的门禁记 LOG_ONLY / RUN_FAILED——否则版本永久停在 GATING，而发布入口恰好拒绝从 GATING 再次发布，只能改库解锁。

**requestId 透传**：TaskDecorator 把 requestId 和计量上下文带到 worker 线程，并且**保存再恢复，而不是无条件清除**——CallerRuns 时任务回跑在提交者线程上，finally 里的清除会清掉提交者自己的 requestId，那条链路从队列满的那一刻起后半段全部断链。

### P104 为什么没有消息队列，也没有通用任务调度平台？

> 标签：架构、选型 ｜ 难度：★★★

**考察点**：架构演进是否由证据驱动。

**参考回答**

当前的异步全部是进程内线程池，跨存储一致性靠「状态表 + 定时补偿」。结论写在 `DURABLE-SCHEDULING-DECISION.md`：**当前不投入通用持久化调度，达到证据门槛再立项。**

理由：持久化调度解决的是「多个进程如何只领取一次、宕机后如何续租、重试如何不重复产生副作用」，不是把 `@Scheduled` 换成另一个框架。主服务以单实例为明确基线，真实数据没有证明重复调度、主节点切换时延或积压是主要约束；此时引入调度中间件，新增的是运维组件、租约状态机、幂等键、迁移与监控成本，收益无法验证。

立项触发器（满足「多实例部署」且至少一项运行证据）：生产稳定 ≥ 2 副本且滚动发布期间要继续接收任务；30 天内出现有证据的重复副作用；单实例任务排队 P95 超过 60 秒或积压持续 15 分钟高于并发 10 倍、且单机调参受限；明确提出 5 分钟内的任务接管 SLA。**「预计未来会扩容」不算证据。**

立项后的最小协议也先定好了：租约（lease_owner / lease_until / heartbeat）、幂等键、at-least-once、死信终态、计量上下文随任务持久化、双实例竞争领取与 kill -9 接管演练；**不承诺基础设施无法保证的 exactly-once**。

### P105 超时预算怎么分配？

> 标签：性能、降级 ｜ 难度：★★ ｜ 关联：R46

**参考回答**：每一级独立超时、独立降级（改写 800ms、重排 1.5s、嵌入 30s、生成读超时 60s、视觉 20s），而不是一个总超时——总超时只能告诉你「慢了」，不能只降级慢的那一级。超时包住整个调用，不只是 socket 读超时。评测走离线档，改写和重排的超时统一放宽到 10 秒，降级 case 自动重试 2 次，且不计入生产监控。详见 R46 第五步。

### P106 运维告警怎么设计？默认阈值是多少？怎么防止告警风暴？

> 标签：告警、可观测、运维 ｜ 难度：★★

**考察点**：告警信号的选择与降噪。

**参考回答**

三个触发器，走 Webhook：

| 触发器 | 默认值 | 语义 |
| --- | --- | --- |
| 任务失败 | `taskFailThreshold = 3` | **同一任务类型连续**失败 3 次；一次成功即清零 |
| 检索降级率 | `degradeRateThreshold = 0.3` | 最近 5 分钟窗口内降级占比超过 30%，且样本至少 20 条 |
| 双写积压 | `syncBacklogThreshold = 1000` | 待同步行总数超过 1000 |

设计要点：

- **连续而非累计**：入库几千个文件的库，累计失败数迟早越过任何阈值，告警就失去意义；同类型连续失败才说明依赖坏了。
- **滑动窗口而非计数器**：窗口是有界的时间戳队列（最多 1 万个样本），两个计数器永远忘不掉一个糟糕的小时，告警会在修复后长期锁存；空闲服务的窗口自然清空。
- **最小样本数**：两次检索一次降级就是 50%，毫无意义；样本下限防止重启后第一条查询就把人叫醒。
- **定时采样**：降级率和积压每 60 秒评估一次，不在检索路径上触发，告警不会拖慢检索。
- **静默窗口 30 分钟**：同一类别冷却期内不重复发送，否则告警通道会变成没人看的噪声。
- **告警通道不可用不是事故**：URL 为空或投递失败都降级为 error 日志，监控缺口不能变成线上故障。

**代码锚点**：`AlertConfig`、`TaskFailureTracker`、`RetrievalDegradeMonitor`、`AlertEvaluator`、`AlertService`

### P108 一次请求怎么串起全链路日志？

> 标签：可观测 ｜ 难度：★

**参考回答**

`request_id` 在入口过滤器生成（或采用调用方的 `X-Request-Id`）→ 进 MDC → 写响应头 → 透传给解析服务和模型 Provider 的调用日志 → TaskDecorator 带进异步线程。日志规范：只有 info / error 两级、英文、error 带错误码占位符。

**追问：`request_id` 能当凭据用吗？** 不能。开放 API 反馈端点接受 `request_id` 来关联当次检索，但它是调用方可自选的关联 id，所以端点还要校验那次检索的应用在本 Key 授权范围内、`chunk_id` 属于那次检索的知识库——否则任何持合法 Key 的应用拿到别人的 `request_id` 就能给自己无权访问的库写反馈。

### P109 检索洞察为什么记在 API 边界，而不是检索服务内部？

> 标签：可观测、运营闭环 ｜ 难度：★★

**参考回答**

评测运行与发布门禁复用同一条检索链路，埋在链路内部会把离线跑的几千次调用污染进「用户在搜什么却搜不到」的报表。所以记录点放在管理台检索与开放 API 的边界，异步写入、失败只记日志；预览不记；被拒绝的调用不记（审计已覆盖）。

隐私口径：只存脱敏后截断到 200 字符的摘要，绝不存原文；`query_hash` 是归一化（trim、小写、折叠空白）后的 SHA-256，用作未命中分组键；保留 90 天直接删除，不做归档——它是统计，不是证据。

### P110 备份恢复怎么做？

> 标签：运维 ｜ 难度：★★

**参考回答**

- 备份：`mysqldump --single-transaction` 全量 + ES `_snapshot` + MinIO `mc mirror`，汇总 manifest，按保留份数滚动；RPO ≤ 24h。
- 恢复顺序固定、fast-fail：MySQL → ES（先删 `kb_*` 再 restore）→ MinIO → 必要时从事实源重建索引。

| full | lite + Qdrant + Redis（可选） | 建议 16GB | 独立向量引擎、多实例 |
| + graph | 叠加 Neo4j 5（`--profile graph`） | 额外约 1GB | 需要 GraphRAG 时 |
| + es-ik | 叠加装了 IK 插件的 ES 镜像 | — | 中文分词与词典热更新 |

`scripts/preflight.sh [lite|full]` 在 `docker compose up` 之前做一次性检查：docker 与 compose 是否就绪、宿主机内存是否满足档位、契约端口是否被占用、`.env` 是否还在用仓库自带的占位口令（`CHANGE_ME_*`）。返回非 0 即存在阻断项。

### P112 数据库升级有什么规矩？V26 为什么是例外？

> 标签：运维、版本管理、一致性 ｜ 难度：★★★

**考察点**：向后兼容迁移的边界，以及「语法兼容」不等于「语义兼容」。

**参考回答**

**常规规则**：schema 变更一律走 Flyway，启动时自动执行，禁止手工 DDL。迁移向后兼容一个版本：优先只加列；允许不改变既有值语义的扩宽（如 `VARCHAR` 变长）；不删列、不收窄类型、不改列名或含义、不重命名表。这样回退旧镜像时，旧代码只是忽略新列，仍可读写。按里程碑顺序升级，每步跑一次冒烟检索，不建议跨版本跳升。

**V26 的例外**：它新增的 `t_kb_email_identity_claim` 是跨 `username` / `email` 两列的**业务唯一性账本**，V25 及更早的代码不会维护它。语法上仍然兼容，但如果新旧 server 混写账号身份，唯一性就被破坏。所以 V26 不能滚动升级：

1. 冻结账号创建、联系邮箱修改、SSO 首次自动建号、注册审批四类写操作；登录和知识库读写照常。执行冲突预检并备份。
2. 一次性替换全部 server 实例，确认 V26 成功后再解冻。
3. 如果必须回退旧镜像，保持身份写入冻结；再次升级前重跑预检，核对账号表与声明表差异。

**教训**：「旧代码能忽略新表」只证明不会报错，不证明业务不变量还成立。

**追问**：「ES / Qdrant 的结构变更怎么升级？」不走迁移脚本，从 MySQL 事实源全量重建，再原子切换别名。

**代码锚点**：`kb-rag-deploy/UPGRADING.md`、`V26__email_registration.sql`

### P115 流式回答为什么用 fetch + ReadableStream，而不是浏览器原生 EventSource？

> 标签：前端、流式 ｜ 难度：★★

**考察点**：浏览器 API 的能力边界与协议细节。

**参考回答**

EventSource 有三个限制，这个场景都绕不开：

1. **只能发 GET**，不能带 JSON 请求体，而问答要提交问题、多轮历史和应用版本。
2. **不能设置自定义请求头**，控制台会话头和开放 API 的 `Authorization` 都带不上。
3. **自带自动重连**，断线后会重新发起请求，等于**自动重发问题**，重复花钱；项目的语义是主动停止不重发，断线由用户决定。

所以前端用 `fetch` 拿到 `response.body.getReader()`，自己实现 SSE 帧解析（`consumeSse`）：

- 支持 LF、CRLF、CR 三种换行；CR 之后紧跟的 LF 即使落在下一个网络块，也不能再产生一个空行。
- `TextDecoder` 以流模式解码，UTF-8 多字节字符跨网络块不会乱码。
- 只派发以空行结束的完整帧；EOF 时未结束的尾帧丢弃。
- 消费方返回 `false` 时主动停止读取，收到业务终态后取消剩余读取并释放 reader。

「是否成功」由业务终态判断，不由 HTTP EOF 判断：没收到 `done` / `error` 就报 `STREAM_INCOMPLETE`。

**代码锚点**：`kb-rag-web/src/utils/sse.ts`、`src/api/chatStream.ts`

### P116 慢响应覆盖新结果怎么防？切换知识库或账号时前端怎么处理？

> 标签：前端、并发、权限 ｜ 难度：★★

**考察点**：前端竞态与授权变化下的数据残留。

**参考回答**

典型竞态：用户先查 A，再查 B，A 的响应更慢，后到的 A 把 B 的结果覆盖了。换成切换知识库或切换账号，旧数据就会出现在新身份的页面上，这已经是越权展示。

项目里的做法：

1. **请求序号**：每次发起请求自增序号，响应回来时序号不是最新的就丢弃（如验证码组件的 `requestSequenceRef`、员工会话的 `requestSequence`）。
2. **可取消**：流式与长请求用 `AbortController`，切换范围时取消旧连接。
3. **按范围隔离状态**：页面状态按登录身份、权限和知识库范围隔离；范围变化时丢弃旧摘要、旧回答和迟到结果。
4. **撤权即清空**：资料撤权后清除详情与正在编辑的草稿，只保留允许看的状态字段。
5. **网络结果不明时不自动重试写入**：先刷新核对服务端状态，再由用户决定是否重试，避免重复提交。

**代码锚点**：`components/LoginSliderCaptcha.tsx`、`pages/workspace/useEmployeeConversation.ts`、`HOME-SOURCE-HEALTH.md`

### P117 模型输出的 Markdown 怎么安全渲染？

> 标签：前端、安全、Prompt注入 ｜ 难度：★★

**考察点**：把模型输出视为不可信输入。

**参考回答**

模型输出受检索资料影响，资料里可能埋了间接注入，所以回答内容按**不可信输入**处理：

- **不执行原始 HTML**：react-markdown 开 `skipHtml`，全仓不使用 `dangerouslySetInnerHTML`。
- **链接白名单**：`urlTransform` 只放行 `http`、`https`、`mailto` 和本页引用锚点 `#kb-citation-N`，其他协议（如 `javascript:`）一律清空；外链加 `target="_blank"`、`rel="noopener noreferrer"`、`referrerPolicy="no-referrer"`。
- **不加载远程图片**：图片只显示 alt 文字。模型给出的图片 URL 可能指向攻击者服务器，加载即泄露用户 IP 和 Referer，或者带出上下文数据。
- **引用编号有界**：`[n]` 渲染成引用按钮，编号超出本轮引用数时不渲染成可点击引用。
- **表格和代码块**：表格包进可聚焦、可滚动的区域，代码块提供复制按钮，都不改变内容语义。

**代码锚点**：`src/pages/workspace/AnswerMarkdown.tsx`

### P118 文档处理进度怎么轮询？为什么不用固定间隔？

> 标签：前端、性能、可观测 ｜ 难度：★★

**考察点**：轮询对服务端的压力控制，以及统计口径。

**参考回答**

文档页的状态同步规则：

- 有活跃处理时每 3 秒一次，空闲时每 30 秒一次。
- **前一轮完成后才安排下一轮**，不会因为慢请求叠加并发。
- 连续失败按指数退避，上限 60 秒。
- 页面隐藏或离开文档标签就暂停，回到可见时立即同步；手动刷新随时可用。
- 旧页、旧筛选、旧知识库的慢响应不能覆盖当前结果。

还有一个统计口径的修正：原来用当前页查询的总数计算整库重建百分比，加了筛选后分母就不可靠。现在由服务端的 `rebuild-status` 返回全库 `document_count` 和 `processing_count`，不受列表筛选与分页影响，排除逻辑删除与回收站文档。

**追问**：「为什么不用 WebSocket 推送？」单实例、低频状态变化、运营页面访问量小，轮询加退避足够；推送需要连接管理和多实例广播，没有真实问题驱动就不引入。

**代码锚点**：`DOCUMENT-WORKFLOW.md`、`e2e/document-polling.e2e.ts`

### P119 批量上传部分失败，怎么只重试失败的文件？

> 标签：前端、数据接入、幂等 ｜ 难度：★★

**考察点**：客户端队列的边界与幂等依赖。

**参考回答**

「添加文档」抽屉保留本次操作中每个文件的结果：已接收、失败或未确认、等待、上传中。

- **只重试失败或未确认的文件**，已接收的保留结果；每个失败文件也可以单独重试或移除。
- **并发控制**：最多 2 个请求并行；**同名文件串行发送**，保留用户选取的版本顺序。
- **网络中断可能发生在服务端接收之后**：先核对文档列表再决定是否重试。重复上传由服务端内容去重兜底，显示「已有版本，未重复建版」，不能表述为已索引或已发布。
- **范围变化**：切换知识库或身份后，未发送的文件停止排队，迟到响应不能刷新另一个知识库。已发出的请求可能仍在服务端完成。
- 队列只在当前页面内存里，**不增加数据库表或任务调度平台**；已接收文件释放浏览器里的文件引用。

**边界**：来源同步的失败项重试、索引任务恢复是另外两条链路，不能由浏览器上传清单替代。

**代码锚点**：`DOCUMENT-UPLOAD-RECOVERY.md`

### P120 知识图谱可视化为什么手写力导向布局，而不用图可视化库？

> 标签：前端、GraphRAG、选型 ｜ 难度：★

**考察点**：依赖引入的成本意识。

**参考回答**

图谱页用 SVG 渲染，布局是手写的 Fruchterman-Reingold 力导向算法，固定 300 次迭代同步计算。随机种子由节点数和边数派生，同样的数据每次得到同样的布局。

不用 @antv/g6 这类库的理由：展示规模在 50 个节点、几百条边的量级，JS 同步计算远小于一毫秒；引入一个几百 KB 的依赖，还要处理 CSP 与打包问题，收益不值。

**边界**：这是「简版可视化」。规模上到上千节点，同步布局会卡主线程，那时再考虑 Web Worker 或专业库；没到那个量级之前不预先引入。

### P122 哪些测试必须用真实 MySQL？怎么防止测试误删业务库？

> 标签：测试、事务、一致性 ｜ 难度：★★★

**考察点**：测试替身的语义差异，以及测试基础设施的安全性。

**参考回答**

**必须用真库的场景**：

- **跨表快照一致性**：H2 的 `REPEATABLE_READ` 能读到另一张表新插入的行，与 InnoDB 一致性读不同，在 H2 上断言会得出错误结论。
- **InnoDB 锁语义**：`INSERT IGNORE` 取 S 锁、`UPDATE` 要 X 锁导致的死锁（M24 配额预占），这类行为只能在真实 InnoDB 上验证。
- **Flyway 迁移**：V1 顺序执行到最新、从上一版本升级、旧记录保留、旧列写入兼容、重复迁移。

**防误删的设计**：

1. 真库测试默认不跑，只有设置了专用环境变量（如 `KB_EVAL_TEST_JDBC_URL` / `_USER` / `_PASSWORD`）才执行，凭据只从环境变量传入。
2. **数据库名必须带专用前缀**（如 `codex_eval_consistency_`、`codex_conversation_`、`codex_quality_migration_`），否则拒绝运行，防止误指业务库。
3. 使用随机独立 schema 和临时账号，测试结束只清理自己创建的表或库。

**同一套测试跑两遍**：员工会话账本的 18 项测试在 H2 和 MySQL 8.0.36 的 `REPEATABLE READ` 下都通过，才算数。

### P123 修 Bug 的流程是什么？举一个「先复现再修」的例子。

> 标签：测试、排障、工程化 ｜ 难度：★★ ｜ 关联：P103

**考察点**：修根因而不是修表象，以及测试为什么没覆盖到。

**参考回答**

流程：先问「为什么现有测试没覆盖到」→ 写最小测试稳定复现并确认失败 → 修根因 → 做与改动范围匹配的回归。

**例 1：流式回答误判成功**。管理预览把 HTTP 正常 EOF 当成回答完成。新增测试先复现了缺失终态、CRLF 换行、多个终态、未结束尾帧以及跨应用版本误用，确认失败后再修：业务流只接受一次 `done` / `error` 终态，缺终态报 `STREAM_INCOMPLETE`。根因是「连接结束」和「业务完成」被当成同一件事。

**例 2：登录按钮离开首屏**。现有布局用例视口高度只有 1000px，没覆盖 1280×720 的常见笔记本。先写真实浏览器断言复现「登录和注册提交按钮离开首屏」，再修布局，并把 390、768、1280、1440、1920 五种宽度与十二套主题纳入回归。

**例 3：`@Async` 自调用**。注解失效时不报错，于是用「提交线程 ≠ 执行线程」的行为断言钉住，而不是相信注解（见 P103）。

### P124 怎么测「取消真的发生了」这类跨进程行为？

> 标签：测试、流式、成本 ｜ 难度：★★★

**考察点**：用真实网络行为验证，而不是 mock 掉关键环节。

**参考回答**

取消、断线、超时的正确性取决于真实的 TCP 与 HTTP 行为，mock 掉 HTTP 客户端就什么也证明不了。项目的做法：

1. **本地真实上游**：起一个本地 HTTP 服务模拟模型流式接口，验证首段提前送达、等待响应头时取消、输出一半后连接实际关闭、静默响应体超时、401 分类、末尾 usage 与缺失 `[DONE]`。
2. **嵌入式 Tomcat 端到端**：客户端收到首段后主动断开，验证心跳触发取消、上游连接被关闭、账单按估算中断结算。

## 十三、踩坑复盘（STAR 素材）

面试官问「讲一个你解决过的最难的问题」时，从下面挑。按「现象 → 根因 → 修法 → 教训」讲，每个 2 分钟。

### P127 踩坑复盘：回滚之后召回全空

> 标签：踩坑、版本管理 ｜ 难度：★★★

- **现象**：应用回滚到历史正式版，检索返回空。
- **根因**：发布时只冻结了索引快照，没冻结可见版本集；回滚后旧快照索引配上当前可见集，版本 id 对不上，全部被强制过滤掉。
- **修法**：发布快照同时固化 `index_snapshots` 与 `visible_version_ids`；可见集解析收敛到 `RetrievalIndexContextResolver` 一处，快照路径绝不经过当前激活集。
- **教训**：同一个决策的两半（查哪个索引、看哪些版本）必须在同一个地方、从同一个上下文解析，分散到调用方迟早会用两个上下文各解析一半。

### P128 踩坑复盘：新策略保存不进去、按页切分泄露隐私、父子组合假生效（同一批交付物）

> 标签：踩坑、切分、隐私 ｜ 难度：★★★

- **现象**：三个新切分策略控制台一保存就报 `unknown split strategy`；按页切分的库把未脱敏的手机号写进了索引；配了 LLM 语义切分 + 父子分片的库实际在跑定长。
- **根因**：策略枚举是配置写入的唯一白名单，却漏登记了三项；切分路由对未知 code 回落定长，让「配置得上、跑的是定长」悄无声息；按页策略直接读解析产物的原始页文本，绕过了清洗与占位符替换；父子切分器注入的是接口，实际两级都跑定长，指纹却记所选策略。之后还补了一刀：解析客户端漏映射了每页 Markdown 字段，按页修复一度「形同虚设」。
- **修法**：枚举补齐并用单测钉住「每个可保存的策略码都路由到同名实现」；逐页清洗 + 拼回 + 记录页区间，按区间在清洗后的正文上下刀；父子切分器字段直接写死定长实现，配置校验拒绝其他组合。
- **教训**：新增一条处理路径，先问它有没有绕过已有的横切步骤；「静默回落」是幽灵故障的温床，封闭枚举 + 显式拒绝比宽容更安全。

### P129 踩坑复盘：`@Async` 自调用静默失效

> 标签：踩坑、并发 ｜ 难度：★★ ｜ 关联：P103

- **现象**：评测矩阵提交后控制台一直转圈，评测线程池却在空转；门禁的两次评测加轮询全压在发布请求线程上；每次 API Key 认证都在请求路径上同步写一次库。
- **根因**：Spring 的 `@Async` 基于代理，同一个 bean 内部的自调用不经过代理，注解静默失效，任务在调用线程上同步执行，当时五处受影响。
- **修法**：注入 Executor 显式提交（`32f0a3c`）；不走 self 注入，也不拆 bean（拆出来会与评测服务循环依赖，Spring Boot 3 默认禁止）；补三个断言「提交线程 ≠ 执行线程」的回归测试，退回自调用就变红。
- **教训**：**依赖代理的注解，失效时不会报错**——要用行为断言钉住，而不是相信注解。拒绝策略与 requestId 透传的细节见 P103。

### P130 踩坑复盘：线程池写下的上限永远到不了

> 标签：踩坑、并发 ｜ 难度：★★ ｜ 关联：P102

- **现象**：索引池配 `core=2,max=4` 加 200 深队列，常年只有 2 个线程；评测池配 `core=2,max=6` 加 50 深队列，注释写着「6 个 run 并行」，实际也只有 2 个。
- **根因**：`ThreadPoolTaskExecutor` 只有队列**满了**才会扩容到 max，「深队列 + 更大的 max」里的 max 永远到不了。
- **修法**：定一条池形状规则——要么队列为 0，要么 core == max；用反射遍历全部线程池 Bean 的测试钉住这条规则。
- **教训**：配置里的数字要和运行时行为一致，否则每个读代码的人都会信一个不存在的并发度。各池的具体取值见 P102。

### P131 踩坑复盘：配额预占死锁

> 标签：踩坑、事务、并发 ｜ 难度：★★★ ｜ 关联：P101

- **现象**：并发问答时，模型配额预占偶发 InnoDB 死锁。
- **根因**：预占事务先 `INSERT IGNORE` 建「租户 × 月份」计数行，再做条件 `UPDATE`。行已存在时，`INSERT IGNORE` 在唯一键上拿 S 锁，`UPDATE` 要 X 锁；两个并发预占各持一把 S 锁、互等升级，InnoDB 判死锁。
- **修法**：条件 `UPDATE` 先行，影响 0 行才建行（`1fdfe58`）。
- **教训**：并发写同一批行时，所有事务必须以相同顺序、从一开始就拿最终需要的锁；`INSERT IGNORE` 的 S 锁是很多人不知道的隐藏锁。配额的完整设计见 P101。

### P132 踩坑复盘：一整族越权

> 标签：踩坑、权限、安全 ｜ 难度：★★★ ｜ 关联：P087

- **现象**：43 个控制台端点可以跨租户操作，包括覆写别家外部数据源的 AK/SK、硬删别家登记、把别家文档回滚到旧版本。
- **根因**：从属表不带 `tenant_id`，按从属 id 寻址的入口前面只有一个「数据范围守卫」。它只回答「这个库在不在你的数据范围里」，没有租户判断，还对租户内超管、未配数据范围的库管理员直接短路放行；守卫里一个提前 `return`，把后面已经写好的围栏查询一起跳过。
- **修法**：守卫重命名为 `KbResourceGuard`，9 个方法一律先解析围栏根表（404）、再判数据范围（403）；另外 15 个「路径里自带 `kbId` 却从不查根表」的入口，修复落在服务层方法首行。
- **教训**：只覆盖一半的守卫比没有守卫更危险；围栏只保护它实际执行的语句。判据只有一条：这条链路上有没有一次对根表的查询。完整分析见 P087。

### P133 踩坑复盘：模型答案「看起来成功」

> 标签：踩坑、生成、幻觉 ｜ 难度：★★★

- **现象**：答案在半句话处结束；答案里出现 `[7]`，而本轮只有 5 条资料；模型把原文里的「参考文献 [12]」当成了引用。
- **根因**：传输层成功被当成了回答完整；引用编号混在资料正文里；没有生成后的校验。
- **修法**：`finish_reason=length` 判截断失败；资料区改为 JSON 条目、编号独立成字段；system 写入本轮合法编号清单；生成后按 Markdown 文本节点校验编号，越界不发成功终态。
- **教训**：**把「模型听话」变成「可检测、可拒绝」**，每一个概率性环节后面都要有一道确定性的检查。

### P134 踩坑复盘：ES 别名双指向

> 标签：踩坑、索引、一致性 ｜ 难度：★★★

- **现象**：索引切换后写入永久失败。
- **根因**：用 `putAlias` 追加别名，别名同时指向新旧两个索引，ES 不知道写哪个。
- **修法**：`updateAliases` 原子操作 + 显式 `is_write_index`。
- **教训**：别名切换必须是一个原子操作，任何「先加后删」的两步做法都有中间态。

## 十四、开放设计题与已知缺口

### P135 如果要上多实例、QPS 翻 10 倍，你先改什么？

> 标签：架构、性能、开放题 ｜ 难度：★★★ ｜ 关联：P104

**参考回答**

先说已经就绪的：会话与权限缓存切 `redis` 模式即可跨节点共享；MCP 无状态；模型用量对账有乐观锁，多实例重复扫描安全；检索链路本身无状态。

再说没有就绪的，按风险排序：

1. **定时任务重复执行**：网页 / 外部源同步、治理清理、审计归档在每个实例上都会触发。先按 P104 的触发器采集证据；需要时先对有外部副作用的任务加数据库租约，而不是一步上调度平台。
2. **进程内限流**：每个实例一个令牌桶，N 个实例等于 N 倍配额，需要换成共享计数。
3. **员工运行没有跨实例接管**：过期扫描只能判中断，不能续跑。
4. **引擎容量**：单机 ES / Qdrant 的设计边界是十万级文档、千万级以下分片，超出要集群化。
5. **缓存命中下降**：改写、路由、可见集缓存是进程内的，多实例只影响效率不影响正确性，放在最后。

**原则**：先测量，再按瓶颈逐项改；不要因为「要多实例」就一次性引入 MQ、分布式锁和调度平台。

### P136 在现有架构上怎么支持 Agentic RAG（多步检索、自我反思）？

> 标签：Agentic RAG、Agent、开放题 ｜ 难度：★★★

**参考回答**

把「多步」放在 Agent 层，而不是塞进检索链路：

1. **检索保持确定性**：现有链路是可评测、可门禁、可复现的单步检索，这是资产。Agent 通过 `knowledge_search` 工具多次调用它，每次调用都受同样的权限、降级、审计约束。
2. **Agent 层负责规划**：问题拆解、根据上一步结果决定下一步查什么、判断证据是否足够（可以用答案 Judge 的忠实度维度做在线自检的离线校准）。
3. **预算控制**：步数上限、每步超时、Token 配额走同一个出站计量；多步的成本和延迟都要能在报告里看到。
4. **评测扩展**：用例增加跨文档的多证据 span，命中判定已经支持多 span（Hit Rate 取任一，Recall 取覆盖比例）；最终答案 Judge 照常可用。
5. **引用**：多步检索的证据要合并编号，沿用「本轮编号 + 继承依赖」的模型，不能让第二步的 `[1]` 覆盖第一步的 `[1]`。

**追问：为什么不在检索链路里加一个「迭代检索」阶段？** 那会让单次检索的延迟和成本不再有上界，也让门禁测到的行为依赖模型的规划随机性。确定性的部分和非确定性的部分分层，各自评测。

### P140 如果要接入飞书知识库这类新数据源，你怎么做？

> 标签：数据接入、架构、增量同步 ｜ 难度：★★

**考察点**：扩展点的使用，而不是新造一条入库旁路。

**参考回答**

按既有 SPI 实现一个连接器，不改入库链路：

1. **实现 `ExternalConnector`**：`type()`、`listObjects`（返回 key、etag、size、lastModified）、`fetchObject`、`testConnection`。`ConnectorRouter` 按 `source_type` 路由，未知类型直接 `INVALID_PARAM`，不回落。
2. **版本标识**：没有 ETag 的 API 型数据源，用「页面 ID + 版本号」作为增量依据。Confluence Cloud（M23）就是这么做的：Space Key 解析为 Space ID，REST API v2 cursor 分页列举，对象键固定为 `confluence/{pageId}.html`，ETag 固定为 `{pageId}:v{version}`；未变化页面记 UNCHANGED，连正文都不请求。标题变化只产生同一文档的新版本，不会建第二篇。
3. **截断证明**：单轮多取 1 条（`max-objects-per-source + 1`），多出的那条只用来证明列表被截断；截断时记 PARTIAL，不做「远端已删除」判定。响应不完整（缺 results、缺版本、cursor 循环）整轮失败，不能把异常响应误判为删除。
4. **内容复用普通入库链**：取回的正文（如 Confluence 的 storage HTML）交给 `DocumentService.upload`，走同一套解析、清洗、版本、治理、索引。
5. **同步语义沿用**：清单截断记 PARTIAL，只有完整清单才能证明对象消失；对象消失标 SKIPPED，不删文档；单对象失败不中断整批。
6. **凭据边界**：Token 只发往登记站点的同 scheme / host / port；禁止自动重定向，跨源的 next 链接在发请求前拒绝，防止 Token 外带；读接口永远回 `******`。

**追问**：「源系统的页面权限怎么同步？」这是真正的难点。M23 同步的是 API Token 所属账号能看到的页面，不映射页面级权限到 kb-rag 的文档 ACL。现在只能按知识库划分可见范围，或入库后手工设置文档可见性；按源权限自动同步 ACL 需要单独设计，包括权限变更的增量感知与撤权时效。

**代码锚点**：`ExternalConnector`、`ConnectorRouter`、`M14-CONTRACTS.md` §2、`M23-CONTRACTS.md`

### P141 项目里哪些东西是明确不做的？你怎么判断一个需求该不该做？

> 标签：架构、选型、开放题 ｜ 难度：★★

**考察点**：取舍能力，以及用证据驱动架构演进。

**参考回答**

需求文档 §13.1 有一张「明确不做 / 未排期」清单，挑几条讲理由：

| 不做 | 理由 |
| --- | --- |
| 站点级爬取、sitemap 多页递归 | 一条登记 = 一个 URL = 一个文档，边界清晰；递归抓取带来 SSRF 面、配额与去重的整套新问题 |
| chunk 级治理 | 文档级足够，chunk 已有 enabled 开关 |
| 多级审批流 | 未排期；单级审核加操作审计（记录审核人与操作者）已覆盖当前需要 |
| 指标带 per-KB / per-key 标签 | Prometheus 无界基数反模式；按库看洞察报表，按 Key 看审计统计 |
| 多实例与引擎集群化 | 需要达到持久化调度决策文档里的证据门槛 |
| MCP 公网 OAuth | 现有 Key 模式服务可信的服务间调用，公网第三方授权未排期 |

判断标准：**有没有真实问题反复出现**。「预计未来会扩容」不算证据，一次偶发慢任务也不算。先采样、先测量，达到写明的门槛再投入，比如任务排队 P95 超过 60 秒，或积压连续 15 分钟高于执行并发的 10 倍。

**代码锚点**：`docs/知识库需求文档.md` §13.1、`DURABLE-SCHEDULING-DECISION.md`

### P142 如果要支持公网第三方 Agent 通过 MCP 接入，你会怎么设计授权？

> 标签：MCP、安全、权限 ｜ 难度：★★★

**考察点**：从「服务间 Key」到「代表用户的委托授权」的演进设计。

**参考回答**

先说现状：MCP 端点用 API Key / Memory Key 认证，适合可信的服务间调用；Key 绑定应用范围，工具不能越界。它的问题是 Key 代表「应用」，不代表「某个终端用户」，开放 API 调用一律滤掉 RESTRICTED 文档，正是因为调用方没有角色。

面向公网第三方，需要 OAuth 委托授权：

1. **资源服务器角色**：MCP 端点只校验访问令牌（受众必须是本服务，防止拿别处的令牌来用），由独立的授权服务器签发；公开受保护资源元数据，让客户端能发现授权服务器。
2. **scope 映射**：`knowledge:search`、`knowledge:chat`、`memory:read`、`memory:write` 映射到现有权限码与应用范围，最小授权。
3. **代表用户**：令牌携带终端用户身份，检索时按该用户的角色裁剪文档 ACL，RESTRICTED 文档第一次可以对外部调用可见。
4. **不变的部分**：限流、审计、配额、Origin 校验全部复用；令牌可撤销、短有效期，撤销立即生效。

**边界**：这是设计题，项目里没有实现；需求文档把它列为未排期。面试时要说清楚现有 Key 模式在什么场景下已经够用。

**代码锚点**：`docs/知识库需求文档.md` §13.1、§13.3
