# 知识库构建最佳实践

> 回答「如果让你从 0 搭一个企业知识库，你会怎么做」。按建设生命周期组织，共 24 节，编号 B01–B24，编号稳定；每节标题下一行是检索行 `> 标签 ｜ 难度 ｜ 关联`，正文给出**原则 → 做法 → 反模式**，「kb-rag 落地」指向本仓库的对应实现（P 为[项目题](01-项目全量面试题.md)编号，R 为 [RAG 八股](../RAG面试八股.md)编号），作为证据而不是唯一答案。全库编号与标签索引见 [题目索引](题目索引.md)。
>
> 面试里讲方法论最怕空泛。每条原则都要能回答两个问题：不这么做会出什么事？你怎么证明这么做是对的？

## 结论先行：十条原则

1. **先建评测集，再谈优化**。没有评测集，之后的每一次调参都是在赌。
2. **唯一事实源，索引皆可重建**。检索引擎是派生数据，正文永远从事实源读。
3. **入库只有一条路**。所有数据源汇入同一个入库入口，治理、版本、索引自动继承。
4. **权限是检索谓词，不是结果过滤**。租户、ACL、版本可见性在召回时生效。
5. **结构优先的切分，参数由评测决定**。没有普适的 chunk 大小。
6. **混合检索 + 重排是默认配方**；阈值只打在跨查询可比的分数上。
7. **每一级可降级，降级必须可见**。宁可慢，不要静默答错。
8. **发布要冻结被测过的语料**。配置变更经过门禁，门禁所测即上线所用。
9. **把「模型听话」变成「可检测、可拒绝」**。输出强校验、引用校验、截断识别。
10. **复杂度由证据驱动引入**。图谱、多模态、Agentic、消息队列、调度平台，都等真实信号出现再上。

## B01 立项：先定问题，再定技术

> 标签：立项、评测集 ｜ 难度：★★ ｜ 关联：R34

**原则**：知识库的第一个交付物是问题集与评测集，不是索引。

**做法**

1. **盘点用例**：谁在问（员工、客户、Agent）、问什么（事实查找、流程指引、跨文档归纳、数据查询）、能容忍什么（延迟、错误、拒答）。
2. **判断 RAG 是否合适**：数据查询与聚合走 SQL 或工具；需要全局归纳的问题要单独设计（map-reduce 摘要、图谱全局检索）；语料小且稳定时直接放进上下文。
3. **定成功标准**：检索侧 Recall@5、Hit Rate；答案侧正确率、忠实度、拒答准确率；工程侧 P95 延迟、单次成本。目标值写下来。
4. **建首批评测集**：发布门禁至少 50 条、推荐 100 条以上；来源是真实问题 + 业务专家编写 + 故意无法回答的问题；**证据用「文档 + 原文片段」锚定，不绑 chunk id**。

**反模式**

- 先把所有文档灌进去，「跑起来再说」。
- 用五六个演示问题判断效果好坏。
- 成功标准只有「用户觉得好用」。

**kb-rag 落地**：项目级成功标准写在需求文档 §1——在 ≥100 条评测集上，混合检索 + 重排的 Recall@5 与命中率相对单路检索的差值超出容差，且连续两轮方向一致；评测集 span 锚定见 [RAG 八股](../RAG面试八股.md) R34。

## B02 数据源盘点与内容治理

> 标签：数据接入、治理 ｜ 难度：★★ ｜ 关联：R24、P019、P022

**原则**：入库不等于可检索。每篇文档都要回答「谁负责、什么时候生效、什么时候失效、谁能看」。

**做法**

1. **数据源清单**：来源系统、属主、格式、规模、更新频率、权限模型、敏感级别、保留期。
2. **准入治理**：
   - 审核发布：高风险知识库开启「新文档先草稿、审核后发布」；发布是终态，下架用有效期或回收站。
   - 有效期：制度类文档设生效与失效时间，窗外自动退出检索。
   - 删除两段式：先进回收站（可恢复），保留期后才彻底清除。
3. **治理状态不进索引**：审核、有效期、回收站作为「可见集合」的行过滤条件，状态变化只改一行数据库记录，不重建索引。
4. **所有来源汇入同一入库入口**：文件上传、网页、对象存储、Confluence、聊天记录都物化成文件交给同一个上传方法，自动继承治理、版本与索引管线。
5. **增量同步**：用稳定标识判断变化（内容哈希、ETag、`pageId:version`），未变不重建；单项失败不中断批次；**列表不完整时禁止做「消失判定」**——没列全就不知道缺的是删了还是没列到。

**反模式**

- 每接一个数据源写一条独立的入库旁路，治理和版本逻辑各写一份。
- 远端看不到了就直接删除本地文档。
- 同步失败只记日志，界面上看不到。

**kb-rag 落地**：治理门控见 [RAG 八股](../RAG面试八股.md) R24；统一入库与增量同步见 [项目全量面试题](01-项目全量面试题.md) P019、P022。

## B03 面向检索的内容写作规范

> 标签：治理、切分、数据清洗 ｜ 难度：★★

**原则**：知识库的上限由内容决定。写给人看的文档，不一定能被检索到；源头按「可检索」来写，比下游任何算法都便宜。

**做法**

1. **一段一个主题**：每个小节只讲一件事，标题直接说明内容（「报销的审批时限」，而不是「其他说明」）。标题层级规范时，按标题切分几乎零成本就能得到高质量分片。
2. **自包含**：关键段落不依赖上文——少用「如上所述」「该产品」这类指代，第一次出现写全称。分片被单独取出后，读者和模型都要能看懂。
3. **写出用户的问法**：FAQ 与操作指南把用户会怎么问写进正文或别名（「忘记密码」「密码重置」「登不上去」），缩小用户措辞与文档措辞的差距。
4. **结构化信息用表格或列表**：参数、限额、流程步骤不要埋在长段落里。
5. **写明时效与适用范围**：生效日期、适用对象、版本号写在文档开头；过期内容及时下架，而不是在正文里加一句「本条已废止」。
6. **图片配文字**：关键图示（流程图、接线图）旁边用文字写出要点；截图里的文字，模型和 BM25 都未必读得到。
7. **一份事实只有一个权威出处**：同一规定散落在五份文档里，改一份漏四份，检索时就会出现互相矛盾的答案。

**反模式**

- 把 PPT 截图、扫描件当作主要知识载体。
- 一篇「大全」文档塞进所有主题，切分后每个分片都语义混杂。
- 用正文里的「已废止」代替下架流程。

**kb-rag 落地**：按标题切分（heading 策略）、有效期与下架（治理状态）、解析预览让运营在入库前核对解析结果；本题库本身就按「一题一个三级标题、标题带编号」组织，用 heading 策略（level 3）入库即是一题一片。

## B04 解析

> 标签：文档解析、OCR ｜ 难度：★★ ｜ 关联：R03、P012、P013

**原则**：解析质量是整条链路的天花板，而且最少被评测。

**做法**

1. **按格式选路线**：电子文档读文本层；扫描页（文本层过少）渲染成图后走 OCR 或视觉模型；表格保留结构转 Markdown。
2. **解析服务独立部署**：依赖重、易 OOM、扩缩容曲线与检索不同；解析服务**不调大模型**，模型调用集中在主服务，计量、配额、降级才有唯一入口。
3. **安全基线**：扩展名与文件头一致性校验、大小上限、zip 炸弹与路径穿越防护、XML 禁用外部实体、解析期零出站请求。
4. **统一中间格式**：结构化 Markdown + 按页文本 + 图片 + 警告，下游与格式解耦。
5. **解析预览**：高价值知识库开启「解析后人工确认再入库」。
6. **质量抽检**：每类格式抽样对照原文，重点看阅读顺序、表格、乱码。
7. **许可证**：解析依赖的许可证会影响分发方式（例如 AGPL 的网络服务条款），选型时一并评估。

**反模式**

- 解析结果不看就入库。
- 在解析服务里直接调大模型，形成第二套模型配置与成本归属。
- 用同一个通用解析器处理所有格式。

**kb-rag 落地**：解析职责边界与双实现见 [RAG 八股](../RAG面试八股.md) R03、[项目全量面试题](01-项目全量面试题.md) P012；扫描件与图片见 P013。

## B05 清洗与脱敏

> 标签：数据清洗、隐私 ｜ 难度：★★ ｜ 关联：R07

**原则**：清洗规则是索引配置的一部分，必须可追溯、可重放。

**做法**

1. **固定顺序**：页眉页脚（跨页统计识别）→ 水印 → 正则替换 → 隐私脱敏。
2. **脱敏默认值按数据性质定**：聊天记录、工单等天然含个人信息的来源默认开启。
3. **原件永远保留**，清洗只作用于派生文本。
4. **规则变化计入配置指纹**：存量文档标记「使用旧配置」，由运营决定何时重建，而不是保存配置就自动全量重建。
5. **任何新处理路径都消费同一份清洗后的正文**。

**反模式**

- 新增一种切分方式时直接读解析原文，绕过清洗与脱敏——按页切分的库把未脱敏的手机号写进索引，就是这样发生的。
- 清洗逻辑散落在各个处理环节。

**kb-rag 落地**：按页切分绕过清洗的真实事故与修法见 [RAG 八股](../RAG面试八股.md) R07。

## B06 切分

> 标签：切分、父子分片 ｜ 难度：★★ ｜ 关联：R06–R09

**原则**：有结构用结构，没结构再谈语义；参数由评测决定。

**做法**

| 语料 | 推荐策略 |
| --- | --- |
| 结构良好的 Markdown / 技术文档 | 按标题层级 |
| 有明确分隔标记 | 按分隔符（字面量或正则） |
| PPT、扫描件等「页即语义」 | 按页（消费清洗后的正文） |
| 无结构、价值高的长文 | LLM 切分：只输出切点编号、强校验、结果缓存 |
| 表格 | 保结构、按行、每块重复表头 |
| 聊天记录 | 按会话 + 时间窗口聚合，可选重叠 + 检索侧去重 |
| 兜底 | 定长 + 重叠 |

1. **起点参数**：600 token、100 重叠（中文技术文档）；在评测集上扫 2–3 档再定。
2. **父子分片**：答案经常「只答了一半」时启用——子片（约 400 token）用于检索，父片（约 1200 token）用于回答；重排在子片粒度做；子片记录在父片中的偏移并逐字校验，校验不过就丢弃偏移。
3. **策略集合封闭**：配置只接受已实现的策略，未知值显式拒绝，不静默回落到默认。

**反模式**

- 凭感觉定 chunk 大小，并称之为「最佳实践」。
- 把表格从中间切开、丢掉表头。
- 配置界面显示 A 策略，实际跑的是默认策略。

**kb-rag 落地**：[RAG 八股](../RAG面试八股.md) R06–R09。

## B07 元数据与索引设计

> 标签：元数据、索引 ｜ 难度：★★ ｜ 关联：R16、R12、R13、P017

**原则**：只有要当过滤谓词的字段才进引擎，而且建索引时就声明。

**做法**

1. **字段分三类**：
   - 定位类（引用与追溯）：文档 id、版本、页码、章节、chunk 序号；
   - 过滤类（进引擎）：租户、知识库、版本、启用状态、权限标签、类型、时间；
   - 增强类：标题、摘要、关键词、假设问题。
2. **强制过滤由服务端构建**：租户、版本可见集、启用状态、ACL 不接受请求参数；可选过滤只能进一步收窄。
3. **自定义元数据加命名空间前缀**，永远撞不上系统字段。
4. **索引命名与别名**：物理索引名包含知识库、嵌入模型段、快照段；业务只访问别名。
5. **嵌入模型版本化**：模型与维度固化进索引；换模型 = 建新索引 → 双写 → 回填（幂等 + 水位二次校验）→ 别名原子切换。
6. **引擎按规模演进**：起步用一个搜索引擎同时承担 BM25 与向量；规模上来再拆出专用向量库；两种形态共用抽象层，并统一分数量纲，保证同一阈值含义不变。
7. **先做容量估算**：`chunk 数 ≈ 总 token / 步长`，`向量存储 ≈ chunk 数 × 维度 × 4 字节 × 副本数`，再加索引结构开销。

**反模式**

- 上线后临时加过滤字段，发现要全量重建。
- 在业务代码里写死某个引擎的查询。
- 原地修改索引 mapping。

**kb-rag 落地**：可过滤字段与 `ext_` 前缀见 [RAG 八股](../RAG面试八股.md) R16；lite / full 与分数统一见 R12、R13；不停机换模型见 [项目全量面试题](01-项目全量面试题.md) P017。

## B08 术语表、同义词与分类体系

> 标签：BM25、元数据、查询改写 ｜ 难度：★★ ｜ 关联：P027、P021、P109

**原则**：企业知识库的检索难点往往不是语义，而是**叫法不统一**——同一个东西有正式名、简称、旧名、英文名和内部代号。

**做法**

1. **建术语表**：每个核心概念一行，列出标准名、别名、缩写、旧称、英文名和所属领域，由业务方维护。
2. **三处使用术语表**：
   - **分词词典**：专名加入 IK 自定义词典，防止被切碎（改完要重建索引）；
   - **同义词扩展**：查询时把别名扩展成标准名，或索引时写入同义词；
   - **改写提示**：改写 Prompt 附上与问题相关的术语，让模型把口语与缩写归一。
3. **分类体系**：按业务线、文档类型、适用对象建立有限的分类标签，作为元数据用于过滤与路由；标签取值要封闭、可枚举，不要让每个人随手造标签。
4. **停用词谨慎**：领域里有意义的短词（如产品代号）不能被当作停用词过滤。
5. **持续更新**：零命中问题里反复出现的新词，是术语表最好的来源。

**反模式**

- 靠嵌入模型「理解」内部代号——模型训练时从没见过这些词。
- 分类标签自由填写，半年后同一个类别有十种写法。

**kb-rag 落地**：IK 词典在控制台维护、ES 远程词典热更新（P027）；元数据抽取规则把字段写入可过滤元数据（P021）；零命中报表提供新词来源（P109）。

## B09 知识库划分与应用设计

> 标签：架构、路由、权限 ｜ 难度：★★★ ｜ 关联：P032、P076、P077、P070

**原则**：知识库按「谁能看、怎么切、谁维护」划分；应用按「给谁用、答什么」组合知识库。两者分开，才能复用内容又分别控制行为。

**做法**

1. **划分知识库的依据**，按优先级：
   - **权限边界**：可见范围不同的内容分库，库级授权最简单可靠；库内只有少量敏感文档时再用文档级 ACL。
   - **处理方式**：切分策略、解析方式、嵌入模型不同的内容分库（如聊天记录与制度文档）。
   - **维护责任**：不同团队维护的内容分库，治理流程与审核人清晰。
2. **不要按「主题」切得过细**：库太多，路由出错的概率和运维成本都会上升；主题差异用元数据标签解决。
3. **应用 = 知识库组合 + 检索配置 + Prompt + 模型**：同一批知识库可以组成多个应用（员工问答、客服、Agent 工具），各自有不同的 Prompt、拒答策略和阈值。
4. **多库应用**：设置库权重与配额，结果用 RRF 合并；路由只在库很多、问题领域可区分时开启，路由失败回落全库检索。
5. **每个应用独立发布和评测**：应用版本冻结配置与语料，门禁用该应用自己的评测集。

**反模式**

- 一个大库装下全公司内容，再靠 Prompt 叮嘱「不要回答机密内容」。
- 每个应用复制一份知识库，内容更新要改 N 处。

**kb-rag 落地**：多库路由与跨库 RRF、配额权重（P032）；应用版本快照与门禁（P076、P077）；员工应用使用授权要求应用关联的**所有**知识库都在用户范围内（P070）。

## B10 FAQ 库建设

> 标签：数据接入、检索、运营闭环 ｜ 难度：★★

**原则**：高频、答案固定、答错代价高的问题，用 FAQ（标准问答对）而不是让模型从长文档里现编。

**做法**

1. **结构**：标准问、若干相似问（用户的不同问法）、标准答案、适用范围、生效时间、负责人。
2. **检索方式**：用「问题对问题」的相似度匹配（相似问一起建索引），命中高置信时直接返回标准答案；置信不足时再走普通 RAG。
3. **相似问的来源**：线上真实问法（零命中、差评、人工客服记录），而不是编写者自己想象。
4. **答案要短而可执行**：给结论和步骤，长解释链接到原文。
5. **定期体检**：命中率低的 FAQ 要补相似问；从不命中的 FAQ 要下线；答案过期的 FAQ 要跟随制度更新。
6. **和文档库的关系**：FAQ 是文档的「高频索引」，答案要能追溯到权威文档，制度修订时一并更新。

**反模式**

- FAQ 只有标准问、没有相似问，用户换个说法就匹配不上。
- FAQ 与正式文档各说各话，没有更新联动。

**kb-rag 落地**：项目没有独立的 FAQ 类型；可以把 FAQ 整理成「一问一节」的 Markdown，用 heading 策略入库，达到一问一片的效果；高置信直返需要在应用层单独实现。面试时照实说明这一边界。

## B11 一致性与版本

> 标签：一致性、版本管理 ｜ 难度：★★★ ｜ 关联：R11、R14、R15

**原则**：数据库与检索引擎不在一个事务里，就把不一致窗口变成可记录、可补偿的证据。

**做法**

1. **唯一事实源**：业务库是事实源，引擎是派生数据，正文永远回事实源读。
2. **双写顺序**：先写「待同步」记录 → 写引擎 → 置成功或失败；定时扫描失败与超时未确认的记录，按目标索引分组幂等重放。
3. **同步状态粒度是「数据 × 物理索引」**，重建期间才能表达「新索引写成功了、旧索引还没有」。
4. **删除**：先写后删，宁可短暂重复，不留补偿看不见的空洞。
5. **读路径自愈**：命中了事实源已删除的数据就丢弃并异步清理引擎；被禁用的数据只丢弃不清理；发布快照上关闭自愈。
6. **事务边界**：事务里只写元数据；**事务提交后**再触发异步处理，否则工作线程读不到未提交的数据。
7. **文档版本**：内容哈希 + 处理指纹决定是否新建版本；新版本构建完成才激活，激活只切换可见集合；保留若干旧版本秒级回退；被发布快照引用的版本不清理。

**反模式**

- 直接覆盖旧版本，构建失败时线上内容就没了。
- 在数据库事务里调用解析、嵌入等外部服务。
- 把检索引擎当事实源，从引擎里读正文返回给用户。

**kb-rag 落地**：[RAG 八股](../RAG面试八股.md) R11、R14、R15。

## B12 检索配方

> 标签：检索、混合检索、重排 ｜ 难度：★★ ｜ 关联：R17–R29

**原则**：默认配方要稳，增强项要可关、可降级、可观测。

**默认配方**

```
改写（默认关闭）→ 路由（多库时，白名单交集，失败搜全部）
→ 向量 + BM25（两次独立请求，query 只嵌入一次）→ RRF(k=60)
→ 重排（候选 50，超时 1.5s）→ 父子归并 → 阈值（只打在重排分或余弦）→ top_n=5
```

**做法**

1. **每级独立超时与降级**，降级原因码按处置动作分类（超时是容量问题、失败是配置问题），写进响应。
2. **阈值只打在跨查询可比的分数上**：重排分优先，其次归一化余弦；只有 BM25 时放弃阈值并明确告知。
3. **响应自描述**：分数附带分数类型、降级标记、引用所需的定位信息。
4. **没有模型也能跑**：嵌入不可用时退化为 BM25 单路，这强迫每一级都想清楚「不可用时怎么办」。
5. **增强项按证据引入**：图检索（关系型多跳问题占比高、实体抽取质量可控）、多模态（图片与扫描件信息占比高）默认关闭；新增能力「加路不换路」。
6. **多库**：跨库只用名次不用分数；重排候选是全局预算而不是每库一份。

**反模式**

- 只用向量检索。
- 阈值打在融合分或 BM25 分上。
- 降级静默发生，调用方无从得知。
- 路由失败时收窄检索范围——用一部分语料答出来的答案，从外面看和正确答案没有区别。

**kb-rag 落地**：[RAG 八股](../RAG面试八股.md) R17–R29。

## B13 生成

> 标签：生成、引用、Prompt注入 ｜ 难度：★★ ｜ 关联：R30–R33、R45

**原则**：Prompt 约束是概率性的，关键约束要有确定性的校验兜底。

**做法**

1. **Prompt 要素**：角色与范围 → 资料区声明 → 业务自定义指令 → 拒答规则 → 防泄露 → 引用规则。安全规则放在业务指令之后，业务方写的指令冲不掉它们。
2. **资料区防伪造**：资料以结构化条目（JSON）呈现并转义尖括号，资料正文拼不出分隔符；引用编号与正文分字段；检索为空时显式告诉模型「没有资料、不能引用」。
3. **生成后校验**：引用编号是否在本轮资料范围内；`finish_reason` 是否正常结束。任何一项不通过都不发成功终态。
4. **流式**：定义唯一终态；引用在完整答案校验通过后下发；心跳 + 断连取消上游请求；取消后按上界保守计费。
5. **长回答与员工场景**：持久运行 + 只读订阅；提交带幂等 id；停止先落库再取消；过期只判中断不自动重跑。
6. **一条生成路径**：线上、调试、评测共用同一个生成服务，评测测到的就是线上会执行的 Prompt。

**反模式**

- 把 HTTP 正常结束当作回答完整。
- 引用编号混在资料正文里，模型把原文的「参考文献 [12]」当成引用。
- 评测用一份手写的「近似 Prompt」。

**kb-rag 落地**：[RAG 八股](../RAG面试八股.md) R30–R33、R45；[项目全量面试题](01-项目全量面试题.md) 第四、六部分。

## B14 权限与安全

> 标签：权限、安全 ｜ 难度：★★★ ｜ 关联：R24、R31、R40

**原则**：凡是涉及数据边界的决策，都用代码里的谓词或集合运算，不靠模型听话。

**做法**

1. **多租户**：只有根聚合表带租户字段，从属数据经根归属；**每个入口先解析根**，而不是相信路径里的父资源 id；越权返回 404，租户判定先于数据范围判定，错误文案一致。
2. **文档 ACL** 在可见集合层裁剪、不缓存；发布快照冻结「哪些版本作答」，不冻结「谁能看」。
3. **身份分链**：控制台会话、应用 Key、记忆 Key 各走独立的过滤器链；Key 只存摘要，明文只展示一次；最小授权范围；按 Key 限流；审计只存脱敏摘要。
4. **注入防线**：数据与指令分离、白名单裁决、中间产物（改写结果）不回流到 Prompt、结构化输出强校验。
5. **出站安全**：抓取用户 URL 校验每个解析 IP、禁止自动重定向、限时限体积；图片只接受内联数据，不接受 URL。
6. **前端**：内容一律按纯文本或安全 Markdown 渲染，不执行原始 HTML。
7. **运维面**：管理端口独立并默认只绑定本机。

**反模式**

- 租户隔离只覆盖请求线程，后台任务线程漏掉。
- 守卫只检查「数据范围」不检查「租户」——只守一半比不守更危险，它让评审以为已经守住了。
- 用提示词约束「不要访问其他知识库」。

**kb-rag 落地**：[RAG 八股](../RAG面试八股.md) R24、R31、R40；[项目全量面试题](01-项目全量面试题.md) 第八部分。

## B15 评测与发布

> 标签：评测、发布门禁 ｜ 难度：★★★ ｜ 关联：R34–R39

**原则**：发布是一个需要证明的动作，证明的对象必须是即将上线的那份东西。

**做法**

1. **评测集维护**：span 锚定；文档更新后证据失效的用例标记待复核、单独统计、不计入未命中；图片用例用文档级锚定；多轮用例带历史；无法回答的用例测拒答。
2. **两层指标**：检索五指标（Recall / Precision / Hit Rate / MRR / NDCG）+ 答案五维（正确性、忠实度、完整性、引用正确性、引用完整性）+ 拒答准确率；K 的口径全组统一。
3. **离线档**：评测放宽超时、降级自动重试，并且不计入线上监控与洞察。
4. **输入快照**：提交评测时冻结用例输入与语料指纹，排队期间的编辑不影响已提交的运行。
5. **门禁**：同语料同时刻双跑 → 双方共同有效的样本交集上重算 → 「不可判定」条件先于指标比较 → 容差 `max(2pp, 1/N)` → 通过 / 拦截 / 仅记录三态；答案门禁显式开启才参与。
6. **冻结与回滚**：发布时同时冻结索引与可见版本集合；正式版唯一；回滚 = 把历史版本重新置为正式版；禁用等止血操作要穿透快照。

**反模式**

- 和上个月的评测数字比较。
- Judge 失败按 0 分计，看起来像质量回退。
- 只冻结索引不冻结可见集合，回滚后召回为空。
- 门禁任务和评测任务共用一个线程池，门禁等评测、评测等线程，自等待死锁。

**kb-rag 落地**：[RAG 八股](../RAG面试八股.md) R34–R39；[项目全量面试题](01-项目全量面试题.md) 第七部分。

## B16 运营闭环

> 标签：运营闭环、评测集 ｜ 难度：★★ ｜ 关联：R39、P073、P079、P109

**原则**：上线是运营的开始。线上信号要能变成可回归的用例。

**做法**

1. **内容缺口**：在 API 边界记录检索洞察（脱敏摘要 + 归一化哈希），按「零命中问题 Top N」输出报表，驱动补文档。
2. **反馈**：正反馈可以转成评测用例；负反馈建成质量问题，**不能直接当成正确证据**——它只说明错，不说明什么是对的。
3. **质量问题**：领取 → 写标准答案与正确证据形成纠正用例 → 回归评测 → 在同一事务里重新核验输入、配置、语料、证据与评分 → 确认解决。
4. **分片标注**：禁用、编辑、合并、拆分都走「事实源先行 → 重嵌入 → 双引擎同步」的变更管线；文档出新版本后，禁用类标注按内容哈希精确继承，其余标注给出相似度推荐（对称相似度），由人逐条确认。
5. **来源健康**：同步状态、失败项与重试入口对运营可见。

**反模式**

- 负反馈只记日志。
- 标注在文档更新后自动批量迁移——误迁移的代价远大于人工确认的成本。

**kb-rag 落地**：[RAG 八股](../RAG面试八股.md) R39；[项目全量面试题](01-项目全量面试题.md) P073、P079、P109。

## B17 团队与流程

> 标签：运营闭环、治理、工程化 ｜ 难度：★★ ｜ 关联：P022、P099、P079

**原则**：知识库是「内容产品」，不是一次性交付的技术项目。没有明确的内容负责人，三个月后内容就会过期。

**做法**

1. **角色**：内容负责人（每个库一位，对内容准确与时效负责）、审核人、运营（处理反馈与缺口）、算法与工程（效果与平台）、业务方（定义「好」与验收）。
2. **内容生命周期**：起草 → 审核 → 发布 → 定期复审 → 修订或下架。每份文档有负责人与复审日期。
3. **变更流程**：检索配置、Prompt、模型的变更走应用版本与发布门禁；内容的大批量更新先在测试版上跑评测。
4. **例行节奏**：每周看零命中与差评，处理质量问题；每月复盘指标趋势与评测集覆盖；每季度清理过期内容。
5. **评测集是共同语言**：内容、算法、工程的改动都用同一套评测集证明效果，争论回到数据。
6. **服务等级**：约定反馈的处理时限、撤权的生效时限、内容更新到可检索的时限。

**反模式**

- 所有内容都由一个「知识库管理员」维护，业务变化了他也不知道。
- 线上问题由工程师直接改数据库或索引，事实源和派生数据说不清。

**kb-rag 落地**：审核发布状态机与有效期（P022）；操作审计记录谁改了什么（P099）；质量问题有领取人、处理记录和关闭标准（P079）。

## B18 可观测与告警

> 标签：可观测、告警 ｜ 难度：★★ ｜ 关联：R42

**原则**：RAG 的典型故障是「服务全绿，答案全错」，必须有业务语义的监控。

**做法**

1. **核心指标**：零命中率、降级率（按原因码）、拒答率、负反馈率、各阶段延迟、索引同步积压、任务失败数、Token 消耗。
2. **告警**：任务连续失败、降级率超阈值、同步积压超阈值；带静默期，避免刷屏。
3. **埋点位置**：放在 API 边界等横切汇聚点，不放进被评测复用的检索链路内部。
4. **标签基数**：不用知识库 id、Key 这类无界维度做指标标签；按库统计用报表，按 Key 统计用审计。
5. **链路追踪**：request_id 贯穿入口、解析服务、模型调用与异步线程；日志只有 info / error，error 带错误码。

**kb-rag 落地**：[RAG 八股](../RAG面试八股.md) R42。

## B19 成本

> 标签：成本 ｜ 难度：★★ ｜ 关联：R41、P101

**原则**：成本要能按租户归属、在请求发出前拦截、事后可对账。

**做法**

1. **索引侧**：按内容与处理指纹复用，只重算变化的阶段；LLM 切分结果缓存。
2. **查询侧**：改写默认关闭；重排候选全局预算；控制 top_n 与上下文长度；不同用途的输出预算分开（改写短、生成长、评测更长）。
3. **配额**：计量放在模型调用的出站边界；请求前原子预占、明确失败才释放、缺少用量按上界结算、崩溃遗留按上界保守结算；价格显式配置并快照，按币种分别汇总。

**反模式**

- 事后按日志统计成本，配额耗尽的瞬间仍能并发打进来一大批请求。
- 取消的请求记成零消耗。

**kb-rag 落地**：[RAG 八股](../RAG面试八股.md) R41；[项目全量面试题](01-项目全量面试题.md) P101。

## B20 Agent 接入最佳实践

> 标签：Agent、MCP、工具调用 ｜ 难度：★★★ ｜ 关联：P051、P007、P053、P060、P059、P056

**原则**：给 Agent 用的知识库是一个**工具**，工具的契约要让模型能正确调用、能看懂结果、能从错误中自我修正。

**做法**

1. **优先给证据，不给答案**：Agent 自己有推理能力，检索工具返回带定位信息的原文片段、来源与分数，让 Agent 综合；问答工具留给没有生成能力的调用方。
2. **参数少而明确**：必填只有应用与查询；可调参数限制在白名单内（条数、阈值、过滤、内容长度），检索策略冻结在应用版本里，Agent 调不坏它。
3. **错误可读**：参数问题返回工具业务错误（模型能读到内容并修正），协议问题才返回协议错误；错误信息写明怎么改。
4. **返回长度可控**：给出内容长度上限参数，避免一次检索塞满 Agent 的上下文窗口。
5. **身份与授权**：每个 Agent 用独立的 Key，授权范围只含它需要的应用；Key 可随时轮换、禁用并立即生效；调用全部审计。
6. **记忆与知识分开**：用户个人信息进记忆库（按用户隔离、可更新可遗忘），企业知识进知识库（有版本、有审核）。
7. **灰度与反馈**：新版本先让 Agent 显式调用测试版灰度；终端用户反馈通过反馈接口回流到质量闭环。
8. **成本护栏**：按 Key 限流，按租户配额，Agent 侧设置单任务的检索次数上限，防止循环调用。

**反模式**

- 把检索参数全部暴露给 Agent，让模型自己调 `recall_top_k` 和重排开关。
- 工具报错只返回「内部错误」，Agent 只能盲目重试。
- 多个 Agent 共用一把 Key，出了问题无法追溯。

**kb-rag 落地**：REST 与 MCP 同一身份两种 transport（P051）；覆盖参数白名单（P007）；MCP 错误平面（P053、P060）；从零接入流程（P059）；记忆库（P056–P058）。

## B21 演进路线与复杂度引入时机

> 标签：架构、选型 ｜ 难度：★★★

**原则**：架构演进是后验的——某处反复出现棘手问题，说明原来的抽象不够用了，才引入新的复杂度。

| 阶段 | 目标 | 做什么 |
| --- | --- | --- |
| 一 | 跑通 | 定长切分 + 单路检索 + 直接生成；**同时建评测集** |
| 二 | 提质 | BM25 + 向量 + RRF + 重排；按语料调切分 |
| 三 | 提质 | 父子分片、改写、多库路由 |
| 四 | 可控 | 评测闭环、发布门禁、快照冻结、运营闭环 |
| 五 | 扩展 | 图检索、多模态、Agent 记忆、MCP |

| 能力 | 引入信号 |
| --- | --- |
| 父子分片 | 答案完整性评分低，证据跨句、跨段 |
| Query 改写 | 多轮追问多；零命中问题里口语化表述占比高 |
| 多库路由 | 应用绑定多个库，无关库的结果挤占名额 |
| 图检索 | 关系型、多跳问题占比高，且实体抽取质量可控 |
| 多模态 | 图片、扫描件承载的信息占比高 |
| Agentic 多步检索 | 复合问题占比高，且业务能接受延迟与成本上升 |
| 消息队列 / 持久化调度 | 多实例部署 + 有证据的重复副作用、持续积压或任务接管 SLA |
| 集群化向量库 | 容量估算显示单机内存放不下 |

**反模式**：「预计未来会扩容」就先上消息队列、分布式锁和调度平台。

**kb-rag 落地**：[持久化调度投入决策](../../kb-rag-deploy/docs/DURABLE-SCHEDULING-DECISION.md)。

## B22 上线检查清单

> 标签：速查、运维 ｜ 难度：★

**数据**

- [ ] 数据源清单完整，每个来源有属主与更新频率
- [ ] 每类格式抽检过解析结果
- [ ] 脱敏规则按来源配置，敏感来源默认开启
- [ ] 审核、有效期、回收站策略已按知识库配置

**索引**

- [ ] 过滤字段在建索引时声明，包含租户、版本、启用状态、权限
- [ ] 嵌入模型与维度固化进索引，业务只访问别名
- [ ] 双写同步状态与补偿任务正常，积压有监控
- [ ] 能从事实源全量重建索引，并演练过

**检索与生成**

- [ ] 默认配方的每一级都有超时、降级与原因码
- [ ] 阈值只打在可比分数上，响应带分数类型
- [ ] 零模型配置下能退化运行
- [ ] Prompt 有资料分隔与声明、拒答、防泄露、引用规则
- [ ] 生成后有引用编号校验与截断识别
- [ ] 流式有唯一终态、心跳与断连取消

**质量**

- [ ] 评测集 ≥ 50 条（推荐 ≥ 100），含无法回答的问题
- [ ] 检索与答案两层指标有基线
- [ ] 发布门禁开启，发布时冻结索引与可见版本集合
- [ ] 回滚演练过

**安全与治理**

- [ ] 每个入口先解析租户根，越权返回 404
- [ ] 文档 ACL 在检索谓词中生效
- [ ] Key 只存摘要、有授权范围与限流、调用可审计
- [ ] 出站请求有 SSRF 防护
- [ ] 管理端口不对公网暴露

**运营**

- [ ] 零命中率、降级率、负反馈率有看板和告警
- [ ] 负反馈能建成质量问题并回归验证
- [ ] 模型配额与成本台账按租户可查
- [ ] 备份与恢复演练过，RPO 明确

## B23 反模式速查

> 标签：速查 ｜ 难度：★

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 没有评测集就调参 | 改完不知道好坏 | 先建评测集，参数进评测 |
| 引擎当事实源 | 引擎坏了就是灾难，陈旧副本返回给用户 | 事实源在数据库，引擎可重建 |
| 每个数据源一条入库旁路 | 治理、版本逻辑分叉 | 所有来源汇入同一入口 |
| 应用层后过滤权限 | 结果数量泄露信息，召回被挤占 | 权限在检索谓词里 |
| 凭感觉定 chunk 大小 | 效果不可解释 | 结构优先，参数由评测扫出 |
| 只用向量检索 | 专有名词、编号召不回 | 向量 + BM25 + 重排 |
| 阈值打在融合分上 | 过滤器随查询漂移 | 只打在重排分或余弦上 |
| 降级静默 | 调用方拿到退化结果却不知道 | 原因码进响应 |
| 路由失败时收窄范围 | 用部分语料答题，外部无法察觉 | 回退到搜全部并标记 |
| 把 HTTP 200 当成功 | 截断的答案被当成完整答案 | 检查结束原因与业务终态 |
| 引用编号混在正文 | 模型引用原文编号 | 编号独立字段 + 生成后校验 |
| 和历史数字比较 | 语料和时间都变了，结论不可信 | 同语料同时刻双跑 |
| 只冻结索引 | 回滚后召回为空 | 索引与可见集合一起冻结 |
| 守卫只查数据范围 | 跨租户越权 | 每个入口先解析租户根 |
| 预判式引入 MQ / 调度平台 | 运维成本上升，收益无法验证 | 等真实信号，再按最小协议立项 |

## B24 附：默认参数起点

> 标签：速查、配置 ｜ 难度：★

以下是 kb-rag 的默认值，可以作为新项目的起点，**上线前都应在自己的评测集上验证**：

| 参数 | 起点 | 什么时候调 |
| --- | --- | --- |
| chunk 大小 / 重叠 | 600 / 100 token | 评测扫 300 / 600 / 1000 |
| 父子分片 父 / 子 / 子重叠 | 1200 / 400 / 50 token | 答案完整性差时启用 |
| 每路召回数 | 50（上限 100） | Recall@50 低时调大 |
| 最终返回数 top_n | 5（上限 20） | 答案不完整时调大，注意上下文成本 |
| RRF k | 60 | 一般不调 |
| 加权融合向量权重 | 0.6 | 仅在确知某一路更强时切换加权 |
| 重排候选 / 超时 | 50 / 1.5 秒 | 看延迟预算与 Recall@候选数曲线 |
| 改写超时 | 800 毫秒，默认关闭 | 多轮追问多时开启 |
| 可见集缓存 | 5 分钟，激活时主动失效 | 有效期自然到期的生效延迟可接受时不调 |
| 评测离线超时 / 降级重试 | 10 秒 / 2 次 | 评测降级率高时检查模型容量 |
| 门禁最少样本 / 容差 | 50 / max(2pp, 1/N) | 评测集扩大后可收紧容差 |
| 文档版本保留 | 3 个 | 回退需求强时调大 |
| 回收站保留 | 30 天 | 按误删恢复窗口定 |
